# Vendor-native and cloud coding-agent orchestration (state as of 2026-09-20)

Scope: the multi-agent and parallel-agent features that model vendors and cloud agent platforms build themselves. Local third-party desktop orchestrators and general frameworks are out of scope except where they overlap. Where a claim is taken from a third-party blog or a search summary rather than vendor docs, it is marked **(secondary)**. Marketing claims are marked **(vendor claim)**. Dates are announcement or doc dates. Anthropic, Cursor, Cognition, Jules and GitHub facts were checked against primary docs fetched on 2026-09-20. The OpenAI Codex app page returned HTTP 403, so some Codex facts rest on secondary sources.

## Key question 0: What does each vendor ship for multi-agent and parallel work as of September 2026?

### Takeaway
Every major vendor now ships three layers: (1) in-session subagents, (2) a local or desktop surface for running many parallel sessions in git worktrees, and (3) a cloud coordinator agent that dispatches threads to cloud VMs and reports back through PRs. Claude Projects, Cursor Projects (Sept 10, 2026), Devin's Managed Devins, Factory Missions and Copilot `/fleet` are examples of layer 3. Almost all of them are single-vendor: the workers are the vendor's own agent. The cross-vendor exceptions are GitHub Agent HQ (Copilot, Claude and Codex, running on GitHub), Augment Intent (bring your own Claude Code, Codex or OpenCode) and OpenHands (ACP).

### Cited Findings

**Anthropic (Claude Code, Claude Platform)**
- Claude Code's docs list five ways to run parallel work: subagents, agent view, agent teams, dynamic workflows and projects. They also say plainly: "In every approach the workers are Claude sessions. To involve a different tool, expose it to Claude as an MCP server." — [Run agents in parallel](https://code.claude.com/docs/en/agents)
- **Subagents.** A subagent is defined as Markdown with YAML frontmatter in `.claude/agents/` or `~/.claude/agents/`, or passed with `--agents` JSON. Fields include `tools`, `disallowedTools`, `model`, `permissionMode`, `maxTurns`, `skills`, `mcpServers`, `hooks`, `memory` (user, project or local), `background`, `effort`, `isolation: worktree` and `initialPrompt`. Defaults: nesting depth 3 (`CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH`) and 20 concurrent subagents (`CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS`). The built-ins are Explore, Plan and general-purpose. Subagents are resumed through `SendMessage` by ID or name. — [Subagents](https://code.claude.com/docs/en/sub-agents)
- **Agent view** (`claude agents`, research preview). A separate supervisor daemon runs background sessions that survive the terminal closing, agent view closing, auto-updates and machine sleep. Sessions do not survive a shutdown; they show as failed and can be restarted within 48 hours. Before its first file edit, each session moves itself into a git worktree under `.claude/worktrees/`. It commits without asking, pushes when a remote exists and may open a draft PR, but never force-pushes or merges to main. Session states are Working, Needs input, Idle, Completed, Failed and Stopped. Scripts can read state with `claude agents --json`. Sessions start with `claude --bg`. Daemon control is `claude daemon status/stop`. — [Agent view](https://code.claude.com/docs/en/agent-view)
- **Agent teams** (experimental, off by default, enabled with `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1`; the docs describe v2.1.178+). A lead session spawns teammates, which are full independent Claude Code instances. They coordinate through a shared task list (pending, in progress, completed, with dependencies; claims use file locks) and a mailbox stored as JSON files at `~/.claude/teams/{team}/inboxes/{agent}.json`. The task list lives at `~/.claude/tasks/{team}/`. Display is in-process or split panes in tmux or iTerm2. Teammates are not spawned under `-p` or the Agent SDK. — [Agent teams](https://code.claude.com/docs/en/agent-teams)
- **Dynamic workflows.** Claude writes a JavaScript script using `agent()`, `pipeline()`, `parallel()` and `phase()`, and a runtime executes it in the background. The script holds the plan and intermediate results, so Claude's context receives only the final answer. Limits: 16 concurrent agents by default (configurable from 1 to 256), 4,096 items per `parallel()` or `pipeline()` call, and 1,000 agents per run. Runs can be resumed within a session. `ultracode` is the prompt keyword, and `/effort ultracode` (xhigh effort plus automatic workflows) is the session-wide form. `/deep-research` is bundled. Saved workflows live in `.claude/workflows/`. — [Workflows](https://code.claude.com/docs/en/workflows)
- `/batch` is a skill that "has Claude split one large change into 5 to 30 worktree-isolated subagents that each open a pull request." — [Run agents in parallel](https://code.claude.com/docs/en/agents)
- **Cloud sessions** (Claude Code on the web; research preview for Pro, Max and Team, plus some Enterprise seats). Each session is an isolated Anthropic-managed VM, or runs in a self-hosted environment. Sessions start from the browser, mobile, desktop, `claude --cloud "task"` (formerly `--remote`) or routines. `claude -p "msg" --cloud <session-id>` queues a follow-up into a running session. `--teleport` pulls a cloud session and its branch into the local terminal; the handoff is one-way from the CLI. — [Cloud sessions](https://code.claude.com/docs/en/claude-code-on-the-web)
- **Projects** (public beta on Pro and Max, rolling out; not yet on Team or Enterprise). "One ongoing conversation where Claude coordinates a stream of related work." The coordinator conversation starts **threads**. Each thread is a cloud session with its own context, working on its own branch and opening a PR. Every thread starts with the project's repos, instructions (up to 16,000 characters) and memory. An Overview pane groups threads as ready for review, waiting on you, working and landing. The coordinator "sees what threads report back, not every step they take." — [Projects](https://code.claude.com/docs/en/claude-projects)
- **Routines** (research preview). A routine is a saved prompt, repos and connectors that runs in the cloud on a schedule (minimum interval one hour), on an API call (`POST .../v1/claude_code/routines/{id}/fire` with a per-routine bearer token and beta header `experimental-cc-routine-2026-04-01`), or on GitHub `pull_request` or `release` events with filters. Each run is a new session with no permission-mode picker. — [Routines](https://code.claude.com/docs/en/routines). Routines reportedly launched in research preview on April 14, 2026 **(secondary)** — [buildfastwithai](https://www.buildfastwithai.com/blogs/claude-code-desktop-redesign-2026)
- **Ultrareview.** Ultrareview uploads the repo to a remote sandbox and runs "a fleet of reviewer agents" that look at a branch or PR from different angles. It reports only findings it could reproduce independently (April 2026) **(secondary)**. — [pasqualepillitteri.it](https://pasqualepillitteri.it/en/news/1301/claude-code-ultrareview-agents-cloud-2026)
- **Claude Managed Agents** (Claude Platform API, beta header `managed-agents-2026-04-01`). A coordinator agent can delegate to a roster of up to 20 agents, including `self` copies. Delegation goes **one level deep only**. A session supports at most 25 concurrent threads. All agents share one sandbox, filesystem and vault credentials, but each has its own persistent "session thread" with an isolated context and its own event stream at `/v1/sessions/{id}/threads/{thread_id}/stream`. An optional "advisor" model can be consulted mid-turn. A session budget is one shared cap across all threads. — [Managed Agents multiagent orchestration](https://platform.claude.com/docs/en/managed-agents/multiagent-orchestration)
- **Claude Tag** is an organisation-managed @Claude in Slack channels, running on the same cloud infrastructure. — [Cloud sessions](https://code.claude.com/docs/en/claude-code-on-the-web); [Projects](https://code.claude.com/docs/en/claude-projects)

### Inferences
- The industry has converged on **coordinator → cloud threads → PRs → human review in an Overview/Inbox**. Claude Projects, Cursor Projects and Managed Devins are nearly the same design, all launched between March and September 2026.
- **Claude Code agent view and the Codex app are the closest vendor-native overlap with Wanigan.** Both run parallel local sessions with worktree isolation, a daemon or supervisor so sessions outlive the terminal, a states view (needs input, working, done) and scriptable status (`claude agents --json`). But each drives only its own vendor's agent. Wanigan's multi-harness PTY model (Claude Code, Codex, GLM and others), its SQLite evidence record and its cross-repo operator review are not duplicated by any single-vendor product. The nearest cross-vendor products are Augment Intent (local, BYO agent, spec-centred), OpenHands (ACP-centred) and GitHub Agent HQ (cloud, GitHub-bound).
- Vendors are putting a **model** in the coordinator seat. Wanigan puts a **human operator** there. That difference is the clearest line of differentiation.

## Key question 1: Orchestration model — how is work decomposed, and by whom?

### Takeaway
There are four models in production. (a) A lead model delegates to workers, and results flow back up; this is the default everywhere. (b) Peer teams with a shared task list and messaging, rare and marked experimental (Claude agent teams). (c) The plan lives in code: Claude workflows scripts, `/batch`, and OpenAI's "orchestrate via code". (d) Human-initiated parallel best-of-N or multi-agent comparison (Codex cloud attempts, Cursor `/best-of-n`, Agent HQ assigning several agents). Decomposition is increasingly done by a planner model, not the human. Cognition's and Cursor's published lessons both argue for hierarchy plus single-threaded writes over flat swarms.

### Cited Findings
- **Claude subagents.** The caller delegates and gets a summary back. Named subagents can message each other. Subagents can nest up to three levels. `tools: Agent(worker, researcher)` restricts which types a subagent may spawn. — [Subagents](https://code.claude.com/docs/en/sub-agents)
- **Claude agent teams.** The lead creates tasks. Teammates are assigned work or claim the next unassigned, unblocked task themselves. Claims are guarded by file locking, and dependencies unblock automatically. Messages are delivered to mailbox files, and idle teammates notify the lead. Teammates cannot spawn their own teammates, and there is one team per session. The docs suggest "5-6 tasks per teammate" and "3-5 teammates for most workflows." — [Agent teams](https://code.claude.com/docs/en/agent-teams)
- **Claude workflows.** The docs contrast who decides what runs next: for subagents it is "Claude, turn by turn"; for agent teams "the lead agent, turn by turn"; for workflows "the script". Intermediate results live in "script variables", and a workflow scales to "dozens to hundreds of agents per run". — [Workflows](https://code.claude.com/docs/en/workflows)
- **Claude Projects.** The coordinator "decides what becomes a thread," can route follow-ups to an existing thread, and can be told to "propose threads and wait for my go-ahead" or "run at most two threads at a time". Those limits are "instructions Claude keeps to, not enforced settings". — [Projects](https://code.claude.com/docs/en/claude-projects)
- **Managed Agents.** The coordinator delegates through a roster, threads persist so a follow-up to an earlier agent keeps its history, and delegation goes one level deep. — [Managed Agents](https://platform.claude.com/docs/en/managed-agents/multiagent-orchestration)
- **Anthropic pattern guidance.** "Building effective agents" (Dec 2024) defines *orchestrator-workers* as a central LLM that dynamically breaks a task down, delegates to workers and synthesises their results. It recommends the pattern where subtasks cannot be predicted in advance, with coding named as an example. It also defines parallelization in two forms, sectioning and voting. — [Anthropic, Building effective agents](https://www.anthropic.com/research/building-effective-agents)
- **Anthropic research system.** A lead (Opus 4) spawns subagents (Sonnet 4), with explicit effort-scaling rules: "simple queries: 1 agent/3-10 calls; complex: 10+ subagents". Subagents run synchronously. — [Anthropic engineering, Jun 13 2025](https://www.anthropic.com/engineering/multi-agent-research-system)
- **Anthropic C compiler experiment** (Feb 5, 2026). Sixteen parallel Claude (Opus 4.6) agents ran with **no orchestrator agent**. Each claimed a task by writing a file to `current_tasks/`, and git sync forced a conflicting claimant to pick something else. An infinite bash loop restarted sessions. — [Anthropic engineering](https://www.anthropic.com/engineering/building-c-compiler)
- **Codex.** Codex spawns subagents on its own initiative or when asked, and "handles spawning, routing, waiting for results, and thread closure automatically." — [Codex subagents](https://learn.chatgpt.com/docs/agent-configuration/subagents)
- **Copilot `/fleet`.** The orchestrator breaks the task down, finds what can run in parallel, sends it out in waves and polls. Subagents do not talk to each other: "only the orchestrator coordinates." — [GitHub blog](https://github.blog/ai-and-ml/github-copilot/run-multiple-agents-at-once-with-fleet-in-copilot-cli/)
- **Cursor's research harness** (Jan 14, 2026). Planners, which can spawn sub-planners recursively, create tasks. Workers "don't coordinate with other workers" and push when done. A judge decides whether to continue at the end of each cycle. — [Cursor blog: Scaling agents](https://cursor.com/blog/scaling-agents)
- **Cursor Projects.** The coordinator plans and delegates but never writes code. — [Cursor blog: Projects](https://cursor.com/blog/projects)
- **Devin.** The coordinator scopes the work, assigns pieces, "resolves any conflicts, and compiles the results." — [Cognition](https://cognition.com/blog/devin-can-now-manage-devins)
- **Factory Missions.** The human and Droid co-write a plan of features and milestones. The orchestrator executes it and runs a validation phase at every milestone. — [Factory docs](https://docs.factory.ai/features/missions/overview)
- **Augment Intent.** Coordinator, then Implementors (in waves), then Verifier, around a spec that updates as work completes. — [Augment](https://www.augmentcode.com/blog/intent-a-workspace-for-agent-orchestration)
- **Task queue from issues.** Copilot takes an issue assignment and returns a PR. — [GitHub Docs](https://docs.github.com/en/copilot/concepts/agents/coding-agent/about-coding-agent). The Jules API creates tasks from Linear or Jira. — [Jules changelog](https://jules.google/docs/changelog/). Factory's Linear and Jira integrations make "tickets into the native unit of work" **(secondary)**. — [Digital Applied](https://www.digitalapplied.com/blog/factory-ai-multi-agent-coding-platform-review)
- **Best-of-N and comparison.** Codex cloud runs 1–4 attempts. — [Codex KB](https://codex.danielvaughan.com/2026/05/31/codex-cloud-environments-setup-scripts-caching-secrets-codex-universal/) **(secondary)**. Agent HQ can assign Copilot, Claude and Codex to the same task. — [GitHub blog](https://github.blog/news-insights/company-news/pick-your-agent-use-claude-and-codex-on-agent-hq/). Cursor 2.0 runs "up to eight agents on a single problem". — [Wikipedia](https://en.wikipedia.org/wiki/Cursor_(company))
- **Advisor pattern.** Claude Managed Agents has an `advisor` roster entry, a stronger model consulted mid-turn. — [Managed Agents](https://platform.claude.com/docs/en/managed-agents/multiagent-orchestration). Amp's Oracle is a second-opinion model. — [Alex Dunlop](https://www.alexdunlop.com/writing/amp-vs-claude-code-worth-switching-2026). Cognition calls this the "Smart Friend" pattern. — [Cognition](https://cognition.com/blog/multi-agents-working)

### Inferences
- Peer messaging between workers is still the exception. Claude agent teams have it but are experimental. Copilot `/fleet` workers explicitly cannot message each other. Managed Agents workers talk only to the coordinator. Hub-and-spoke with a single writer is the dominant shape.
- "Plan as code" (Claude workflows, OpenAI "orchestrate via code") is a notable 2026 move: repeatable, resumable and auditable orchestration rather than turn-by-turn model judgement. It is a natural fit for Wanigan's evidence and review model, which wants runs that can be inspected and replayed.

### Gaps
- No vendor publishes the planner prompts or decomposition heuristics behind Cursor Projects or Claude Projects coordinators.
- How Cursor Projects' "thousands of subagents" are bounded in practice (concurrency caps, per-project limits) is not documented in the sources I read.

## Key question 2: Isolation and execution — sandboxes, VMs, worktrees, durability, resume

### Takeaway
Locally, the unit of isolation is the git worktree: Claude agent view isolates automatically before the first edit, subagents opt in with `isolation: worktree`, and Codex, Cursor, Augment and Antigravity all use worktrees. In the cloud it is one VM or container per session or thread: Claude cloud, Codex cloud, Copilot on Actions, Jules, Devin, Cursor and Amp orbs. Durability comes from vendor daemons locally and from cloud sessions that outlive the laptop. Resume is uneven, and several in-context team or subagent features do not survive a session resume.

### Cited Findings
- **Claude subagents with `isolation: worktree`.** The worktree branches from the default branch, not the parent's HEAD. It is cleaned up if nothing changed. Commands that point git back at the main checkout, or compute git paths at runtime, are refused. — [Subagents](https://code.claude.com/docs/en/sub-agents)
- **Agent teams do not use worktrees.** The docs say "Two teammates editing the same file leads to overwrites. Break the work so each teammate owns a different set of files." — [Agent teams](https://code.claude.com/docs/en/agent-teams); [Run agents in parallel](https://code.claude.com/docs/en/agents)
- **Agent view durability.** Sessions survive terminal close, agent view close, auto-update and sleep. After shutdown they are recoverable, showing as "failed" within 48 hours. A finished session left unattached for over an hour is stopped, but its transcript stays on disk. — [Agent view](https://code.claude.com/docs/en/agent-view)
- **Claude cloud sessions.** Each runs in an isolated VM with network allowlist levels (the Default environment is "Trusted"). Git credentials and signing keys stay outside the sandbox, and a proxy authenticates with scoped credentials. When the environment expires, reopening provisions a fresh VM with the conversation restored, but "background work that was still running... such as subagents and shell commands, isn't restored." Without GitHub, the CLI can upload a git bundle under 100 MB and leaves out `.env`, `*.tfvars` and key files. — [Cloud sessions](https://code.claude.com/docs/en/claude-code-on-the-web)
- **Claude Projects threads** "clone... repositories into [their] own cloud sandbox and work on [their] own branch" and do not need worktrees. — [Projects](https://code.claude.com/docs/en/claude-projects)
- **Resume limits in agent teams.** "/resume and /rewind do not restore in-process teammates." The task list persists locally, and the team config is deleted when the session ends. — [Agent teams](https://code.claude.com/docs/en/agent-teams)
- **Workflow resume** replays completed agents from saved results. A failed agent causes it and every later agent to rerun. Runs carry over when a session is backgrounded, and in cloud sessions results survive VM reclamation. `Date.now()` and `Math.random()` throw inside scripts so that replays are deterministic. — [Workflows](https://code.claude.com/docs/en/workflows)
- **Managed Agents.** All threads share one sandbox and filesystem. "Session, harness, and sandbox are fully decoupled, with vault credentials never entering the sandbox" **(secondary summary of docs)**. — [Managed Agents](https://platform.claude.com/docs/en/managed-agents/multiagent-orchestration)
- **Codex cloud.** The internet is available during the setup script but "off by default" during the agent phase, and can be configured to limited or unrestricted. All outbound traffic goes through an HTTP/HTTPS proxy. — [OpenAI: agent internet access](https://developers.openai.com/codex/cloud/internet-access); [Codex KB](https://codex.danielvaughan.com/2026/05/31/codex-cloud-environments-setup-scripts-caching-secrets-codex-universal/) **(secondary)**
- **Codex subagents** inherit the parent's sandbox policy and permission mode, and custom agents can override `sandbox_mode`. — [Codex subagents](https://learn.chatgpt.com/docs/agent-configuration/subagents). The CLI got experimental worktree support in 0.154.0 (Sept 2026), and the app-server daemon keeps saved threads through restarts. — [Changelog](https://learn.chatgpt.com/docs/changelog)
- **Copilot cloud agent.** An ephemeral Actions environment, a 59-minute hard cap, one repo, one branch and one PR per task. — [GitHub Docs](https://docs.github.com/en/copilot/concepts/agents/coding-agent/about-coding-agent). Copilot CLI `/fleet` subagents share the filesystem with no isolation. — [GitHub blog](https://github.blog/ai-and-ml/github-copilot/run-multiple-agents-at-once-with-fleet-in-copilot-cli/)
- **Jules** runs in a cloud VM with environment snapshots for faster starts and a 20 GB disk. — [Jules changelog](https://jules.google/docs/changelog/)
- **Devin.** Each managed Devin runs in its own VM with a terminal, a browser and a dev environment. — [Cognition](https://cognition.com/blog/devin-can-now-manage-devins)
- **Cursor.** Subagents run on isolated VMs (Aug 19, 2026). Self-hosted "My Machines" and team pools, plus AWS Lambda, Vercel and Modal infrastructure (Sept 2, 2026). — [Cursor changelog](https://cursor.com/changelog). A Project runs on its own cloud computer and syncs shared files across machines. — [Cursor Projects](https://cursor.com/blog/projects)
- **Self-hosted cloud environments** for Claude cloud sessions and routines: "isolation is your deployment's responsibility." — [Cloud sessions](https://code.claude.com/docs/en/claude-code-on-the-web)
- The **C compiler experiment** used one Docker container per agent with the repo mounted at `/workspace`, and git pull, merge and push to sync. — [Anthropic engineering](https://www.anthropic.com/engineering/building-c-compiler)

### Inferences
- Vendors are converging on the same local primitive Wanigan relies on: a long-lived supervisor that owns agent processes separately from the UI. Claude's `claude daemon` and Codex's background server with daemon lifecycle commands both follow it. Claude's agent view documents what Wanigan's guardrail already states, that sessions do not survive a machine shutdown and only transcripts do. Vendor behaviour supports that honesty.
- Worktree isolation is now expected. Products without it (Copilot `/fleet`, Claude agent teams) carry explicit "last writer wins" or "partition the files" warnings.

### Gaps
- Cursor's local-vs-cloud handoff inside Projects ("spins up a local agent") is not documented at mechanism level.
- I did not verify the VM isolation technology (Firecracker, gVisor or other) for any vendor.

## Key question 3: Integration — issue trackers, PRs, CI, Slack/Linear triggers, MCP, programmatic dispatch

### Takeaway
The PR is the universal output contract. The universal triggers are GitHub events, Slack and Linear/Jira. Programmatic dispatch exists through several routes: Claude's routine `/fire` API, the `claude -p --cloud` follow-up queue and the Managed Agents API; the Codex SDK and app-server; the Jules REST API; and Copilot through issues and MCP. "Watch the PR and auto-fix CI and review comments" has become a standard feature (Claude, Jules, Cursor).

### Cited Findings
- **Claude routines** have three trigger types: schedule, HTTP API and GitHub events. The API returns `claude_code_session_id` and URL. GitHub triggers filter on author, title, body, base and head branch, labels, draft and merged, with regex. Webhook events above hourly caps are dropped. Connectors (MCP) are all included by default, and Claude "can use every tool from an included connector, including writes, without asking". — [Routines](https://code.claude.com/docs/en/routines)
- **Claude cloud auto-fix PR.** Claude subscribes to a PR's CI failures and review comments, pushes fixes when the fix is clear, and asks when a comment is ambiguous. It cannot react to merge conflicts, because GitHub sends no webhook for them. Replies post under the user's GitHub account, labelled as Claude Code. The docs warn about comment-triggered automation such as Atlantis. — [Cloud sessions](https://code.claude.com/docs/en/claude-code-on-the-web)
- **Programmatic follow-ups:** `claude -p "msg" --cloud <id>` with `--output-format json` returning `{ok, session_id, url}`. — [Cloud sessions](https://code.claude.com/docs/en/claude-code-on-the-web). Cross-session messaging lets Claude message a user's other sessions, whether local, on another machine or in the cloud. — [Run agents in parallel](https://code.claude.com/docs/en/agents)
- **Headless and SDK constraints.** Agent teams do not spawn under `-p` or the Agent SDK. — [Agent teams](https://code.claude.com/docs/en/agent-teams). Workflows do run under `-p` and the SDK, gated by permission rules (`Workflow`, `Workflow(<name>)`), `PreToolUse` hooks, `--permission-prompt-tool` or the SDK's `canUseTool`. — [Workflows](https://code.claude.com/docs/en/workflows)
- **Managed Agents** give each thread its own event stream (SSE) for building custom UIs over subagent activity. — [Managed Agents](https://platform.claude.com/docs/en/managed-agents/multiagent-orchestration)
- **Copilot** entry points: issues, the Agents panel, VS Code, `@copilot` in PRs, Slack, Teams, Azure Boards, Jira and Linear. MCP is configurable. — [GitHub Docs](https://docs.github.com/en/copilot/concepts/agents/coding-agent/about-coding-agent). Agent HQ: `@Claude` and `@Codex` mentions in PR comments, and an Agents tab per repository. — [GitHub blog](https://github.blog/news-insights/company-news/pick-your-agent-use-claude-and-codex-on-agent-hq/)
- **Jules:** REST API (task creation, repoless sessions, git-patch output, `createTime` filtering), CLI, CI Auto-Fix, PR-comment feedback (`@Jules`), curated MCP (Linear, Supabase, Neon and others) and Render build-failure integration. — [Jules changelog](https://jules.google/docs/changelog/)
- **Codex:** the Python SDK gained `ExternalMessage`, resume and fork `include_turns`, and a per-turn service tier. App-server APIs cover stored thread attachments. MCP OAuth refresh coordination was added. — [Changelog](https://learn.chatgpt.com/docs/changelog). Codex triggers from Slack and Linear create cloud tasks **(secondary)**. — [Codex KB](https://codex.danielvaughan.com/2026/03/27/codex-slack-linear-cloud-tasks/)
- **Cursor:** cloud agents subscribe to PRs and Slack threads. It has native code hosting (Origin), with Vercel, Depot and Buildkite CI and Vercel publishing. — [Cursor changelog](https://cursor.com/changelog)
- **Gemini CLI** delegates to remote agents over A2A. — [Gemini CLI remote subagents](https://geminicli.com/docs/core/remote-agents/)
- **OpenHands** controls third-party coding agents through ACP. — [OpenHands blog](https://www.openhands.dev/blog/use-any-coding-agent-in-openhands-with-acp)

### Inferences
- Every vendor cloud product assumes GitHub as the code host and identity. Claude Projects needs the Claude GitHub App and does not support GHES, GitLab or Bitbucket. Cursor now hosts code itself. Wanigan's local-first model, which works on any local checkout, avoids that dependency.
- MCP is the de facto cross-tool extension point. A2A (Gemini CLI) and ACP (OpenHands) are the emerging agent-to-agent and agent-control protocols. They are the likely standard seams for driving other vendors' agents without scraping a PTY.

### Gaps
- Official Codex cloud trigger docs (Slack, Linear, GitHub) were not fetched directly.
- I found no official Cursor API reference for programmatic Project dispatch.

## Key question 4: Supervision and trust — review gates, approvals, audit, cost controls, observability

### Takeaway
Vendors rely on four controls: (1) PR review as the final gate, with agents confined to prefixed branches; (2) hook or exit-code gates on task completion; (3) permission modes inherited by workers, with prompts bubbling up to the lead; (4) usage and budget caps plus per-thread token dashboards. Two design choices stand out. Claude Code treats inter-agent and trigger payloads as untrusted and never as user consent. The Claude agent-team lead **auto-approves** teammates' plans. Hard caps are few, and the documented ones are mostly Anthropic's. Several vendors note that a green status does not mean the task succeeded.

### Cited Findings
- **Claude quality gates through hooks:** `TeammateIdle`, `TaskCreated` and `TaskCompleted`. A hook that exits with code 2 blocks the action and sends feedback. `SubagentStart` and `SubagentStop` hooks exist, as do per-subagent `PreToolUse` and `PostToolUse` in frontmatter. — [Agent teams](https://code.claude.com/docs/en/agent-teams); [Subagents](https://code.claude.com/docs/en/sub-agents)
- **Plan approval in agent teams.** "Claude Code approves the plan in the lead's session as soon as the request arrives, without the lead reviewing it." Edits still go through permission prompts, which appear in the lead's session. Teammates inherit the lead's permission mode, including `--dangerously-skip-permissions`. — [Agent teams](https://code.claude.com/docs/en/agent-teams)
- **Inter-agent messages are not consent.** "A teammate can't approve a permission prompt or supply consent on your behalf." In auto mode, a classifier reviews each inter-agent message before delivery and treats relayed approval claims as untrusted. — [Agent teams](https://code.claude.com/docs/en/agent-teams). Subagent reports are scanned, and text that imitates system tags is escaped (v2.1.210+). — [Subagents](https://code.claude.com/docs/en/sub-agents)
- **Untrusted trigger payloads.** Routine fire `text` is wrapped in `<routine-fire-payload>` and labelled untrusted, so the saved prompt must opt in to acting on it. The fired prompt "can't act as approval or consent." The `ultracode` keyword does not start a workflow when it arrives through `-p`, a webhook or a PR comment (a v2.1.210 fix). — [Routines](https://code.claude.com/docs/en/routines); [Workflows](https://code.claude.com/docs/en/workflows)
- **Branch confinement.** Routines push to `claude/`-prefixed branches. A push elsewhere is refused if the branch is protected, has someone else's open PR, or carries another author's commits. — [Routines](https://code.claude.com/docs/en/routines). Agent view never force-pushes or merges to main. — [Agent view](https://code.claude.com/docs/en/agent-view). Copilot works on one branch with one PR, and org rulesets apply. — [GitHub Docs](https://docs.github.com/en/copilot/concepts/agents/coding-agent/about-coding-agent)
- **"Green isn't success."** A green routine status "does not mean the task in your prompt succeeded. Open the run to read the transcript." — [Routines](https://code.claude.com/docs/en/routines). The Codex changelog shows goals that "block after three empty automatic continuation turns". — [Changelog](https://learn.chatgpt.com/docs/changelog)
- **Hard caps (Anthropic):**
  - Projects: 200 new threads per day. The concurrency limits a user asks for are "a preference rather than a cap". — [Projects](https://code.claude.com/docs/en/claude-projects)
  - Workflows: 1,000 agents per run and 16 concurrent by default. A "Large workflow" warning appears above 25 agents or 1.5M projected tokens, and it is advisory only. — [Workflows](https://code.claude.com/docs/en/workflows)
  - Subagents: 20 concurrent and depth 3. — [Subagents](https://code.claude.com/docs/en/sub-agents)
  - Managed Agents: 25 concurrent threads, and a session budget shared across threads under which threads pause independently. — [Managed Agents](https://platform.claude.com/docs/en/managed-agents/multiagent-orchestration)
  - Routines: a daily run cap. — [Routines](https://code.claude.com/docs/en/routines)
- **Usage-limit behaviour.** Claude Projects threads that hit plan limits "keep retrying on its own and continues when the limit resets", so left-running work consumes the next usage window automatically. — [Projects](https://code.claude.com/docs/en/claude-projects)
- **Observability.** Projects have a per-thread and per-model usage view. — [Projects](https://code.claude.com/docs/en/claude-projects). `/workflows` shows per-phase agent counts, token totals and elapsed time, and each agent's recent tool calls. — [Workflows](https://code.claude.com/docs/en/workflows). Devin shows ACU per child session. — [Cognition](https://cognition.com/blog/devin-can-now-manage-devins). Agent HQ has audit logging, agent and model access policies and a Copilot metrics dashboard. — [GitHub blog](https://github.blog/news-insights/company-news/pick-your-agent-use-claude-and-codex-on-agent-hq/)
- **Admin controls.** Team and Enterprise owners can disable routines, cloud sessions (`allow_remote_sessions`) and workflows (`disableWorkflows` in managed settings). An `availableModels` allowlist substitutes a permitted model for a blocked teammate model. — [Routines](https://code.claude.com/docs/en/routines); [Cloud sessions](https://code.claude.com/docs/en/claude-code-on-the-web); [Workflows](https://code.claude.com/docs/en/workflows); [Agent teams](https://code.claude.com/docs/en/agent-teams)
- **Codex safety work** (Sept 2026 changelog): "Guardian" review with context-budget enforcement, Touch ID verification for MCP requests, and hardened WSL sandbox escapes. — [Changelog](https://learn.chatgpt.com/docs/changelog)
- **Verifier and critic agents as gates.** Jules' Planning Critic (−9.5% task failures, **vendor claim**). — [Jules changelog](https://jules.google/docs/changelog/). Augment's Verifier checks work before human review. — [Augment](https://www.augmentcode.com/blog/intent-a-workspace-for-agent-orchestration). Factory validates at every milestone. — [Factory docs](https://docs.factory.ai/features/missions/overview). Antigravity uses Artifacts with document-style comments as its review surface. — [Google Developers Blog](https://developers.googleblog.com/build-with-google-antigravity-our-new-agentic-development-platform/)
- **Review intensity decays by design.** Cursor says: "As the fixes hold up, you review less, and the coordinator keeps working through the migration on its own." — [Cursor Projects](https://cursor.com/blog/projects)

### Inferences
- Vendors document trust mechanisms (untrusted-payload wrapping, no consent through relay, branch prefixes) but keep evidence inside their own session viewers. No vendor offers a cross-vendor, locally owned evidence record. That is Wanigan's lane.
- The auto-approved teammate plans and the idea of reviewing less over time mark a real philosophical split from Wanigan's "operator reviews, estimates are not facts" premise. Wanigan can present itself as the review layer for exactly these autonomous fleets.
- Cost controls are mostly advisory (warnings, "preference rather than cap") or plan-level (subscription windows). Per-task hard budgets exist only on Anthropic's API (Managed Agents session budgets). Metered, per-run cost evidence is a weak spot across vendors.

### Gaps
- I found no vendor-published audit log schema for Claude Projects, Cursor Projects or Devin that is exportable for cross-tool review.
- Agent HQ's governance specifics (log retention, per-agent policy granularity) are described only at marketing level.

## Key question 5: Published results and lessons — when multi-agent helps or hurts

### Takeaway
The best evidence says multi-agent helps on breadth-first, parallelizable work (research, review, audits, migrations with a test oracle) and hurts on tightly coupled writes. Token cost rises roughly 4× for an agent and roughly 15× for a multi-agent system relative to chat (Anthropic, 2025), and run-to-run cost variance can reach 30× (Stanford, 2026). Coordination by locks or flat peers failed at Cursor. Cognition moved from "don't build multi-agents" (2025) to "single writer, many contributors" (2026).

### Cited Findings
- **Anthropic research system** (Jun 13, 2025). The multi-agent version (Opus 4 lead, Sonnet 4 subagents) "outperformed single-agent Claude Opus 4 by 90.2%" on an internal research eval. Agents use about 4× the tokens of chat, and multi-agent systems about 15×. Token usage explains 80% of BrowseComp variance, and tokens, tool calls and model together explain 95%. Coding is named a poor fit: "domains that require all agents to share the same context or involve many dependencies between agents are not a good fit." Synchronous subagents create bottlenecks. Production needs durable execution with resumption, full tracing, and "rainbow deployments" so running agents are not disrupted. — [Anthropic engineering](https://www.anthropic.com/engineering/multi-agent-research-system)
- **Anthropic C compiler** (Feb 5, 2026). Sixteen agents, about 2,000 sessions over two weeks, 2B input and 140M output tokens, about $20,000. The result was a 100,000-line Rust C compiler that builds Linux 6.9 on x86, ARM and RISC-V. The key enabler for parallelism on a monolithic task was a **test oracle**: compile most of the kernel with GCC and only some files with the new compiler, so agents could work on different files. Its limits: no 16-bit x86, no assembler or linker, and inefficient generated code. — [Anthropic engineering](https://www.anthropic.com/engineering/building-c-compiler)
- **Cursor scaling agents** (Jan 14, 2026). A shared file with locks failed: agents held locks too long or forgot them, and 20 agents' throughput fell to "two or three". Optimistic concurrency made agents "risk-averse" and caused churn. A flat structure produced "small, safe changes". An integrator role "created more bottlenecks than it solved." What worked was planners, workers and a judge, run over hundreds of concurrent agents for about a week, producing over 1M LOC and a browser from scratch at "trillions of tokens". GPT-5.2 beat Opus 4.5 for long autonomous runs, and choosing models per role helped. Open problems: planners lack event triggers, agents sometimes run too long, and periodic fresh starts are needed to fight drift. — [Cursor blog](https://cursor.com/blog/scaling-agents). Simon Willison discussed the post. — [simonwillison.net](https://simonwillison.net/2026/Jan/19/scaling-long-running-autonomous-coding/)
- **Cognition, "Don't Build Multi-Agents"** (2025): share full context and traces; actions carry implicit decisions; parallel writers make conflicting choices. — [Cognition](https://cognition.com/blog/dont-build-multi-agents)
- **Cognition, "Multi-Agents: What's Actually Working"** (Walden Yan, Apr 22, 2026). "Multiple agents contribute intelligence to a task while writes stay single-threaded." Three patterns work:
  - *Code-Review Loop*: the reviewer starts with a clean context and avoids "context rot". Devin Review averages "2 bugs per PR, of which roughly 58% are severe" **(vendor claim)**.
  - *Smart Friend*: escalation to a frontier model. It failed with SWE-1.5 as the primary because the gap was too wide, and works across frontier models.
  - *Map-reduce-and-manage*: live in Devin, but "requires extensive prompt-tuning". Managers become overly prescriptive, children assume shared state, and cross-agent communication does not emerge naturally.

  Unstructured swarms are dismissed. — [Cognition](https://cognition.com/blog/multi-agents-working)
- **Claude Code docs' own guidance.** Teams "use significantly more tokens"; "for sequential tasks, same-file edits, or work with many dependencies, a single session or subagents are more effective"; "Three focused teammates often outperform five scattered ones"; start with research and review rather than parallel implementation. — [Agent teams](https://code.claude.com/docs/en/agent-teams)
- **Competing hypotheses.** Claude docs recommend adversarial teammates for debugging because "sequential investigation suffers from anchoring." — [Agent teams](https://code.claude.com/docs/en/agent-teams). Claude workflows recommend adversarial cross-verification, and `/deep-research` votes on each claim and drops claims that fail cross-checking. — [Workflows](https://code.claude.com/docs/en/workflows)
- **Cost unpredictability** (Stanford Digital Economy Lab, May 5, 2026). The same agent on the same task varied up to 30× in tokens. Agentic tasks used about 1,000× more tokens than code chat, driven by input tokens. Models underestimate their own spend. — [Stanford DEL](https://digitaleconomy.stanford.edu/news/how-are-ai-agents-spending-your-tokens/)
- **Factory** admits that parallelization efficacy and cost-versus-quality tradeoffs are unresolved. — [Factory docs](https://docs.factory.ai/features/missions/overview)
- **Vendor productivity claims:** new Cursor Projects users make "30% more PRs", and primary users merge "six times as many" **(vendor claim, no methodology)**. — [Cursor Projects](https://cursor.com/blog/projects). Anthropic's 2026 Agentic Coding Trends Report calls multi-agent coordination a defining 2026 trend, citing a 12.5M-line codebase change in one 7-hour run **(secondary summaries of the report)**. — [Tessl summary](https://tessl.io/blog/8-trends-shaping-software-engineering-in-2026-according-to-anthropics-agentic-coding-report); [Report](https://resources.anthropic.com/2026-agentic-coding-trends-report)

### Inferences
- A pattern runs through all of this. Parallelism pays when there is (a) a mechanical oracle (tests, a compiler, a reference implementation), (b) a partition of files or modules, or (c) read-only intelligence work (review, research, hypotheses). It fails when shared mutable state has to be coordinated by agents themselves. Wanigan's review surface should make those three preconditions visible, so the operator can see whether a fan-out had an oracle and a partition.
- Cost variance (30×) and the vendors' advisory-only caps both favour Wanigan's policy of metering from recorded runs rather than estimates.

### Gaps
- No controlled, third-party A/B study compares a multi-agent coding setup against a single agent on held-fixed SWE tasks with cost. Vendor numbers are internal or anecdotal.
- Anthropic's claude.com post "Building multi-agent systems: when and how to use them", linked from the Managed Agents docs, was not fetched.

## Key question 6: What developers praise and complain about

### Takeaway
Developers praise fire-and-forget async work, worktree isolation, fresh-context reviewers and "second opinion" models. They complain about token burn from automatic subagent fan-out, subagents re-reading context, silent file clobbering, flaky team coordination (task status lag, orphaned sessions, leads doing the work themselves), and a review bottleneck: generation has scaled 10× but human review has not.

### Cited Findings
- **Hacker News (thread about 70 days old at fetch time, so roughly July 2026).** "What really burns tokens is sub agents. I once gave Claude Code a pretty big task, and it immediately launched 7 sub agents which burned through my budget before even one of them was finished."
