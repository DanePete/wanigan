# General-purpose AI agent orchestration frameworks and protocols: the primitives they define (as of September 2026)

Scope note: research done 2026-09-20. Sources are official docs, specs and vendor engineering blogs where possible. Third-party blogs and search-result summaries are marked as such. Several frameworks shipped major versions between April and August 2026 (MCP 2026-07-28, A2A 1.0, Microsoft Agent Framework 1.0, ADK 2.0, OpenAI Agents SDK sandbox update), so anything older than April 2026 about these projects is probably out of date.

## Q1. The leading frameworks: orchestration model, state, persistence and resume, human-in-the-loop, parallelism, retries, budgets, observability

### Takeaway
By late 2026 the main frameworks have converged on one design: a graph or workflow engine runs underneath, and agent-level patterns (handoff, group chat, supervisor) sit on top of it. State is saved at step boundaries, and a run can pause for a human, be serialized, and resume later. Google ADK 2.0 deprecated its Sequential, Parallel and Loop agents in favour of graphs. Microsoft Agent Framework 1.0 builds every multi-agent pattern on a superstep workflow engine. The OpenAI Agents SDK added sandboxed workspaces and a serializable `RunState`. The main remaining split is between checkpointing (saving snapshots and resuming by hand) and true durable execution (detecting failure and restarting automatically without repeating side effects). The second is still mostly supplied by Temporal, Restate, DBOS and Dapr rather than by the agent frameworks themselves.

### Cited Findings

**LangGraph / LangSmith (LangChain)**
- LangGraph 1.0 and LangChain 1.0 were released October 22, 2025. The core pitch is durable state, built-in persistence, first-class human-in-the-loop pausing, and streaming and memory. LangChain 1.0's `create_agent` is "built on the LangGraph runtime", and LangChain 1.0 added middleware, including prebuilt human-in-the-loop approval, summarization and PII redaction — [LangChain blog](https://www.langchain.com/blog/langchain-langgraph-1dot0)
- Named production users: Uber, LinkedIn, Klarna, JP Morgan, BlackRock, Cisco, Rippling. "90M monthly downloads" across LangChain and LangGraph — [LangChain blog](https://www.langchain.com/blog/langchain-langgraph-1dot0) (vendor-reported)
- Persistence model: checkpointers save graph state as snapshots inside a thread (`thread_id`) and enable "conversation continuity, human-in-the-loop workflows, time travel, and fault tolerance". `PostgresSaver` and `SqliteSaver` are recommended for production over `InMemorySaver` — [LangGraph docs: durable execution](https://docs.langchain.com/oss/python/langgraph/durable-execution)
- LangGraph Platform was renamed LangSmith Deployment (October 2025), sold as "deploy in one click and get durable execution, state, and streaming out of the box" — [LangSmith Deployment](https://www.langchain.com/langsmith/deployment); rename date per search summary of the same page.
- Latest version seen: LangGraph 1.2.4 (June 2, 2026) — search summary of the [LangGraph GitHub](https://github.com/langchain-ai/langgraph); not verified against the release page.
- Temporal ships a LangGraph plugin that adds Temporal's durable execution underneath LangGraph. That a plugin exists at all suggests LangGraph's own checkpointing is not treated as full durable execution — [Temporal blog](https://temporal.io/blog/temporal-langgraph-plugin-durable-execution)
- Caution: one search summary put "LangGraph 1.0" in April 2026. That is wrong; the primary source gives October 22, 2025.

**Microsoft Agent Framework (successor to AutoGen and Semantic Kernel)**
- Version 1.0 shipped April 3, 2026 for .NET and Python as "production-ready" with "stable APIs, and a commitment to long-term support". It unifies "the enterprise-ready foundations of Semantic Kernel with the innovative orchestrations of AutoGen", and migration guides are available — [Microsoft devblog](https://devblogs.microsoft.com/agent-framework/microsoft-agent-framework-version-1-0/)
- Orchestration patterns: sequential, concurrent, handoff, group chat and Magentic-One. All of them support "streaming, checkpointing, human-in-the-loop approvals, and pause/resume". They sit on a graph workflow engine that can "branch on conditions, fan out to parallel steps, and converge results". Observability is OpenTelemetry. It supports MCP for tools and A2A for "cross-runtime agent collaboration" — [Microsoft devblog](https://devblogs.microsoft.com/agent-framework/microsoft-agent-framework-version-1-0/)
- Checkpoint semantics: a checkpoint is created "at the end of each superstep, after all executors in that superstep have completed". It captures every executor's state, all messages pending for the next superstep, pending requests and responses (that is, outstanding human-in-the-loop requests), and shared state — [Microsoft Learn: checkpoints](https://learn.microsoft.com/en-us/agent-framework/workflows/checkpoints). This is a Pregel/BSP-style model.
- Critique from a vendor (Diagrid, the Dapr company; post dated March 2, 2026; it pitches Dapr Workflows): resume needs a checkpoint ID supplied by hand, and nothing restarts automatically. There is no heartbeat or lease, so two processes can resume the same checkpoint at once. Superstep-level checkpoints lose partial work inside a step. True durability depends on the Azure Durable Task extension — [Diagrid](https://www.diagrid.io/blog/still-not-durable-how-microsoft-agent-framework-and-strands-agents-repeat-the-same-mistake)

**OpenAI Agents SDK**
- Core primitives as documented: Agents ("LLMs equipped with instructions and tools"), Handoffs ("allow agents to delegate to other agents"), Guardrails ("validation of agent inputs and outputs"), Sessions (persistent memory across turns), Sandbox Agents, Realtime and voice agents, MCP integration, human-in-the-loop, and built-in tracing "for visualizing, debugging, and monitoring workflows" tied into OpenAI evals and fine-tuning — [OpenAI Agents SDK docs](https://openai.github.io/openai-agents-python/)
- The 2026-04-15 update brought three primitives together: a "model-native harness" (the control plane), native sandbox execution (the compute plane), and configurable memory (session plus sandbox) — [DEV Community summary](https://dev.to/rams901/openai-agents-sdk-sandbox-execution-and-model-native-harness-in-2026-37jn) (third-party; the date was not confirmed on an OpenAI page)
- Sandbox agents: a Manifest sets up the fresh workspace (files, repos, mounts, env vars, OS accounts). There are provider clients for Blaxel, Cloudflare, Daytona, Docker, E2B, Modal, Runloop, Unix-local and Vercel. Three state surfaces exist: `RunState` (model items, tool state, approvals), serialized sandbox session state (for reconnecting), and workspace snapshots (to seed fresh sandboxes). A handoff makes the sandbox agent the active agent for the next turn, while agents-as-tools nests sandbox agents as tool calls. The memory capability consolidates into `MEMORY.md` after a session closes — [OpenAI sandbox agents guide](https://developers.openai.com/api/docs/guides/agents/sandboxes)
- Human-in-the-loop: a tool declares `needs_approval` (a boolean or a per-call function). Paused runs expose `RunResult.interruptions` (`ToolApprovalItem`). The caller converts with `result.to_state()`, calls `state.approve()` or `state.reject()`, and resumes with `Runner.run(agent, state)`. `RunState` serializes with `to_json()`/`from_json()` for long-lived approvals. Interruptions from handoff targets and nested `Agent.as_tool()` runs surface on the outer run. This works for function tools, `ShellTool`, `ApplyPatchTool`, and local and hosted MCP (`require_approval`). The docs warn: "never deserialize untrusted snapshots" — [OpenAI Agents SDK: HITL](https://openai.github.io/openai-agents-python/human_in_the_loop/)
- Temporal integration GA (Python) on March 23, 2026. The agent loop, tool selection and handoffs run inside a Temporal Workflow, and model calls run as Activities. `activity_as_tool()` makes tool calls durable. Rate-limited model calls wait for capacity and retry automatically — [Temporal blog](https://temporal.io/blog/announcing-openai-agents-sdk-integration); [Temporal docs](https://docs.temporal.io/develop/python/integrations/openai-agents)

**Claude Agent SDK (Anthropic)**
- It exposes "the same tools, agent loop, and context management that power Claude Code" as a Python and TypeScript library. Capabilities: built-in tools, hooks, subagents, MCP, permissions, sessions ("resume or fork later"), skills, commands and memory loaded from `.claude/`, and plugins. Other languages are told to "run the CLI as a subprocess with the `-p` flag and `--output-format json`". Managed Agents is a separate hosted product for long-running asynchronous agents — [Claude Agent SDK overview](https://code.claude.com/docs/en/agent-sdk/overview)
- Licensing constraint relevant to any third-party orchestrator: "Unless previously approved, Anthropic does not allow third party developers to offer claude.ai login or rate limits for their products, including agents built on the Claude Agent SDK" — [Claude Agent SDK overview](https://code.claude.com/docs/en/agent-sdk/overview)
- Subagents get their own context window and tool permissions. SubagentStart and SubagentStop hooks fire around them. Sessions resume by passing back the `session_id` — [ksred.com](https://www.ksred.com/the-claude-agent-sdk-what-it-is-and-why-its-worth-understanding/); [hidekazu-konishi.com](https://hidekazu-konishi.com/entry/claude_agent_sdk_complete_guide.html) (third-party). One third-party guide counts about 30 hook events across session, prompt, tool, subagent, task, file and notification phases — [morphllm](https://www.morphllm.com/claude-code-hooks) (unverified count)
- Claude Code "agent teams" (experimental, off by default, `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1`): a lead session spawns teammate Claude Code instances. They share a task list with automatic dependency unblocking and a "mailbox" for direct agent-to-agent messages — [Claude Code docs: agent teams](https://code.claude.com/docs/en/agent-teams) (details via search summaries of that page and third-party guides)
- Claude Code "dynamic workflows" (blog June 2, 2026): Claude writes a JavaScript harness on the fly that spawns subagents with chosen models and isolation levels. Workflows can be saved and resumed across sessions, set explicit token budgets, and be shared via `~/.claude/workflows` or skills. Named patterns: fan-out-and-synthesize, adversarial verification, tournament (pairwise judging), classify-and-act, loop-until-done. The post's guidance: workflows "often use more tokens", so ask "does it really need more compute?"; parallelism must "earn [its] coordination cost" — [Claude blog](https://claude.com/blog/a-harness-for-every-task-dynamic-workflows-in-claude-code)

**Google Agent Development Kit (ADK)**
- ADK 2.0 GA: Python May 19, 2026, Go June 30, 2026, TypeScript August 21, 2026. The core change is from hierarchical agent execution to a graph workflow engine in which agents, tools and functions are nodes. New Event fields (`node_info`, `output`, `route`, `isolationScope`) track graph state. `RetryConfig` handles automatic retries. Human-in-the-loop pauses through a `RequestedInput` event field. Sessions are resumable and checkpointed. There is parallel fan-out, logging, metrics and traces, and A2A support — [ADK 2.0 docs](https://adk.dev/2.0/)
- Breaking changes: `SequentialAgent`, `ParallelAgent` and `LoopAgent` are deprecated ("should be expressed as graph workflows"). `BaseAgent` now extends `BaseNode`. Events must be yielded, not appended directly. Custom session stores need a schema migration — [ADK 2.0 docs](https://adk.dev/2.0/)
- Google calls the engine "a deterministic control layer around probabilistic language models", with human-in-the-loop as a built-in primitive and "dynamic orchestration written in plain Go" — [Google Developers Blog: ADK Go 2.0](https://developers.googleblog.com/announcing-adk-go-20/)

**AWS Strands Agents / Amazon Bedrock AgentCore**
- Strands' built-in multi-agent orchestrators are Graph and Swarm, plus Agents-as-Tools and Workflow patterns. Swarm means "self-organizing agent teams that collaborate through autonomous handoffs, shared context, and working memory", with no central orchestrator — [Strands docs: multi-agent patterns](https://strandsagents.com/docs/user-guide/concepts/multi-agent/multi-agent-patterns/); [Strands docs: swarm](https://strandsagents.com/docs/user-guide/concepts/multi-agent/swarm/)
- AgentCore Runtime is a serverless agent runtime with session isolation, identity, memory, observability, and long-running asynchronous tasks up to 8 hours. It can call tools over MCP, A2A or API Gateway — [AWS ML blog: Strands deep dive](https://aws.amazon.com/blogs/machine-learning/strands-agents-sdk-a-technical-deep-dive-into-agent-architectures-and-observability/) (the 8-hour figure came from a search summary and was not re-read on the page). AgentCore Runtime supports A2A — [Linux Foundation press](https://www.linuxfoundation.org/press/a2a-protocol-surpasses-150-organizations-lands-in-major-cloud-platforms-and-sees-enterprise-production-use-in-first-year)
- Diagrid's critique (vendor): Strands' per-message persistence restores conversation history but not execution state. A failed graph restarts from the beginning. Only `ModelThrottledException` retries automatically. `FileSessionManager` is not thread-safe — [Diagrid](https://www.diagrid.io/blog/still-not-durable-how-microsoft-agent-framework-and-strands-agents-repeat-the-same-mistake). An open GitHub issue asks for a multi-agent session manager for Graph and Swarm — [strands-agents issue #867](https://github.com/strands-agents/sdk-python/issues/867)

**CrewAI (Crews vs Flows)**
- Flows are the deterministic, event-driven layer that wraps autonomous Crews. `@persist()` saves Flow state to a database so a run can resume after a crash or while waiting for a human. `@human_feedback` pauses a flow for approval gates. Practitioner advice: put `@persist` on a terminal step rather than on the whole class, because class-level persist saves after every method and `load_state` may pick up a mid-run snapshot — [jahanzaib.ai production guide](https://www.jahanzaib.ai/blog/crewai-flows-production-multi-agent-guide) (third-party); see also [CrewAI production architecture docs](https://docs.crewai.com/en/concepts/production-architecture)

**Mastra (TypeScript)**
- Workflows can suspend at any step for human input, callbacks or throttling. Suspending writes a serializable snapshot (runId, input, step status, suspend and resume payloads, output) to storage, and `resume()` restarts from a step ID — [Mastra docs: snapshots](https://mastra.ai/docs/workflows/snapshots); [suspend and resume](https://mastra.ai/docs/workflows/suspend-and-resume)
- Agent networks pause and emit events when a tool, subagent or workflow needs approval, again using snapshots — [Mastra docs: network approval](https://mastra.ai/docs/v1/agents/network-approval). Open issues show suspend/resume does not work cleanly when agents call workflows, and approvals fail on large snapshots — [#11015](https://github.com/mastra-ai/mastra/issues/11015), [#11283](https://github.com/mastra-ai/mastra/issues/11283), [#22413](https://github.com/mastra-ai/mastra/issues/22413)

**Pydantic AI**
- Supports durable execution on seven engines: Temporal, DBOS, Prefect, Restate, AWS Lambda, Kitaru and Airflow, with human-in-the-loop approval built in — [Pydantic docs: durable execution](https://pydantic.dev/docs/ai/capabilities/durable_execution/overview/) (list via search summary). With Restate, "every LLM response is saved in the Restate Server and replayed during recovery" — [Pydantic article](https://pydantic.dev/articles/restate-durable-execution-pydanticai)
- An open issue proposes a first-class `RuntimeCapability` extension point for durable execution after v2 — [pydantic-ai #5477](https://github.com/pydantic/pydantic-ai/issues/5477)

**LlamaIndex Workflows**
- Event-driven: `@step` functions accept and emit typed Events. The `Context` can be serialized and checkpointed so a run resumes after a restart. Built-in `InputRequiredEvent` and `HumanResponseEvent` provide human-in-the-loop — [LlamaIndex Workflows docs](https://developers.llamaindex.ai/python/llamaagents/workflows/); [HITL](https://developers.llamaindex.ai/python/framework/understanding/agent/human_in_the_loop/)

**Durable-execution engines used under agents (Temporal, Restate, DBOS, Inngest, Dapr)**
- One survey lists Temporal, Restate, Inngest, Hatchet, DBOS, Cloudflare Workflows, AWS Lambda Durable Functions and Azure Durable Task as exposing durable primitives directly. Agent frameworks (LangGraph, OpenAI Agents SDK, AutoGen, CrewAI, Dapr Agents, Microsoft Agent Framework) are "adding persistence and checkpointing at the agent layer". Its summary of where the field is converging: "persist completed execution boundaries, then recover after crashes without repeating tool calls, external mutations, human approvals, or outbound messages" — [Zylos Research](https://zylos.ai/research/2026-04-24-durable-execution-agent-runtimes/) (third-party research blog)
- DBOS runs in-process and saves workflow state to Postgres. `@DBOS.workflow` and `@DBOS.step` decorators, plus a `DBOSAgent` wrapper, make a Pydantic AI agent durable with exactly-once execution — search summary of [Reactify Solutions](https://www.reactify-solutions.com/articles/durable-ai-agents-2026) and Pydantic docs (not re-verified)
- Restate "durable agents" pattern — [Restate docs](https://docs.restate.dev/ai/patterns/durable-agents)

**Dagger container-use (isolation primitive)**
- An MCP server and CLI that gives each coding agent its own container plus its own git branch (`container-use/<env_name>`), so "conflicts only surface when you merge". It works with Claude Code, Cursor and other MCP clients — [dagger/container-use README](https://github.com/dagger/container-use/blob/main/README.md); [Dagger blog](https://dagger.io/blog/agent-container-use/)

### Inferences
- Almost every framework now models human approval as a serializable pending-request object that can be resumed later: `RunState` interruptions (OpenAI), `RequestedInput` (ADK), pending requests/responses stored in the checkpoint (Microsoft), `@human_feedback` (CrewAI), `InputRequiredEvent` (LlamaIndex), suspend payloads (Mastra), `interrupt` (LangGraph). An in-process callback that blocks is no longer the norm. For Wanigan, an approval should be a durable database row with an ID, and should survive an app restart even though the PTY does not.
- The frameworks checkpoint the orchestration state, not the worker's process. That is exactly Wanigan's situation: a live CLI agent cannot be snapshotted. The workable equivalent is to persist the orchestration graph, pending approvals and results in SQLite, and rehydrate the workers through each CLI's own resume (`session_id` / `--resume`, ACP `session/load`), plus a workspace snapshot such as a git branch or worktree commit.
- Diagrid's checkpointing-versus-durable-execution distinction (vendor-motivated but technically sound) gives a useful rubric. A "true orchestration tool" needs failure detection (heartbeat or lease), automatic restart, and side-effect deduplication, not just snapshots. For a single-user desktop app a lease matters less, but "don't re-run a completed tool action or re-ask an answered approval after a crash" still applies.
- Isolation is converging on "one workspace per worker": OpenAI Manifest plus sandbox, container-use's container plus branch, AgentCore session isolation. Git worktrees are the local-first equivalent.

### Gaps
- The LangGraph API specifics I know from prior knowledge were not re-verified this session: durability modes `exit`/`async`/`sync`, `interrupt()`/`Command(resume=...)`, the `Send` map-reduce API, `RetryPolicy`, and `get_state_history`/fork for time travel. The fetched page did not include them.
- It is not confirmed whether AutoGen and Semantic Kernel are formally in maintenance mode. The Microsoft 1.0 post fetched here does not say so.
- CrewAI Flow decorators (`@start`, `@listen`, `@router`) and CrewAI adoption numbers were not verified. Neither were Inngest's AgentKit specifics or the Mastra 1.0 GA date.
- Pydantic AI's graph library (pydantic-graph) and its current parallel and fan-out support were not researched.
- Built-in timeout and budget primitives are poorly documented across frameworks. Only Claude dynamic workflows (token budgets) and ADK (`RetryConfig`) showed up explicitly. The per-framework `max_turns`/timeout options were not verified.

## Q2. Which primitives are converging into a de facto standard set, and which are differentiators?

### Takeaway
The de facto set: a run or thread identity; a graph or workflow with fan-out and fan-in; state checkpointed at step boundaries; interrupt and resume for human approval; handoff and agent-as-tool delegation; a task lifecycle state machine; per-worker workspace isolation; OpenTelemetry-style tracing; and MCP for tools. The differentiators are real durable execution (automatic recovery, exactly-once side effects), time travel and forking of checkpoints, sandbox provider breadth, built-in evals and verification loops, and cost budgets. Budgets remain the weakest-supported primitive, even though the evidence shows cost is the main multi-agent tax.

### Cited Findings
- Graph as the substrate: Microsoft Agent Framework puts all five orchestration patterns on a graph workflow engine — [Microsoft devblog](https://devblogs.microsoft.com/agent-framework/microsoft-agent-framework-version-1-0/). ADK 2.0 replaces Sequential, Parallel and Loop agents with graph workflows — [ADK 2.0](https://adk.dev/2.0/). Strands' built-in orchestrators are Graph and Swarm — [Strands](https://strandsagents.com/docs/user-guide/concepts/multi-agent/multi-agent-patterns/). LangChain's `create_agent` runs on the LangGraph runtime — [LangChain](https://www.langchain.com/blog/langchain-langgraph-1dot0)
- Common pattern vocabulary. Microsoft: sequential, concurrent, handoff, group chat, Magentic-One — [Microsoft devblog](https://devblogs.microsoft.com/agent-framework/microsoft-agent-framework-version-1-0/). Claude dynamic workflows: fan-out-and-synthesize, adversarial verification, tournament, classify-and-act, loop-until-done — [Claude blog](https://claude.com/blog/a-harness-for-every-task-dynamic-workflows-in-claude-code). OpenAI: handoffs versus agents-as-tools — [OpenAI sandbox guide](https://developers.openai.com/api/docs/guides/agents/sandboxes)
- Task lifecycle states converge across protocols. A2A 1.0: SUBMITTED, WORKING, INPUT_REQUIRED, AUTH_REQUIRED, COMPLETED, FAILED, CANCELED, REJECTED — [A2A spec](https://a2a-protocol.org/latest/specification/). MCP tasks: working ⇄ input_required → completed / failed / cancelled — [SEP-2663](https://modelcontextprotocol.io/seps/2663-tasks-extension)
- Observability is the most-adopted production primitive: 89% of respondents have agent observability versus 52% with evals. Among teams with agents in production, 94% have observability and 71.5% full tracing — [LangChain State of Agent Engineering](https://www.langchain.com/state-of-agent-engineering) (via [KDnuggets](https://www.kdnuggets.com/the-state-of-agent-engineering-report-overview) and search summaries). Microsoft Agent Framework uses OpenTelemetry — [Microsoft devblog](https://devblogs.microsoft.com/agent-framework/microsoft-agent-framework-version-1-0/). OpenAI tracing is built in — [OpenAI Agents SDK](https://openai.github.io/openai-agents-python/). ADK 2.0 ships traces and metrics — [ADK 2.0](https://adk.dev/2.0/)
- Durable execution as a differentiator: frameworks conflate checkpointing with durable execution ("automatic failure detection, restart from the exact failure point, duplicate prevention, and recovery orchestration") — [Diagrid](https://www.diagrid.io/blog/still-not-durable-how-microsoft-agent-framework-and-strands-agents-repeat-the-same-mistake) (vendor). Durability is often bolted on through Temporal (OpenAI SDK GA March 2026, LangGraph plugin) or Pydantic AI's seven-engine support — [Temporal](https://temporal.io/blog/announcing-openai-agents-sdk-integration); [Temporal LangGraph plugin](https://temporal.io/blog/temporal-langgraph-plugin-durable-execution); [Pydantic](https://pydantic.dev/docs/ai/capabilities/durable_execution/overview/)
- Time travel is a LangGraph-listed checkpointer use case — [LangGraph docs](https://docs.langchain.com/oss/python/langgraph/durable-execution). Session fork appears in the Claude Agent SDK ("resume or fork later") — [Claude Agent SDK](https://code.claude.com/docs/en/agent-sdk/overview)
- Budgets: Claude dynamic workflows let a user set explicit token budgets — [Claude blog](https://claude.com/blog/a-harness-for-every-task-dynamic-workflows-in-claude-code). Temporal-wrapped agents handle rate limits by waiting — [Temporal](https://temporal.io/blog/announcing-openai-agents-sdk-integration)
- Memory as a primitive: OpenAI sandbox memory consolidates into `MEMORY.md` — [OpenAI sandbox guide](https://developers.openai.com/api/docs/guides/agents/sandboxes). CrewAI has a persistent memory layer that "strategically forget[s]" — search summary of [CrewAI docs](https://docs.crewai.com/llms-full.txt)

### Inferences
- A "true orchestration tool" for CLI coding agents should expose, as first-class and persisted objects: (1) a Run or Task with an A2A/MCP-compatible lifecycle (submitted, working, input-required, completed, failed, canceled); (2) a DAG or plan with fan-out and fan-in edges between tasks; (3) durable approvals and interrupts; (4) a workspace per task (worktree or branch); (5) a trace of spans per task linked to the evidence; (6) a budget per run (tokens, dollars, wall-clock) enforced before fan-out; (7) a verification node type (review, tests, evaluator), because the evidence in Q5 says verification is where the gains come from.
- Taking the A2A task states wholesale for Wanigan's session and task model would line it up with both A2A and MCP tasks at almost no cost, and would make a later protocol bridge simple.
- Wanigan's existing premises map directly onto primitives the frameworks now sell: recorded evidence in SQLite is the checkpoint store and trace; the review gate is the verification and approval node; metering is the budget. The missing pieces are the graph or plan layer and parallel fan-out with join semantics.

### Gaps
- There is no cross-framework standard for trace schemas beyond OpenTelemetry. Whether OTel GenAI semantic conventions are stable as of September 2026 was not researched.
- No framework-neutral eval primitive was found. Evals remain platform features (LangSmith, OpenAI evals) rather than orchestration primitives.

## Q3. Protocols: A2A, ACP (Zed's Agent Client Protocol and IBM's Agent Communication Protocol), MCP tasks and elicitation, AG-UI, and which coding-agent CLIs implement them

### Takeaway
For driving heterogeneous coding agents from a desktop app, the relevant standard is Zed's Agent Client Protocol (ACP). It is JSON-RPC 2.0 to an agent subprocess, with sessions, prompts, streamed updates (message chunks, tool calls, plans), permission requests, fs/terminal callbacks and cancel. Its registry lists about 50 agents. Gemini CLI, Goose, GitHub Copilot, Cursor, Cline, OpenCode, OpenHands, Kiro, Junie and others implement it natively. Claude Code (via `claude-agent-acp`) and Codex CLI (via `codex-acp`) need adapters, and Codex's own native protocol is its JSON-RPC app-server. A2A 1.0 (April 2026) is for remote agent-to-agent delegation, not local CLI control. IBM's Agent Communication Protocol merged into A2A in August 2025. MCP 2026-07-28 went stateless and moved Tasks into an official extension. AG-UI standardizes the agent-to-frontend event stream.

### Cited Findings

**Agent Client Protocol (Zed; agentclientprotocol.com)**
- JSON-RPC 2.0 with methods and notifications. The client sends `initialize` (version and capability negotiation), then `authenticate` if needed. Agent-side methods: `session/new`, `session/prompt`; optional `session/load` (needs the `loadSession` capability), `session/set_mode`, `logout`; notification `session/cancel`. Client-side methods: `session/request_permission` (baseline), optional `fs/read_text_file`, `fs/write_text_file`, `terminal/create|output|release|wait_for_exit|kill`, and `elicitation/create`. The agent streams `session/update` with message chunks (agent, user, thought), tool calls and updates, plans, available-command updates and mode changes. "All file paths in the protocol MUST be absolute" — [ACP protocol overview](https://agentclientprotocol.com/protocol/overview)
- Native agents listed by ACP include AgentPool, Augment Code, Blackbox AI, Cline, Cursor, Docker's cagent, fast-agent, Factory Droid, Gemini CLI, GitHub Copilot, Goose, Hermes Agent, Junie (JetBrains), Kimi CLI, Kiro CLI, Mistral Vibe, OpenClaw, OpenCode, OpenHands, Poolside, Qoder CLI, Qwen Code, VT Code and others. Via adapter: Claude Agent (Zed's SDK adapter), Codex CLI (ACP's adapter), Pi (pi-acp) — [ACP agents page](https://agentclientprotocol.com/get-started/agents)
- The Claude adapter is `agentclientprotocol/claude-agent-acp`, "Use Claude Agent SDK from any ACP client" — [GitHub](https://github.com/agentclientprotocol/claude-agent-acp)
- The ACP Registry launched in January 2026 and lists about 50 agents. It has been live in JetBrains IDEs and Zed since January 2026. Remote transports are "on the roadmap to push ACP beyond the local subprocess model" — [Marc Nuri](https://blog.marcnuri.com/agent-client-protocol-acp-introduction); [danilchenko.dev](https://www.danilchenko.dev/posts/agent-client-protocol/) (third-party). Editors as of June 2026: Zed and JetBrains (native), Neovim and Emacs (community plugins) — [danilchenko.dev](https://www.danilchenko.dev/posts/agent-client-protocol/). JetBrains published an ACP how-to in August 2026 — [JetBrains blog](https://blog.jetbrains.com/idea/2026/08/how-to-use-ai-agents-in-intellij-idea-with-acp/). A community VS Code ACP client exists — [formulahendry/vscode-acp](https://github.com/formulahendry/vscode-acp)
- Zed documents ACP agents as "External Agents" — [Zed docs](https://zed.dev/docs/ai/external-agents)

**Codex app-server (OpenAI's native control protocol)**
- JSON-RPC 2.0 "lite" (the `"jsonrpc"` field is omitted) over newline-delimited stdio. Lifecycle: `initialize` → `thread/start` → `turn/start` → streamed notifications (`item/started`, `item/completed`, `item/agentMessage/delta`, …) → `turn/completed`. Approvals are server-initiated requests. Command decisions: `accept`, `acceptForSession`, `decline`, `cancel`, or `acceptWithExecpolicyAmendment`. File-change decisions: `accept`, `acceptForSession`, `decline`, `cancel` — [Codex App Server docs](https://developers.openai.com/codex/app-server); [OpenAI: Unlocking the Codex harness](https://openai.com/index/unlocking-the-codex-harness/) (details via search summaries)

**Claude Code**
- Native programmatic surfaces: the Claude Agent SDK (Python/TS) and the CLI subprocess with `-p --output-format json` — [Claude Agent SDK overview](https://code.claude.com/docs/en/agent-sdk/overview). ACP only through the adapter above. No evidence that Claude Code speaks A2A natively.

**Gemini CLI**
- Native ACP — [ACP agents page](https://agentclientprotocol.com/get-started/agents). It supports remote subagents over A2A (a `RemoteAgentInvocation` tool type; remote agents are defined with `kind = "remote"`) and is enabled by default — [Gemini CLI docs: remote subagents](https://geminicli.com/docs/core/remote-agents/); [PR #16013](https://github.com/google-gemini/gemini-cli/pull/16013). The `@google/gemini-cli-a2a-server` package exposes Gemini CLI as an A2A server — [npm](https://www.npmjs.com/package/@google/gemini-cli-a2a-server)

**A2A (Agent2Agent, Linux Foundation)**
- v1.0, the first stable spec, was released April 9, 2026. It added multi-protocol support, multi-tenancy, modernized security flows, Signed Agent Cards, and a migration path. At the one-year mark, 150+ organizations support it; Microsoft integrated it into Azure AI Foundry and Copilot Studio, and AWS into Bedrock AgentCore Runtime — [Linux Foundation press](https://www.linuxfoundation.org/press/a2a-protocol-surpasses-150-organizations-lands-in-major-cloud-platforms-and-sees-enterprise-production-use-in-first-year); [Google Open Source Blog](https://opensource.googleblog.com/2026/04/a-year-of-open-collaboration-celebrating-the-anniversary-of-a2a.html)
- Spec 1.0.0 concepts. Agent Card: JSON metadata with endpoint, auth schemes (API key, OAuth2, mTLS…), capabilities (streaming, push, extended card), skills, extensions; it can be signed. Task lifecycle: the eight states listed in Q2. Message/Part/Artifact data model; `contextId` groups related interactions. Operations: SendMessage, SendStreamingMessage, GetTask, ListTasks, CancelTask, SubscribeToTask, push-notification config (webhooks). Bindings: JSON-RPC 2.0, gRPC, HTTP+JSON/REST. Optional `tenant` field — [A2A specification](https://a2a-protocol.org/latest/specification/)
- IBM's Agent Communication Protocol (launched March 2025 for BeeAI) merged into A2A under the LF in August 2025 and "is no longer evolving as a separate protocol". BeeAI now uses A2A (`A2AServer`, `A2AAgent` adapters) — [LF AI & Data](https://lfaidata.foundation/communityblog/2025/08/29/acp-joins-forces-with-a2a-under-the-linux-foundations-lf-ai-data/); [i-am-bee discussion](https://github.com/orgs/i-am-bee/discussions/5)

**MCP (Model Context Protocol)**
- The 2026-07-28 spec is final (published July 28, 2026 after a ten-week release-candidate window). The core is stateless: no `initialize` handshake, no `Mcp-Session-Id`. Each request carries protocol version, client identity and capabilities in `_meta` (SEP-2575, SEP-2567). `Mcp-Method` and `Mcp-Name` headers allow gateway routing (SEP-2243). List results are cacheable with `ttlMs`/`cacheScope` (SEP-2549) — [MCP blog: 2026-07-28](https://blog.modelcontextprotocol.io/posts/2026-07-28/)
- Multi Round-Trip Requests (SEP-2322) replace server-initiated requests. A tool needing mid-call input returns `resultType: "input_required"` with its questions, and the client retries the original call with `inputResponses`. This is how elicitation now works on stateless servers — [MCP blog](https://blog.modelcontextprotocol.io/posts/2026-07-28/)
- Tasks: experimental in core in 2025-11-25, now the official extension `io.modelcontextprotocol/tasks` (SEP-2663). A server may answer `tools/call` with a task handle (`resultType: "task"`); whether to create a task is the server's decision per request. Methods: `tasks/get` (idempotent, cacheable), `tasks/update`, `tasks/cancel` (cooperative; the task "may still reach a non-cancelled terminal status"). States: working ⇄ input_required → completed / failed / cancelled. Notifications arrive via an opt-in `tasks/subscriptions/listen` stream — [SEP-2663](https://modelcontextprotocol.io/seps/2663-tasks-extension); [MCP blog](https://blog.modelcontextprotocol.io/posts/2026-07-28/)
- Deprecated (removal no sooner than twelve months): Roots, Sampling, Logging (SEP-2577), the legacy HTTP+SSE transport, and Dynamic Client Registration (replaced by Client ID Metadata Documents). Auth hardening: RFC 9207 `iss` validation (SEP-2468), issuer-bound credentials (SEP-2352), `application_type` in DCR to fix localhost redirects for desktop and CLI apps (SEP-837). Official extensions: Tasks, MCP Apps, Enterprise Managed Authorization. TS, Python, Go and C# SDKs support it; Rust is in beta — [MCP blog](https://blog.modelcontextprotocol.io/posts/2026-07-28/)
- MCP defines no agent-to-agent capability in this release — [MCP blog](https://blog.modelcontextprotocol.io/posts/2026-07-28/). MCP material is also published by the Agentic AI Foundation — [AAIF blog](https://aaif.io/blog/mcp-2026-07-28-whats-changing-and-how-to-migrate)

**AG-UI (Agent–User Interaction protocol, CopilotKit)**
- An event-streaming protocol of about 16 standard event types over SSE, WebSockets or webhooks. It covers streaming chat, bidirectional state sync, generative UI, frontend tool calls and human-in-the-loop. First-party integrations exist in Microsoft Agent Framework, Google ADK, AWS Strands and AgentCore. Adopters include Oracle, LangChain, Mastra and Agno. About 14.2K GitHub stars — search summaries of [CopilotKit blog](https://www.copilotkit.ai/blog/big-updates-on-ag-ui) and [Ry Walker research](https://rywalker.com/research/ag-ui) (vendor and third-party)
- CopilotKit raised a $27M Series A in May 2026 — [TechCrunch](https://techcrunch.com/2026/05/05/copilotkit-raises-27m-to-help-devs-deploy-app-native-ai-agents/)

### Inferences
- The protocols form a stack. MCP connects an agent to its tools. ACP connects a client (editor or control surface) to a local coding agent. A2A connects an agent to a remote agent. AG-UI connects an agent to a web frontend. For Wanigan, ACP matches the job most closely: it is literally "drive a coding agent subprocess from a UI", with typed permission requests, tool-call and diff updates, plans, terminals and cancel. Those are what Wanigan otherwise has to infer from a PTY.
- A realistic Wanigan design keeps the PTY as the universal fallback and adds structured drivers per harness: ACP for the long tail of native agents (Gemini CLI, Goose, Copilot, Cursor, OpenCode, etc.), Codex app-server for Codex, and the Claude CLI's stream-json or the Agent SDK for Claude. The Claude ACP adapter wraps the Agent SDK. Anthropic says third parties may not offer claude.ai login or rate limits for Agent SDK products "unless previously approved", so driving Claude through the adapter may push users onto API-key billing. Wanigan's current approach of launching the real CLI avoids this, and the question should be checked before any change.
- This fits Wanigan's rule that capabilities must be verified per provider: ACP makes `session/load`, terminals, fs and modes optional capabilities negotiated at `initialize`. A capability probe against the ACP `initialize` response is a natural, honest way to fill a provider pack's capability declaration.
- Mapping ACP `session/request_permission` and Codex approval requests onto one durable Wanigan approval object (see Q1) would give one review inbox across harnesses.
- A2A matters to Wanigan only if it wants to expose its own orchestrated runs as a remote agent, or to consume remote agents (as Gemini CLI now does). The A2A task state machine is still worth adopting as the internal vocabulary.
- MCP's move to a stateless core and its deprecation of Sampling and Roots affect any MCP server Wanigan hosts or injects. Elicitation now works by MRTR retry rather than server push, and Wanigan's MCP store should expect servers on the 2026-07-28 revision.

### Gaps
- Not verified: whether Goose, Cursor and Copilot CLI implement the full ACP surface (terminals, `session/load`) or subsets. A per-agent capability matrix was not found.
- Whether the ACP remote transport has shipped by September 2026 is not confirmed; the sources say "on the roadmap".
- Not researched: whether Codex CLI or Claude Code expose A2A servers, or Codex's `mcp-server` mode.
- How `claude-agent-acp` authenticates (API key versus subscription) was not verified. It matters because of the Agent SDK licensing note.
- AG-UI numbers come from vendor and third-party pages and were not checked against GitHub.

## Q4. Adoption signals and developer sentiment

### Takeaway
LangGraph/LangSmith has the strongest production adoption evidence: named enterprises and about 90M monthly downloads for LangChain and LangGraph (vendor-reported). The cloud vendors' frameworks (Microsoft Agent Framework 1.0, ADK 2.0, Strands/AgentCore) reached stable releases in the first half of 2026 and are integrated into their clouds. Sentiment has moved from "multi-agent everything" to skepticism: quality and reliability, not cost, is the top production blocker; observability is nearly universal while evals lag; and the most-cited practitioner advice is to keep writes single-threaded.

### Cited Findings
- LangChain's State of Agent Engineering (1,300+ practitioners, surveyed November–December 2025): 57.3% have agents in production and 30.4% are developing with plans to deploy (up from 51% in production the year before). About 89% have observability versus 52% with evals. Among production teams, 94% have observability and 71.5% full tracing. Quality (hallucinations, evaluation gaps, a "delegation trust deficit") is the main barrier, and using several models is the norm — [LangChain report](https://www.langchain.com/state-of-agent-engineering); [KDnuggets](https://www.kdnuggets.com/the-state-of-agent-engineering-report-overview); [NoCode.Tech](https://www.nocode.tech/article/langchain-report-quality-not-cost-killing-ai-agents) (vendor survey, likely skewed toward LangChain users)
- LangGraph production users: Uber, LinkedIn, Klarna, JP Morgan, BlackRock, Cisco, Rippling; 90M monthly downloads — [LangChain](https://www.langchain.com/blog/langchain-langgraph-1dot0)
- A2A: 150+ organizations and production deployments across industries at one year — [Linux Foundation](https://www.linuxfoundation.org/press/a2a-protocol-surpasses-150-organizations-lands-in-major-cloud-platforms-and-sees-enterprise-production-use-in-first-year)
- Cognition, "Don't Build Multi-Agents" (June 12, 2025): "Share context, and share full agent traces, not just individual messages"; "Actions carry implicit decisions, and conflicting decisions carry bad results". It criticizes OpenAI Swarm and AutoGen for pushing "the wrong way of building agents" and recommends a single-threaded linear agent, with an LLM that compresses history for very long tasks — [Cognition](https://cognition.com/blog/dont-build-multi-agents)
- Cognition's follow-up, "Multi-Agents: What's Actually Working" (April 22, 2026): multi-agent setups work where "multiple agents contribute intelligence to a task while writes stay single-threaded", while "parallel-writer swarms still don't see meaningful adoption". Devin Review catches an average of 2 bugs per PR even on Devin-written PRs, about 58% of them severe, and Devin and Devin Review now iterate against each other — [Cognition](https://cognition.com/blog/multi-agents-working) (details via search summary)
- The durability critique of Microsoft Agent Framework, Strands, LangGraph, CrewAI and ADK (vendor-motivated) — [Diagrid](https://www.diagrid.io/blog/still-not-durable-how-microsoft-agent-framework-and-strands-agents-repeat-the-same-mistake)
- Open issues show state and resume edge cases in younger frameworks: Mastra suspend/resume through agents, and large-snapshot approvals failing against a 2-second validator deadline — [Mastra #22413](https://github.com/mastra-ai/mastra/issues/22413); Strands multi-agent session manager missing — [#867](https://github.com/strands-agents/sdk-python/issues/867)
- One third-party claim is that AWS Strands replaced "40 lines of LangGraph with 3". It is often read as a sign of fatigue with graph boilerplate — [DEV Community](https://dev.to/aws-builders/aws-strands-replaced-60-lines-of-langgraph-with-3-heres-the-full-story-2ok0) (anecdotal; the title itself is inconsistent at 40 versus 60)

### Inferences
- The market is treating observability plus approvals as table stakes, and quality and verification as the unsolved problem. That favours Wanigan's evidence-first positioning over a "spawn more agents" pitch.
- The frameworks' biggest weakness from a coding-agent point of view is that they orchestrate model calls, not existing CLI agents. They would have to wrap Claude Code or Codex as tools or subprocesses. That leaves room for a control plane that orchestrates the real CLIs (Wanigan) and borrows the frameworks' primitives rather than their runtimes.

## Q5. Published evidence on multi-agent patterns: when they beat a single agent, token-cost multipliers, failure modes

### Takeaway
Multi-agent helps on broad, decomposable, read-heavy work: Anthropic reports +90.2% on research, and Google's scaling study found +80.8% on decomposable financial reasoning. It hurts on sequential or tool-heavy work: −70% on sequential planning in the same study. Most coding tasks are the latter. Cost is about 15× chat tokens for multi-agent versus about 4× for a single agent. Failures are mostly organizational (specification and system design, inter-agent misalignment, weak verification), not model capability. Centralized verification sharply limits error amplification: 4.4× versus 17.2× for independent parallel agents. The best-supported pattern for coding is an orchestrator with read-only parallel helpers, one writer, and an explicit verifier or evaluator loop.

### Cited Findings
- Anthropic's multi-agent research system (June 13, 2025): an orchestrator-worker setup (Opus 4 lead, Sonnet 4 subagents) beat single-agent Opus 4 by 90.2% on internal research evals. Agents use about 4× the tokens of chat, and multi-agent systems about 15×. Token usage alone explains 80% of performance variance in browsing tasks. "Most coding tasks involve fewer truly parallelizable tasks than research", and domains needing shared context or heavy interdependence are poorly suited. Production lessons: durable execution with checkpoint recovery rather than restarts, tracing without reading conversation content, rainbow deployments so updates do not break running agents, and synchronous subagent execution as a bottleneck — [Anthropic Engineering](https://www.anthropic.com/engineering/multi-agent-research-system)
- Google and MIT, "Towards a Science of Scaling Agent Systems" (arXiv 2512.08296, December 2025): relative change versus a single agent ranges from +80.8% (decomposable financial reasoning) to −70.0% (sequential planning). There is a capability-saturation effect: coordination returns diminish once the single-agent baseline is strong. Tool-heavy tasks carry multi-agent overhead. Independent multi-agent systems amplified errors 17.2×, versus 4.4× for centralized (orchestrated) ones. The study reportedly covered 260 configurations across 6 benchmarks, 5 architectures (single, independent, centralized, decentralized, hybrid) and 3 LLM families — [arXiv](https://arxiv.org/abs/2512.08296); [Google Research blog](https://research.google/blog/towards-a-science-of-scaling-agent-systems-when-and-why-agent-systems-work/) (figures via search summary; the configuration count was not checked against the PDF)
- MAST, "Why Do Multi-Agent LLM Systems Fail?" (Cemri, Pan, Yang et al., UC Berkeley; NeurIPS 2025): 14 failure modes in 3 categories, built by Grounded Theory from 150+ traces (κ = 0.88). MAST-Data holds 1,642 annotated traces from 7 MAS frameworks, and SOTA open-source MAS show 41%–86.7% failure rates. Prevalence from Figure 1 across the 1,642 traces:
  - **System design issues (44.2%)**: disobey task specification 11.8%, disobey role specification 1.5%, step repetition 15.7%, loss of conversation history 2.8%, unaware of termination conditions 12.4%.
  - **Inter-agent misalignment (32.3%)**: conversation reset 2.2%, fail to ask for clarification 6.8%, task derailment 7.4%, information withholding 0.85%, ignored other agent's input 1.9%, reasoning-action mismatch 13.2%.
  - **Task verification (23.5%)**: premature termination 6.2%, no or incomplete verification 8.2%, incorrect verification 9.1%.
  - The paper also shows a 210-trace subset split 41.8% / 36.9% / 21.3%.
  - Interventions: better role specification or workflow gave +9.4% on ChatDev, and a high-level objective verification step gave +15.6% on ProgramDev. "Improvements in the base model capabilities will be insufficient", and good MAS design "requires organizational understanding" — [arXiv 2503.13657](https://arxiv.org/abs/2503.13657) (numbers read from the PDF text)
  - Note: a secondary blog ([Medium/Grigoryan](https://thegrigorian.medium.com/why-do-multi-agent-llm-systems-fail-14dc34e0f3cb) and search summaries) quotes different percentages, such as step repetition 17.14% and categories 41.77/36.94/21.30. Use the PDF figures above. An earlier arXiv version had 37.17/31.41/31.41.
- Cognition's production experience: single-threaded writes, with multi-agent limited to contributing intelligence such as review. A review agent iterating with the coding agent catches about 2 bugs per PR, about 58% severe — [Cognition 2026](https://cognition.com/blog/multi-agents-working); [Cognition 2025](https://cognition.com/blog/dont-build-multi-agents)
- Claude Code's own guidance for multi-subagent workflows: best for "complex, high value tasks" and not routine coding. Adversarial verification and tournament judging are first-class patterns, and token budgets can be set explicitly — [Claude blog](https://claude.com/blog/a-harness-for-every-task-dynamic-workflows-in-claude-code)
- Anthropic's earlier "Building effective agents" (December 2024) sets out the canonical workflow patterns: prompt chaining, routing, parallelization (sectioning and voting), orchestrator-workers, and evaluator-optimizer. It advises starting with the simplest workable solution — [Anthropic](https://www.anthropic.com/engineering/building-effective-agents) (content from prior knowledge, not re-fetched this session)
- Newer 2026 arXiv work on silent failures in production agent runtimes: "When Errors Become Narratives: A Longitudinal Taxonomy of Silent Failures in a Production LLM Agent Runtime" — [arXiv 2606.14589](https://arxiv.org/pdf/2606.14589); "Silent Failure in LLM Agent Systems: The Entropy Principle…" — [arXiv 2606.08162](https://arxiv.org/pdf/2606.08162) (titles only; not read)

### Inferences
- For Wanigan the evidence supports three defaults:
  - **Fan out reads, not writes.** Parallel research, review and exploration agents are fine. Parallel writers need isolated worktrees and a single merge decision.
  - **Always attach a verifier.** MAST's largest single intervention gain was a verification step (+15.6%), and centralized verification cut error amplification by about 4×. Wanigan's review gate is the right primitive, and an evaluator-optimizer loop (worker → tests or review → worker) should be a built-in node type.
  - **Make cost visible before fan-out.** About 15× tokens for multi-agent justifies Wanigan's rule against silently spending tokens or fanning out work. A budget and estimate should gate any parallel launch.
- The MAST failure modes map onto features a control surface can detect from recorded evidence:
  - step repetition (15.7%): loop and duplicate-action detection;
  - unaware of termination (12.4%): stop conditions, `/goal`-style completion criteria;
  - reasoning-action mismatch (13.2%): diff-versus-plan review;
  - no or incorrect verification (17.3% combined): mandatory test and review gates;
  - fail to ask for clarification (6.8%): prompting the agent to raise input-required.
- The capability-saturation finding means that as models improve, the payoff from multi-agent orchestration for coding shrinks, while the payoff from verification, isolation and cost control stays. An orchestration tool should not assume more agents means better results.

### Gaps
- No controlled study was found that measures evaluator-optimizer versus single-agent on coding benchmarks (for example SWE-bench) with token costs. The Anthropic 90.2% result is for research tasks, not coding.
- The Google scaling paper's per-benchmark coding results (if any) and exact token multipliers per architecture were not extracted.
- The two June 2026 arXiv papers on silent failures were not read. They may contain production failure data relevant to long-running coding agents.
