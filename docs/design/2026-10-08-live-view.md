# Live view

The owner's real local site, inside Wanigan, changing as the agents change it.
Drupal and WordPress first; anything with a URL works as a plain live view.

Decided with the owner on 8 October 2026:

| Question | Answer |
|---|---|
| What it shows | Both: the real page, and "this piece alone" when an edit maps to a piece |
| Content for a piece | Real content from the local site when an instance exists; labelled sample content when none does |
| How a piece is rendered | A small dev-only helper the owner installs with one click, kept out of git |
| Cards in their own worktree | "Serve this card": the site is switched to serve that card's checkout, on a click |
| Edit → piece | The site marks what produced each region; clicking a region says what produced it |
| Optional | Off until switched on, from the project's Live tab (always shown) or Settings › Live view; screenshots are a second switch |
| Before and after | Screenshots of the card's page, before its session works and after each turn, on the card |

## Where it stands (9 October 2026)

Built and verified by hand on the owner's own local Drupal 11 and WordPress
sites, the real app driven step by step with whole-window screenshots:
finding the site, following edits, layers named from Twig debug and the
helpers' marks, a part's details with overrides and admin links, notes sent to
an agent as one message, words saved to a template (with revert) or a plain
text field, styles tried on the page and sent as intent, device widths, page
problems, both helpers, pieces alone, content changes followed, and a card's
before and after with what changed boxed.

Not built: Serve this card; a component's props form (a theme with its own prop
types needs its resolved schema, not the `.component.yml` on disk); saving
WordPress content by hand; Layout Builder components and Canvas instances by
their own ids; axe-core per turn; a crash-safe CDP session (screenshots grow a
hidden window instead of using the debugger).

The research behind the next steps is the report "Visual editing and design
import tools" (9 October 2026), kept with the owner's notes outside the
repository.

## What already exists

- Every agent edit arrives as a hook. Claude Code, Gemini and Grok name the file;
  Codex's `apply_patch` sends the patch, which names every file (`src/shared/edits.ts`).
  `session_edits` keeps one row per file.
- The core runs CLIs as the owner (MCP adds, git), shows the exact command first,
  and writes into a project only on an explicit click that says what it writes.
- The main process owns windows; the renderer reaches it only through the preload
  bridge, and `trusted()` refuses any other page.

## Pieces

### Settings (main process)

`AppSettings` gains `liveView: boolean` and `liveShots: boolean`, both false. With
`liveView` off the Live tab, the session split and the card section are absent,
and the main process creates no view. The core keeps project configuration
regardless (it costs nothing and is only read when asked).

### Core: `src/core/live/`

- Table `live_sites` (additive migration): `project_id` (PK), `url`, `platform`
  (`drupal` | `wordpress` | `site`), `served_path` (the checkout the local site
  serves; null is the project folder), `helper` (installed helper version or null),
  `token` (what the helper accepts from Wanigan's view), `updated_at`.
- Table `live_shots`: `id`, `card_id`, `session_id`, `kind` (`before` | `after`),
  `url`, `file` (a PNG in the data folder), `width`, `height`, `created_at`.
  Table `live_pages`: the page each card watches (`card_id` PK, `url`, `set_by`).
- Detection, read-only: `.ddev/config.yaml` (name, type, docroot, extra hostnames)
  gives `https://<name>.ddev.site` and the platform; `wp-config.php` (`WP_HOME`),
  Drupal's `core/lib/Drupal.php`, `package.json` dev scripts and `.lando.yml`
  fill the rest. The owner can always type the address.
- Methods (owner only): `live.get`, `live.set`, `live.helper` (preview and install,
  like `mcp.add`), `live.removeHelper`, `live.clearCaches`, `live.devSettings`
  (Drupal), `live.serve` (Serve this card), `live.shots`, `live.shot`,
  `live.saveShot`, `live.setPage`. Sessions get `live.setPage` for their own card
  (`wanigan live page <url>`), so an agent can say which page it is changing.
- Events: `live` `{ projectId, sessionId, cardId, paths, kind }` where kind is
  `edit` (paths named), `turn-start` or `turn-end`.

### Helpers (written into the site on a click)

Both are shipped inside the app as text, carry a token the core generates, and
are listed in the repository's `.git/info/exclude` (never `.gitignore`), so they
can never be committed. Removing one undoes all of it.

- **Drupal** — module `wanigan_live` in `<docroot>/modules/custom/`, enabled with
  `drush pm:install`. It adds `data-wl-entity` (type:bundle:id:view mode),
  `data-wl-block` and `data-wl-view` attributes; Twig's own debug comments give
  the template file. Routes under `/_wanigan/` render one entity, sample entity
  (`createWithSampleValues`, labelled), block, view or component alone, as a bare
  page in the front-end theme, only with the token. Response headers say whether
  Twig debug and render caching are on, so the view can say when an edit may not
  show yet. `live.devSettings` turns on Drupal's development settings.
- **WordPress** — must-use plugin `wp-content/mu-plugins/wanigan-live.php`. Template
  files are bracketed with comments through `wp_before_load_template` /
  `wp_after_load_template`; blocks get `data-wl-block` through `render_block` and
  `WP_HTML_Tag_Processor`; Elementor's own `data-element_type` / `data-widget_type`
  are read as they are. `?wanigan_piece=` renders a block from a post, a template
  part, a pattern, a block's own `example` (labelled) or an Elementor element alone,
  with `wp_head()` and `wp_footer()` so its styles load.

### Pieces, per kind, and seeing them as they are built

Agents change two kinds of things, and each has its own signal:

- **Code** (templates, CSS, preprocess hooks, a block's `render.php`, theme PHP):
  every edit is a `live` event naming the file. The view reloads (or swaps the
  stylesheet), then outlines the regions that file produced.
- **Content and configuration** (a paragraph created with drush, a Layout Builder
  section saved, Elementor data written with WP-CLI): no file changes. While a
  session's turn is running, the view asks the helper every two seconds for one
  number that moves when anything is saved: the sum of Drupal's cache-tag
  invalidations, or WordPress's latest `post_modified_gmt`. When it moves, the
  view reloads.

Each region the helper can render alone carries `data-wl-piece`, an address only
the helper interprets; Wanigan opens `/_wanigan/piece/<address>` (Drupal) or
`?wanigan_piece=<address>` (WordPress) with its token.

| Kind | How a region is known | Alone, real content | Alone, sample (labelled) |
|---|---|---|---|
| Drupal paragraph | `data-wl-entity="paragraph:hero:12:default"`, Twig debug for the template | `entity/paragraph/12/default`, access checked through its parent | `sample/paragraph/hero/default` via `createWithSampleValues()` |
| Drupal SDC | core's own `data-component-id` | the entity or block that renders it (its props are computed there) | `component/theme:card` with the props' `examples` from `.component.yml` |
| Layout Builder | each section's layout template (Twig debug); each block `data-wl-block` plus its component UUID | `lb/node/5/<uuid>` — that component from the override or default display — or a whole section | — |
| Drupal block, view | `data-wl-block` (plugin and config id), `data-wl-view` | `block/<id>`, `view/<id>/<display>` | — |
| Gutenberg block | `data-wl-block="core/cover"` and its path in the post, via `render_block` | `block/<post>/<path>` from the post's own content | the block type's `example` |
| Block theme parts, patterns | they are blocks (`core/template-part`, `core/pattern`) | `part/<slug>`, `pattern/<name>` | — |
| Classic theme (Astra) | template files bracketed through `wp_before_load_template` / `wp_after_load_template` | `template/<file>` (that part, with `wp_head()` and `wp_footer()`) | — |
| Elementor | its own `data-id`, `data-element_type`, `data-widget_type` | `elementor/<post>/<element id>` through Elementor's elements manager, with that post's CSS | — |

Other builders (Divi, Beaver Builder, WPBakery) get the live page and template
outlines; their own markup can be read later the way Elementor's is.

### Editing by hand

The owner asked for real-time hand edits alongside the agents'. Cursor's Design
Mode (Builder.io's write-up, 19 Dec 2025) shows the shape and its failure:
visual tweaks preview instantly and stay temporary until Apply, then the agent
searches the repository and writes code; it guesses where a change belongs, so it
hard-codes values or duplicates components ("design drift"), selects DOM nodes
not components, and has no real undo. Wanigan's mapping is deterministic instead
(a component's folder from `data-component-id`, a template from Twig debug, an
entity and field from the helper), so:

- **Select components**, not DOM nodes; shift-click adds; a group (24 product
  teasers) is one selection.
- **Preview first, write on Save.** Text edited in place and style changes from a
  small panel apply to the page at once and touch nothing on disk.
- **Two ways out:** Save writes where the change belongs (a Drupal or WordPress
  field through the helper, as a revision; a component's CSS or Twig after
  showing the diff), using the theme's own tokens where they exist; or Ask the
  agent, which hands it the exact change, file and tokens, so it guesses nothing.
- **A history with Revert** for every hand edit; content edits keep their CMS
  revision too.
- **Props** of a component edit through a form built from its `.component.yml`,
  and the component re-renders alone as they change.

### Main process: `src/main/live-view.ts`

- One `WebContentsView` laid over a placeholder the renderer positions. Its own
  session partition per project (`persist:wanigan-live:<id>`), so logins stay.
  Sandboxed, context-isolated, no Node, a preload that only reads the page
  (regions, picks, stylesheet swaps) and reports to the main process, which checks
  the sender is that view.
- Navigation stays on the site's own host (http and https); anything else opens in
  the default browser. No new windows, downloads or permissions. The helper token is
  added as a request header to the site's own host only.
- A dialog, the palette or the chat covering the view hides it and shows its last
  frame instead, since a native view draws above the page.
- Reload: an edit inside the served checkout reloads after 400 ms of quiet; a
  stylesheet edit swaps the stylesheet in place; a turn ending reloads once more.
  After a reload, regions the edited files produced are outlined.
- Screenshots: an offscreen window in the project's partition loads the card's page
  at 1440×900 and captures it; the core stores it. Before: when a session first
  starts on a card that has none. After: each time one of its turns ends.

### Renderer

- Settings › Live view: the two switches and what they do.
- A project's **Live** tab: toolbar (back, forward, reload, address, Page/Piece,
  Pick, Clear caches, Open in browser), the view, and an inspector for the picked
  or outlined region: what produced it, Show alone, Send to a session.
- Setup inside the tab: detected addresses to choose from, a typed address, and the
  helper's plan (files, exclude line, command) before it is installed.
- A session's **Live** button splits its terminal with the view, following that
  session's edits.
- The card drawer's **Before and after**: the first before beside the latest after,
  and the page it watches.

### Serve this card

The core runs `ddev stop --unlist` where the site is served and `ddev start` in
the card's checkout (with `ddev composer install` when its `vendor` is missing),
streaming output to a dialog. The database is shared, as ddev shares it by project
name. A checkout with no `.ddev` folder is refused with that reason.

## What is honest to say

- The view shows what the local site serves. A card in another checkout is shown
  only after Serve this card; until then the view says whose code it is showing.
- Drupal template edits show only when Twig caching is off; the view says so and
  offers the development settings or Clear caches.
- Elementor content lives in the database, not files: an agent changing it through
  WP-CLI or Elementor's own tools is seen at the end of its turn, not per edit.

## Tests

- Shared: detection from fixture folders; edit paths; region matching.
- Core: configuration, the helper plan and install/remove against a fixture site
  (files, exclude line, the command run through a stand-in `ddev`), events on edits
  and turns, shots stored and listed, card pages set by owner and session.
- Helpers: against throwaway ddev Drupal 11 and WordPress sites made for the test,
  never the owner's.
- UI sweep and crawl: the demo serves a stand-in site; the tab, setup, inspector
  and card section in both themes.
- App smoke: the real `WebContentsView` loads the stand-in site, reloads on an edit,
  and a screenshot is stored on a card.
