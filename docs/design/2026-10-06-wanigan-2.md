# Wanigan 2.0 — design

October 6, 2026. A ground-up rebuild. Two apps are the source material: **Wanigan 1**
(a session-first control surface for Claude Code and Codex across many repositories)
and **OnTour Production Hub** (a work-first production board built for one game).
Neither codebase is carried forward wholesale. What carries forward is what each one
proved: the Hub's way of working and its interface, and Wanigan's honesty, its
character, and the hard-won knowledge of how the agent CLIs actually behave.

## What the owner asked for

- Work-first, the way the Hub works: a board per project is where work is planned,
  claimed, reviewed and finished. Sessions attach to cards.
- Many projects — all of the owner's web projects — not one game. Each project opened
  in Wanigan has its own board, sessions and history.
- One-off sessions stay first class: open a terminal in a project and work, with no card.
- The Wanigan character — the glass orb with real 3D water — stays.
- Every feature of both apps scrutinised: kept, improved, merged, cut or added, with a
  reason. Game-specific parts of the Hub (levels, the Route, assets, teleport, QA crash
  groups, the Unreal machine) do not exist here.
- Orders of magnitude better in function and in code, and a beautiful, usable product.

## What Wanigan 1 measured

An inventory of Wanigan 1 at `babeb5d` (October 6, 2026) found:

- About 200,000 lines across 551 files, with 463 preload methods, 475 IPC handlers and
  107 SQLite tables.
- 20 destinations in 6 areas, reached through three navigation systems at once: a
  header space switcher, area sub-tabs, and a bottom dock with a drawer rail.
- The same job built many times:
  - "needs you" rendered in 8 or more places;
  - account selection in 8;
  - the review gate in 5;
  - resume in 5;
  - transcript search in 4;
  - spend in 6;
  - the goal task graph has three front ends (Goals, Board, Relay) and six ways to
    create a goal;
  - two separate GPU fluid engines.

2.0's rule is **one place per job**. Each row of the ledger below names that place.

## Principles (inherited, still binding)

1. **The operator is the constraint.** Design for what one person can review.
2. **Nothing happens you can't see afterward.** Every claim, transition, hook event and
   session is recorded and attributable.
3. **It survives a quit.** Closing or crashing the window never kills a session.
4. **Local, and yours.** No account, no cloud tier, nothing written into a user's repo
   to make Wanigan work.
5. **Say the true thing.** No false greens. Unknown is shown as unknown. A claim is not
   proof a process is running; a hook delivery is not proof an instruction was done.

## The model

| Object | What it is |
|---|---|
| **Project** | A folder on disk the owner opened. Has a short key (`NOR`), its own board, sessions, decisions and activity. |
| **Card** | A unit of work: task, bug, feature or idea. Key `NOR-12`. Moves Inbox → Ready → Working → Review → Done. Has a description, acceptance criteria, comments, evidence and attached sessions. |
| **Session** | A real terminal process (Claude Code, Codex, or a shell) running in a project. Attached to a card, or a one-off. Has a live state and a recorded event timeline. |
| **Claim** | A session's lease on a card. Expires unless renewed. One claimant per card. |
| **Evidence** | Something offered as proof: a file, a screenshot, a test log, a note. Moving a card to Review requires at least one piece. |
| **Decision** | A recorded rule for a project ("use pnpm", "no new dependencies without asking"). Injected into every session that starts in that project. |
| **Activity** | The append-only record of everything that happened, by whom. |

### Board rules (enforced by the core, not the UI)

- Statuses: `inbox`, `ready`, `working`, `review`, `done`, plus `archived` (hidden).
- An agent can claim a Ready card; claiming moves it to Working. The Inbox is the
  owner's to triage: an agent cannot take a card from it, and a session the owner
  starts on an Inbox card is the owner accepting it.
- A claim is a 30-minute lease, renewed automatically while its session's process
  runs. Another session cannot take a claimed card.
- An agent cannot move a card to Done. It submits for review with evidence; the owner
  approves (Done) or sends back with a note (Ready, note becomes a comment and the
  session that submitted sees it).
- **Reopen as not fixed:** the owner can pull a Done card back. What is still wrong
  becomes a new acceptance criterion. The card goes to Ready, flagged.
- Only the owner archives, and archiving is final. Nothing is deleted.

### Session states

`starting` → `working` ⇄ `waiting` (idle at its prompt) → `ended` / `failed`.
`permission` — the agent is blocked on an approval the owner must give.
`interrupted` — the process was lost (machine restart, core crash); resumable if the
provider keeps a conversation ID.
`limited` — the account's usage limit stopped its turn.

States come from evidence, never assumption: Claude Code hook events
(UserPromptSubmit, PreToolUse, PostToolUse, PermissionRequest, Notification, Stop,
SessionEnd — the rules proven in Wanigan 1, including "a permission request stands
until something answers it"), PTY exit codes, and process liveness. A shell session
has only `running`, `ended`, and `failed` (a non-zero exit). Any process ended by a
signal Wanigan did not send is `failed`.

### Needs you

One cross-project inbox, the first thing in the sidebar, counting:

1. sessions blocked on a permission prompt (highest);
2. cards in Review waiting for the owner;
3. sessions that failed or were interrupted;
4. sessions waiting at their prompt after finishing a turn (lowest, and dismissible).

It also counts two live sessions editing one file, a session stopped by its usage
limit, a working Claude session gone quiet, and an agent's question on its card.
The full order is `NEED_KINDS` in `src/shared/model.ts`.

The orb's colour reflects the most urgent of these.

## Architecture

```
┌──────────────┐  IPC (typed, allowlisted)  ┌───────────────┐   socket (JSON lines)   ┌────────────────────────┐
│  Renderer    │ ─────────────────────────▶ │ Electron main │ ──────────────────────▶ │  Core (daemon)         │
│  React UI    │ ◀───────── events ──────── │ windows, menu │ ◀──── events ────────── │  SQLite · PTYs · rules │
└──────────────┘                            └───────────────┘                         └────────▲───────────────┘
                                                                                               │ socket, session token
                                                                                     ┌─────────┴─────────┐
                                                                                     │ `wanigan` CLI     │
                                                                                     │ (agents + owner)  │
                                                                                     └───────────────────┘
```

- **Core** (`src/core`) is the only owner of the database and of every terminal. It is
  a separate process started by the app (Electron's binary in Node mode, so native
  modules share one ABI), detached so it outlives the window. It listens on a Unix
  socket in the data directory (directory `0700`). It shuts itself down only when no
  session is live and no client has connected for ten minutes.
- **Auth is identity.** The app authenticates with an owner token (`0600` file). Every
  session gets its own random token in its environment; the core stores only its hash.
  A request made with a session token *is* that session — an agent cannot claim to be
  someone else, and cannot act outside its project. (The Hub trusted `--agent` names.)
  This holds against a mistaken or confused agent, not a hostile one: a session runs
  as the owner's own macOS user, so it can read the owner token from the data
  directory like any other file of that user's. The session/owner split is a rule the
  core keeps for well-behaved agents, not a sandbox, and Wanigan never describes it as
  one. Containing a hostile agent needs an OS boundary (a separate user or a sandbox
  profile), which 2.0 does not have.
- **Electron main** (`src/main`) is thin: ensure the core is running, connect, bridge an
  allowlist of methods and event topics to the renderer, own windows, menu,
  notifications. The renderer never sees a token or a socket. A core that cannot start
  writes why to `core.failed.json`, and the window says so with Try again; it is not
  started again on every call. A core left running by another build (its `core.hello`
  build is a hash of the core's entry script) is replaced when no session runs in it,
  and otherwise the owner is asked, because its live sessions would end with it.
- **Renderer** (`src/renderer`) talks only through `window.wanigan`. The same renderer
  can run in plain Chromium against a real core through a test-only gateway, which is
  how every view is checked in both themes; the real app's window is driven by
  Playwright's Electron driver in `scripts/app-smoke.mjs` and `scripts/showcase.mjs`.
- **CLI** (`src/cli`) is how agents use the board: `wanigan status`, `claim`, `note`,
  `review --evidence`, `file`, `release`. A shim on the session's `PATH` makes it
  available in every session Wanigan starts, with no global install and nothing
  written into the repository.
- **Shared** (`src/shared`) holds the protocol types and the pure domain rules (board
  transitions, attention ranking, state derivation). Pure means testable in
  milliseconds.

### Protocol

Newline-delimited JSON. Request `{id, method, params}` → `{id, result}` or
`{id, error: {code, message}}`. Server events `{event, data}`. The method map lives
in `src/shared/protocol.ts` and types both ends; a method not in the map does not
exist. Each method declares which roles may call it (`owner`, `session`). Hook events
arrive on a socket of their own, one per connection, and call no methods.

### Data

SQLite (WAL) at `<dataDir>/wanigan.db`. `dataDir` is
`~/Library/Application Support/Wanigan 2` — never Wanigan 1's store. Migrations are
additive and versioned in `meta`. Terminal scrollback lives in the core's memory
(bounded ring buffer per session) and a capped file per session, so a reopened window
replays it.

## Interface

The Hub's layout, refined; Wanigan's character, placed where it means something.

```
┌ rail (248) ────────┬ topbar: title · subtitle ·············· toolbar ┬ drawer (min 560) ┐
│ (orb) Wanigan      │                                                  │ NOR-12  Task  ✕   │
│ [+ Session ⌘T]     │   Inbox   Ready   Working   Review   Done        │ title             │
│ [+ Card     C]     │   ┌───┐   ┌───┐   ┌───┐◉    ┌───┐   ┌───┐        │ status · priority │
│ ── Needs you   3   │   └───┘   └───┘   └───┘     └───┘   └───┘        │ criteria ☐☑       │
│    Running     2   │                                                  │ sessions ▸ term   │
│ ── Projects        │                                                  │ evidence          │
│  ● Northstar   ▾   │                                                  │ comments          │
│     Board          │                                                  │ activity          │
│     Sessions  1    │                                                  │                   │
│     Decisions      │                                                  │                   │
│     Activity       │                                                  │                   │
│  ○ Orbit API       │                                                  │                   │
│ ── ⌘K · ◐ · core ● │                                                  │                   │
└────────────────────┴──────────────────────────────────────────────────┴───────────────────┘
```

- **Rail:** brand with the live orb; two primary actions (New session ⌘T, New card C);
  Needs you and Running across all projects; the project list, the open project
  expanded into its views; footer with command palette, theme, core status.
- **Board:** columns with counts; cards show key, type, priority, title, claim and live
  session badge; drag between columns; filter, sort, group; keyboard first.
- **Drawer:** the card, editable in place. Start a session on the card from here.
- **Session view:** the terminal, full height, with a composer that queues a message
  until the agent is idle, and a right rail with the session's event timeline (tool
  calls, permission requests, files touched).
- **Command palette (⌘K):** every action and every card and session, fuzzy.
- **Keyboard:** `C` new card, `⌘T` new session, `G` then `B/S/N/R/D/A` to jump,
  `J/K` move, `Enter` open, `Esc` close.

### Visual language

- Warm-neutral dark first, with a real light theme. One accent family per meaning:
  **water blue** is Wanigan and primary action; **amber** is reserved for *needs you*;
  red is failure; green is done. Colour is an event, not decoration.
- IBM Plex Sans for interface text, IBM Plex Mono for keys, paths and terminals,
  bundled locally. A condensed display face only for the nameplate.
- 4px spacing grid, three radii, one shadow for overlays. Every value is a token.
- Motion is short and functional (drawer, drag, state change) and respects reduced
  motion.

### The character

The water orb from Wanigan 1, ported with water as its only material (the other
twelve materials are cut). It lives in the rail as a small live presence, tinted by
the most urgent Needs-you state (clear when quiet, blue when agents are working,
amber when someone needs you, red on failure), and large as the empty state of
Needs you ("Nothing needs you"). Drag to stir him. It never appears yellow in
published screenshots.

## Build order

Each milestone ends working, tested, and committed.

1. **Foundation.** Repo, build, core with SQLite and the socket API, projects, cards,
   criteria, comments, activity; unit tests in Electron's own Node.
2. **Interface shell and board.** Rail, topbar, drawer, board with drag, list, palette,
   themes, keyboard; the browser harness and a both-themes sweep that asserts every
   view rendered real data.
3. **Sessions.** PTYs in the core, terminal view with replay, one-off and card sessions,
   promote to card, survive window quit.
4. **Agents on the board.** The CLI with session tokens, hook injection and state, claims
   and leases, review with evidence, Needs you.
5. **The character.** Water orb in the rail and Needs you.
6. **Decisions and polish.** Decisions injected at session start, native notifications,
   empty states, motion.
7. **Accounts and usage.** Ported readers, profile selection at session start.

Later, in order of value, as planned on 6 October: AI reviewer and PM (opt-in,
metered), worktrees and Changes, since-you-last-looked, saved views, overlap warning,
pause all, packaging. All but saved views have since been built; the PM became Jev's
triage and Talk to Wanigan.

## Testing

- `npm run test:unit` — `node --test` under Electron's Node over `src/**/*.test.ts`:
  shared rules, the core's stores against a real temporary SQLite file, the socket API
  with real tokens, real PTYs running `/bin/sh`.
- `npm run test:ui` — build, start a real core in a temporary data directory, seed it
  through the CLI and API, serve the renderer to Chromium through the test gateway,
  visit every route in both themes, and fail on console errors, error boundaries,
  `undefined`/`NaN`/`null` text, horizontal overflow, or a view still loading.
  Screenshots are written per route and theme and are looked at, not just counted.
- `npm test` runs typecheck, unit and UI.
