# Paid-request settlement — primary sources — 2026-09-19

Research only. No source was edited, no provider was called, no credential was entered. Web pages were read on 2026-09-19; the SDK inspected is `@anthropic-ai/sdk` **0.68.0** as installed in `node_modules` (`package.json:3`). Citations are to the page or file that owns the claim. Where no primary source settles a point this note says **not established**, and that is a finding, not a gap to paper over.

## Outcome

A successful Messages response is strong evidence of *what was metered* — it carries a server-issued `request-id` and a `usage` object — but no Anthropic source calls that object the bill, and the documentation of the Usage & Cost API explicitly positions the Admin reports, not response counting, as the record to reconcile against. Anthropic's help centre states that failed requests are not charged **and** that a request the client abandoned mid-flight "is still charged", so a transport failure or timeout with no response is genuinely unknown, not zero. There is no idempotency key on the Messages or Batches API in the SDK or the docs, the SDK retries up to twice by re-entering the whole request path, and the custom `fetch` is invoked exactly once per attempt — so Wanigan's per-attempt receipt is correct and a timed-out attempt followed by a successful retry can be two charges. The Admin cost report is daily, grouped only by workspace and description, and has no request id or API-key dimension; the usage report goes down to one minute and can filter by API key but reports tokens, not dollars, and also has no request id. Reconciliation can therefore bound a *window per key*, never settle *one receipt*. Claude Code's `total_cost_usd` and its OTel cost metric are documented by Anthropic as client-side estimates. A settlement contract is possible, but it has three terminal states, not one: **metered**, **not charged (provider-stated)**, and **unresolved** — and the last one does not age into either of the others.

## 1. What a Messages response establishes about billing

**Established.**

- The `usage` fields, from the SDK's generated types ([`src/resources/messages/messages.ts:1108-1143`](../../node_modules/@anthropic-ai/sdk/src/resources/messages/messages.ts)): `input_tokens`, `output_tokens`, `cache_creation_input_tokens`, `cache_read_input_tokens`, `cache_creation` ("Breakdown of cached tokens by TTL"), `server_tool_use` ("The number of server tool requests"), `service_tier` (`'standard' | 'priority' | 'batch' | null`).
- The same file's doc comment on `Message.usage` (`messages.ts:474-490`): "Billing and rate-limit usage. Anthropic's API bills and rate-limits by token counts, as tokens represent the underlying cost to our systems. … the token counts in `usage` will not match one-to-one with the exact visible content of an API request or response. … Total input tokens in a request is the summation of `input_tokens`, `cache_creation_input_tokens`, and `cache_read_input_tokens`." So `usage` is declared to be the billing-relevant count, and local token estimation is declared not to match it.
- In a stream, "The token counts shown in the `usage` field of the `message_delta` event are *cumulative*." (<https://platform.claude.com/docs/en/build-with-claude/streaming>). The Agent SDK cost page adds that `output_tokens` at `message_start` is a placeholder and "The API reports the real output count at the end of the response" (<https://code.claude.com/docs/en/agent-sdk/cost-tracking>). A stream that ends before its final `message_delta` has **no** authoritative output count.
- Failed requests, from the help centre ("How do I pay for my Claude API usage?", <https://support.claude.com/en/articles/8977456-how-do-i-pay-for-my-api-usage>, page dated August 19, 2026), verbatim: "You're billed only for successful API calls and completed tasks. Failed requests aren't charged." and "**Note:** If your client disconnects or times out in the middle of a request that was on track to succeed, that request is still charged."
- An error can arrive after HTTP 200 on a stream: "an error can occur after the API returns a 200 response" (<https://platform.claude.com/docs/en/api/errors>), e.g. an `overloaded_error` event "which would normally correspond to an HTTP 529" (streaming page, "Error events").
- Adjacent per-feature statements on the pricing page (<https://platform.claude.com/docs/en/about-claude/pricing>): "If an error occurs during web search, the web search will not be billed."; code execution "execution time is billed even if the tool is not called" when files are included.

**Not established.**

- No Anthropic page states that response `usage` *is* the invoiced quantity. The Usage & Cost API page lists as a benefit "Get precise token counts and usage patterns instead of relying solely on response token counting" and "Cost reconciliation: Match internal records with Anthropic billing" (<https://platform.claude.com/docs/en/manage-claude/usage-cost-api>). Read plainly: response `usage` is a meter reading; the Admin reports are the billing-side record.
- "Failed requests aren't charged" is not broken down by status. It is a help-centre sentence, not an API contract: nothing on the errors page, pricing page or API reference says 4xx, 5xx or 529 are unbilled. It is reasonable to read an HTTP error *response* (with a `request-id`) as a failed request; it is **not established** what is charged for a stream that emitted tokens and then errored mid-stream, nor how much of a client-abandoned request is charged (full generation, or up to disconnect).
- Whether the server can observe a client disconnect and stop generating: not stated.

**Wanigan currently assumes** nothing here — the receipt is never settled ([`usage-paid-operations.ts:10-15`](../../src/main/modules/usage-paid-operations.ts)). Callers that do record cost store tokens and *this app's* price arithmetic (`estimated_cost_usd` in [`prompt-improve-usage.ts`](../../src/main/prompt-improve-usage.ts)); the dry-run sample at [`batch/estimate.ts:198`](../../src/main/batch/estimate.ts) reads `msg.usage` into a return value and writes no ledger row.

## 2. Request identity, idempotency and SDK retries

**Established.**

- "Every API response includes a unique `request-id` header." and "The same identifier appears as the `request_id` field in error response bodies." (<https://platform.claude.com/docs/en/api/errors#request-id>). Its documented purpose is support, not billing lookup: "When contacting support about a specific request, include this ID".
- SDK exposure: `_request_id` is defined from `response.headers.get('request-id')` on object responses ([`src/internal/parse.ts:72-81`](../../node_modules/@anthropic-ai/sdk/src/internal/parse.ts)); `.withResponse()` returns `request_id` ([`src/core/api-promise.ts:73`](../../node_modules/@anthropic-ai/sdk/src/core/api-promise.ts)); `APIError.requestID` is set from the same header ([`src/core/error.ts:25`](../../node_modules/@anthropic-ai/sdk/src/core/error.ts)). A connection error or timeout has no response and therefore **no request id**.
- Retries ([`src/client.ts`](../../node_modules/@anthropic-ai/sdk/src/client.ts)): default `maxRetries` is 2 (`:316`). A thrown fetch (connection failure, or the SDK's own timeout abort) retries while attempts remain (`:565-591`); a caller abort does not (`:567-569`). An HTTP error retries when `x-should-retry: true`, or on 408, 409, 429 and `>= 500` — which includes 529 (`:737-758`), unless `x-should-retry: false`. Backoff is `retry-after-ms`/`retry-after` if under 60 s, else 0.5 s doubling to 8 s with jitter (`:760-812`). README agrees: "Connection errors …, 408 Request Timeout, 409 Conflict, 429 Rate Limit, and >=500 Internal errors will all be retried by default" and "requests which time out will be retried twice by default".
- **Custom `fetch` is called once per attempt — confirmed.** `retryRequest` ends with `return this.makeRequest(options, retriesRemaining - 1, requestLogID)` (`client.ts:796`); `makeRequest` rebuilds the request and calls `fetchWithTimeout` once (`:562`), which calls `this.fetch.call(undefined, url, fetchOptions)` once (`:731`); `this.fetch` is `options.fetch ?? Shims.getDefaultFetch()` (`:317`). There is no other call site on the request path. The comment at [`usage-paid-operations.ts:34-35`](../../src/main/modules/usage-paid-operations.ts) is accurate for 0.68.0.
- Each attempt is a new HTTP request, so each response that arrives has its own `request-id`. The SDK sends `X-Stainless-Retry-Count` (`client.ts:877`) but no stable cross-attempt identity; the `log_…` id is local ("Not an API request ID, just for correlating local log entries", `:541`).
- **No idempotency key.** The base client has an `idempotencyHeader` hook (`client.ts:269`, `:866-870`) but nothing in the package assigns it, so no header is sent. The only "idempotent" in the resources is the batch *retrieve* poll (`resources/messages/batches.ts:48`). The docs index at <https://platform.claude.com/llms.txt> contains no page mentioning idempotency.

**Not established.** That the API would ignore or honour a caller-supplied idempotency header; nothing documents one, so assume none. Whether `request-id` can be looked up by a customer anywhere (Console or Admin API): no documented surface does this.

**Consequence.** A timed-out attempt may be "still charged" (section 1) and its retry charged again. Nothing on the wire lets the provider or Wanigan collapse them.

## 3. Message Batches

**Established** (<https://platform.claude.com/docs/en/build-with-claude/batch-processing>):

- Price: "All usage is charged at 50% of the standard API prices."
- Per-result billing, from the result-type table: `errored` — "Request encountered an error and a message was not created. … You will not be billed for these requests."; `canceled` — "User canceled the batch before this request could be sent to the model. You will not be billed for these requests."; `expired` — "Batch reached its 24-hour expiration before this request could be sent to the model. You will not be billed for these requests." Only `succeeded` results are billed, and each carries a full `message.usage`.
- A canceled batch "may contain partial results" — requests already sent to the model before cancellation come back `succeeded` and are billable.
- Retention: "Batch results are available for 29 days after creation." and, in troubleshooting, "less than 29 days since batch `created_at` (not processing `ended_at`) time". **Wanigan's 29-day assumption ([`notify.ts:51-56`](../../src/main/notify.ts), [`batch/poll.ts:164`](../../src/main/batch/poll.ts)) is confirmed, including the clock starting at creation.**
- Expiry: "Batches expire if processing does not complete within 24 hours."

**Not established.** *When* a batch's charges post (per request as processed, or at `ended`). Whether per-result `usage` is the invoiced quantity — same caveat as section 1. What happens to a `POST /v1/messages/batches` whose response was lost: the batch may exist. Unlike a lost Messages call this one is discoverable, because batches are listable server-side objects (`batches.list` exists in the SDK), but matching a listed batch to a lost receipt would rest on creation time and request count, not on an identifier Wanigan sent.

## 4. Usage & Cost Admin API

**Established** (guide: <https://platform.claude.com/docs/en/manage-claude/usage-cost-api>; reference: <https://platform.claude.com/docs/en/api/admin-api/usage-cost/get-cost-report>):

- Key type: "an Admin API key, an OAuth token with the `org:admin` scope, or a personal or service account key that isn't scoped to a workspace; workspace API keys don't work." and "The Admin API is unavailable for individual accounts." [`spend.ts:873-1030`](../../src/main/spend.ts) already refuses to reuse the batch key, which matches.
- Usage report `/v1/organizations/usage_report/messages`: buckets `1m` (max 1,440), `1h` (max 168), `1d` (max 31); "Filter by API key, workspace, model, service tier, context window, data residency, or speed (beta), and group results by these dimensions". It returns **tokens**, not dollars.
- Cost report `/v1/organizations/cost_report`: "Daily granularity only (`1d`)"; `group_by` is "`description`" or "`workspace_id`" only; `amount` is "in lowest currency units (e.g. cents) as a decimal string"; buckets are "snapped to the start of the minute/hour/day in UTC". Result fields: `amount`, `currency`, `cost_type`, `description`, `model`, `service_tier`, `token_type`, `context_window`, `inference_geo`, `workspace_id`. **No `request_id`, no `api_key_id`.**
- "Priority Tier costs use a different billing model and are not included in the cost endpoint."
- Freshness: "Usage and cost data typically appears within 5 minutes of API request completion, though delays may occasionally be longer." Polling: "once per minute for sustained use".
- Playground usage has `api_key_id` `null`; the default workspace has `workspace_id` `null`.

**Confirmed negative.** Neither report can attribute anything to a single request. The finest dollar figure is one UTC day × workspace × description line; the finest token figure is one minute × API key × model.

**Not established.** An upper bound on report latency ("may occasionally be longer" is unbounded). Whether the cost report equals the invoice (the page says the data is "similar to" the Console pages and is for "reconciliation"; credits, taxes and contracted discounts are not discussed). Whether an abandoned-but-charged request appears in the usage report under the minute it started or finished.

## 5. Claude Code headless cost fields and OTel metrics

**Established.**

- Headless: "With `--output-format json`, the response payload includes `total_cost_usd` and a per-model cost breakdown … Both figures are client-side estimates and can differ from your actual bill." (<https://code.claude.com/docs/en/headless>).
- Agent SDK cost page (<https://code.claude.com/docs/en/agent-sdk/cost-tracking>): "The `total_cost_usd` and `costUSD` fields are client-side estimates, not authoritative billing data. The SDK computes them locally from a price table bundled at build time … For authoritative billing, use the Usage and Cost API or the Usage page in the Claude Console. Do not bill end users or trigger financial decisions from these fields." It also says `usage` excludes subagents while `total_cost_usd` and `modelUsage` include them; error results carry cost too; after a process crash the final result "may carry zeroed `usage`, `total_cost_usd`, and `modelUsage`"; and "connection or process failures yield no result message". `modelUsage[*].costBasis` is `list`, `managed` or `unknown` (Claude Code v2.1.246+).
- Subscription versus API key (<https://code.claude.com/docs/en/costs>): "Claude Max and Pro subscribers have usage included in their subscription, so the session cost figure isn't relevant for billing purposes." and "Claude Code computes the dollar figure locally from token counts at list price … The figure is an estimate, so for authoritative billing see the Usage page in the Claude Console." On Teams/Enterprise, "Usage inside the seat allowance isn't metered in dollars."
- OTel (<https://code.claude.com/docs/en/monitoring-usage>): `claude_code.cost.usage` — "Cost of the Claude Code session", unit USD; `claude_code.token.usage` — "Number of tokens used", `type` ∈ `input`/`output`/`cacheRead`/`cacheCreation`. "Cost metrics are approximations. For official billing data, refer to your API provider (Claude Console, Amazon Bedrock, or Google Cloud's Agent Platform)." The `api_request` event has `cost_usd`: "Estimated cost in USD" and `request_id` "Present only when the API returns one"; `client_request_id` is "Available even when a failure such as a timeout or connection error never produced a server `request_id`" (v2.1.214+).

**Not established.** That `total_cost_usd` is suppressed or zero under a Pro/Max login — the docs say it is irrelevant to billing, not that it is absent, so a non-zero figure from a subscription session is a list-price notional and must not be summed as spend. Whether Wanigan can know, from the CLI result alone, which login produced it.

**Wanigan currently** stores `cost_reported` per headless row ([`spend.ts:121-129`](../../src/main/spend.ts)) and keeps unreported distinct from zero, which is consistent with all of the above. For the `learning:cli` receipt, a parsed result message is evidence that the run *reported*, with an estimate attached — not a bill.

## 6. Analogy only: pending-to-settled practice elsewhere

This section is analogy from a first-party payment provider. It says nothing about Anthropic.

- Authorisation holds expire **because the counterparty defines the expiry**: "You need to capture the funds before the authorization expires. If the authorization expires before you capture the funds, the funds are released and the payment status changes to `canceled`." with network-defined windows of 2–7 days (<https://docs.stripe.com/payments/place-a-hold-on-a-payment-method>). The pending entry is aged out by a rule the *provider* publishes and enforces, not by the merchant's patience.
- Retries are made safe by a provider-side key: "use an idempotency key. Then, if a connection error occurs, you can safely repeat the request without risk of creating a second object" and keys may be pruned "after they're at least 24 hours old" (<https://docs.stripe.com/api/idempotent_requests>).

**Principle.** A pending entry may be closed by time only when the party that can charge has published a rule saying that after that time it will not. Anthropic publishes such a rule for batches (24-hour expiry, per-result "not billed") and publishes none for an abandoned Messages request — it publishes the opposite ("still charged"). Without a provider idempotency key, the client also cannot make a retry provably single-charge.

## Consequences for a settlement contract

An unknown is never zero, and an estimate is never a bill. The contract below never writes a dollar figure it did not observe, and distinguishes *accounted for* (the owner ledger holds the provider's own meter reading, or the provider's stated non-charge) from *reconciled* (matched to the Admin report), which this design does not claim per receipt.

1. **(a) Strong enough to mark a receipt accounted-for — `metered`.** A parsed 2xx Messages response (or a stream that reached its final `message_delta`) on the same attempt. Record on the receipt: the `request-id`, the settlement kind `metered`, the time, and the **owner ledger row id** that now holds `usage` verbatim (all seven fields, including `service_tier` and `server_tool_use`, nulls preserved). The receipt does not copy tokens or dollars; it points. No owner row means no settlement — which makes the ledger-less dry-run sample at [`batch/estimate.ts:198`](../../src/main/batch/estimate.ts) the first thing to fix, by giving it an owner row. Label it "metered by provider response", never "billed".
2. **(a) Also strong enough — `not-charged (provider-stated)`.** An HTTP error *response* (4xx/5xx/529) that carried a `request-id`, before any stream body. Record request id, status, error `type`, and the citation class "help-centre: failed requests aren't charged". This is a provider statement, not an observation, and the label must say so. A mid-stream `error` event after 200 does **not** qualify (section 1, not established).
3. **(a) Batches.** The `anthropic:batches` receipt is accounted-for when the create call returns a batch id and that id is written to the batch owner row; cost then belongs to the existing per-result ledger, where `succeeded` is `metered` from its `usage` and `errored`/`canceled`/`expired` are `not-charged (provider-stated)` per the batch page. A batch whose results were never fetched inside 29 days of `created_at` stays unresolved: its succeeded requests were billable and their usage is no longer retrievable.
4. **(a) Learning CLI.** A parsed `result` message settles the receipt as `reported-estimate`, pointing at the headless row with `cost_reported`, `total_cost_usd`, `modelUsage` and `costBasis`. It is accounted-for in the sense that the owner ledger holds everything the harness will ever say; it is an estimate by Anthropic's own words and, under a subscription login, not spend at all.
5. **(b) Must stay unresolved.** Connection error, SDK timeout or caller abort with no response headers; a stream cut before the final `message_delta`; a mid-stream `error` event; a 2xx whose body could not be parsed; a batch create with no response; a CLI that exited, crashed or was killed without a result message (or with the zeroed crash result); any app crash between receipt and response. For these, record the *reason* and, where one exists, the partial evidence (request id from headers, last cumulative usage seen) — as evidence, not as settlement.
6. **(c) Admin-report reconciliation cannot settle a single receipt, and should not pretend to.** What it can responsibly do is a *window statement*: for API key K and minute-bucket window W (usage report, filtered by `api_key_ids[]`), compare reported tokens against the sum of `metered` owner rows in W. If they agree exactly and the window closed well past the documented "typically … 5 minutes", the unresolved receipts in W are *consistent with no charge*; if reported exceeds metered, the excess is an upper bound on what the unresolved receipts cost. Stated uncertainty, every time: requires an admin key (absent for individual accounts); freshness has no documented upper bound; any other client using K in W breaks the inference; the dollar report is a UTC day by workspace and cannot confirm the token inference; Priority Tier is absent from cost. This is a third label — `window-consistent` — shown to the operator as evidence. Whether it may lift the restore refusal is an operator decision made with that label visible, not something Wanigan infers silently.
7. **(d) Receipts do not age out.** No Anthropic source says an abandoned Messages request becomes free after any interval; the only source says it "is still charged". Age changes nothing about the fact. What may change with age is *presentation* (group old unresolved receipts) and what an operator may do: an explicit, recorded **operator acknowledgement** ("I accept N unresolved receipts from before T as unknown cost") can stop them blocking restore while leaving them unresolved in the ledger and in every total as unknown. That is a consent record, not a settlement, and it must never convert to zero. The batch path is the one place a provider-published clock exists (24-hour expiry, 29-day retention), and it closes in the conservative direction.
8. **(e) Per-attempt receipts are correct; keep them.** The SDK calls `fetch` once per attempt (`client.ts:731`, re-entered from `:796`), each attempt is a distinct request with its own `request-id`, there is no idempotency key, and a timed-out attempt may be charged alongside its successful retry. Settle each attempt's receipt on its own evidence: a 429/5xx/529 attempt becomes `not-charged (provider-stated)`, the successful retry becomes `metered`, and a timed-out attempt in the same chain stays unresolved even though the caller got an answer. To make that practical, `admittedFetch` needs to hand the receipt id to whatever observes the response for that attempt — the response is visible at the same seam, since `send(input, init)` returns it. Callers that want fewer unresolved rows can set `maxRetries: 0` on paid calls and surface the failure instead.
9. **Schema shape, additive.** Keep `usage_paid_operations` append-only and add a sibling `usage_paid_settlements(receipt_id, kind, request_id, owner, owner_row_id, status, evidence, at)` rather than updating the receipt, so the pre-send record stays exactly what was written before the send and Recovery can treat "receipt without settlement row" as today's unresolved.
