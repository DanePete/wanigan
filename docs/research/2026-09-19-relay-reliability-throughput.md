# Relay reliability and accepted throughput

Research and repository comparison, 2026-09-19. Objective: lower **total cost per accepted coding task**, including failed attempts, while increasing accepted throughput under the same quality requirements. This report supplements [the earlier orchestration comparison](2026-09-19-coding-agent-orchestration.md); it focuses on execution and measurement failures exposed by [the real Relay trials](2026-09-19-relay-live-trials.md).

The practical priority is to make a paid attempt start correctly, keep its workspace available, and return useful verified progress before making routing more elaborate. The recommendations below are design inferences from inspected implementations and local evidence, not measured savings. No provider call, installation, benchmark run, or product-source change was performed for this research. Moving upstream `main` references were inspected on this date; pin a revision before adopting code.

## Ten primary references worth borrowing from

### 1. mini-SWE-agent: explicit execution results and bounded failure

The inspected [`environments/local.py`](https://github.com/SWE-agent/mini-swe-agent/blob/main/src/minisweagent/environments/local.py) executes each action as its own subprocess with explicit cwd/environment, return code and timeout. On POSIX, timeout handling kills the process group. Its completion marker means submission, not independently verified correctness. [`agents/default.py`](https://github.com/SWE-agent/mini-swe-agent/blob/main/src/minisweagent/agents/default.py) distinguishes exit reasons, persists trajectories, and bounds calls, elapsed time and repeated formatting failures. Its cost limit is checked before the next call, so a completed call can overshoot it.

**Relay adaptation:** prefer a declared machine execution protocol where the actual harness supports one; otherwise use a tested interactive startup state machine. Borrow explicit readiness, completion and failure receipts, not a replacement simulated agent. A CLI session does not automatically expose the per-call controls of this Python loop.

Maintenance matters: [SWE-agent's own documentation](https://swe-agent.com/latest/config/environments/) now describes SWE-agent as maintenance-only and points to mini-SWE-agent. The latter's inspected [license is MIT](https://github.com/SWE-agent/mini-swe-agent/blob/main/LICENSE.md). Reuse the small contracts; adopting its Python/model stack wholesale would duplicate Wanigan's provider and credential boundaries.

### 2. Aider: inexpensive checks precede another repair turn

In [`aider/coders/base_coder.py`](https://github.com/Aider-AI/aider/blob/main/aider/coders/base_coder.py), `send_message` applies edits, optionally lints changed files, and optionally runs the configured test command. Accepted repair feedback becomes a reflected message; `run_one` bounds reflections, with `max_reflections = 3`. Automatic tests are configurable, not universally enabled. This is an inspectable execution loop, not evidence of a universally optimal retry count.

**Relay adaptation:** let a deterministic failure produce a concise repair packet. Avoid an extra model merely to say that a known command failed. Keep the complete required final gate; targeted checks shorten intermediate feedback, not the acceptance standard. Aider's [Apache-2.0 license](https://github.com/Aider-AI/aider/blob/main/LICENSE.txt) differs from the MIT projects here; the recommendation is conceptual reuse, not copying its automatic-commit policy into Relay.

### 3. OpenHands: workspace lifetime is a separate interface

The SDK's [`workspace/local.py`](https://github.com/OpenHands/software-agent-sdk/blob/main/openhands-sdk/openhands/sdk/workspace/local.py) operates directly on the host; its pause/resume methods do not suspend host processes. [`DockerWorkspace`](https://github.com/OpenHands/software-agent-sdk/blob/main/openhands-workspace/openhands/workspace/docker/workspace.py) instead owns container launch, health checks, mounts, pause/unpause and cleanup. Configurable volume mounts mean “container” alone does not prove every dependency is private. Its context-manager cleanup stops the container, so durable workspace retention must still be chosen deliberately.

**Relay adaptation:** define separately the task record, process, checkout, dependency environment and lease. Preserve the task's checkout after a process dies. A workspace interface can support private local clones first and a contributed container backend later. The inspected SDK [license is MIT](https://github.com/OpenHands/software-agent-sdk/blob/main/LICENSE); Python services, Docker startup, image maintenance and macOS native-app compatibility are real adoption costs. No inspected source proves those costs pay back for small Electron changes.

### 4. LangGraph: recovery is not “replay everything”

Official [checkpointer documentation](https://docs.langchain.com/oss/python/langgraph/checkpointers) distinguishes persisted successful sibling writes, resumption, and replay from a prior checkpoint. Replay re-executes subsequent LLM/API calls. `sync`, `async`, and `exit` durability make different crash-safety/performance tradeoffs. The [interrupt documentation](https://docs.langchain.com/oss/python/langgraph/interrupts) warns that interrupted nodes restart and preceding side effects must be idempotent. Actual [`pregel/_retry.py`](https://github.com/langchain-ai/langgraph/blob/main/libs/langgraph/langgraph/pregel/_retry.py) selects retry policies by exception, caps attempts, and applies backoff/jitter.

**Relay adaptation:** persist attempt intent before launch; reconcile the same attempt after a crash; retain completed deterministic stage receipts. Use an operation identity to prevent duplicate launches or decisions. External actions need reconciliation even when graph state is durable. This does not preserve a Wanigan PTY across a full quit. LangGraph is [MIT licensed](https://github.com/langchain-ai/langgraph/blob/main/LICENSE); borrowing these semantics in Relay's existing SQLite kernel is a smaller first step than introducing a second workflow runtime.

### 5. SWE-bench's actual harness: grade repair and preservation separately

[`swebench/harness/grading.py`](https://github.com/SWE-bench/SWE-bench/blob/main/swebench/harness/grading.py) distinguishes `FAIL_TO_PASS` from `PASS_TO_PASS`; full resolution requires both groups to succeed. [`run_evaluation.py`](https://github.com/SWE-bench/SWE-bench/blob/main/swebench/harness/run_evaluation.py) applies candidate patches, runs evaluation in containers with timeouts, and retains logs and execution errors.

**Relay adaptation:** the acceptance packet must contain both the requested behavior and existing behavior that must remain intact. Store the actual checkout identity, command recipe and execution result. Separate environment failure, invalid proof and code failure. A useful verification mechanism does not make every task/test pair a valid benchmark, and passing its selected tests does not establish maintainability or product fit.

### 6. Anthropic's later long-running harness: handoff policies must be tested per model

The March 2026 [long-running application harness report](https://www.anthropic.com/engineering/harness-design-long-running-apps) uses scoped work, written handoffs, and a separate evaluator interacting with the running application. It also reports removing context resets when the stronger model no longer needed the workaround. One illustrated comparison cost $9 for a solo run versus $200 for the full harness, while the harness expanded the task into a much larger product. That comparison is not a controlled cost-per-accepted-equivalent-task result.

**Relay adaptation:** keep an explicit acceptance contract and bounded handoff artifact. Compare resume, compaction and a fresh session on the *same* scoped work before choosing a policy. Do not require a planner, evaluator, context reset, or ambitious scope expansion for every small edit. Model-graded quality remains advisory to the test/human gate.

### 7. Anthropic's multi-agent research system: parallelism has an economic threshold

The [production research-system report](https://www.anthropic.com/engineering/multi-agent-research-system) reports approximately 15 times chat token use for its multi-agent system and cautions that coding often has fewer independent subtasks than research. It uses bounded assignments and scales effort to query complexity. The token multiplier belongs to that research deployment; it is neither Relay's expected multiplier nor a comparison with a single coding agent.

**Relay adaptation:** parallelize independent tasks with separate writable environments and a defined integration owner. Do not fan out competing implementations of a tiny copy change by default. Evaluate accepted output per elapsed time and total spend together: additional workers can shorten time while worsening cost or saturating the human review queue.

### 8. Anthropic's infrastructure study: resource settings can masquerade as model quality

The February 2026 [infrastructure-noise study](https://www.anthropic.com/engineering/infrastructure-noise) reports a six-percentage-point Terminal-Bench 2.0 gap between its resource extremes with model, harness and tasks fixed. Guaranteed allocation and enforced limits produced different failure behavior. Its separate SWE-bench RAM experiment showed a smaller effect.

**Relay adaptation:** control CPU/RAM pressure, native build concurrency, timeouts, dependency state, and CLI/toolchain versions in route comparisons. Record both allocation and enforcement. Shared `node_modules` corruption is an execution failure, not evidence that the small model cannot code. These vendor experiments identify confounders; they do not supply the right worker count or resource multiplier for a developer's Mac.

### 9. OpenAI's SWE-bench Verified audit: inspect the grader before trusting the leaderboard

OpenAI's February 2026 [Verified audit](https://openai.com/index/why-we-no-longer-evaluate-swe-bench-verified/) inspected 138 difficult problems selected from 500 and reported material test/description problems in 59.4% of that audited subset. It also found evidence of training contamination in the models tested. **59.4% is not an estimate from a random sample of all tasks.** Some tests required implementation details absent from the task; others tested additional unspecified behavior.

**Relay adaptation:** use recent, operator-owned tasks with independently reviewed acceptance criteria for routing decisions. Audit suspicious failures, tolerate functionally equivalent implementations, and withhold evaluation-only cases from router tuning. Public benchmark rank is background evidence, not a calibrated probability that a specific model/effort will deliver an accepted Wanigan change.

### 10. Anthropic's evaluation guide: check outcomes, repeated reliability and isolation

The January 2026 [agent-evaluation guide](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents) separates tasks, trials, trajectories and final environment outcomes. It distinguishes success at least once across attempts from consistent success across repeated trials, and warns that shared state can both inflate performance and create correlated failures.

**Relay adaptation:** retain the final checkout and recorded human decision as the outcome; use the transcript to diagnose it. A self-reported success, a screenshot fixture, or one lucky successful attempt is insufficient. Run independent repeated trials with fresh mutable state, record all attempts, and combine deterministic checks with human review of professional quality. A model grader can help triage; it must not become the sole authority for the acceptance label.

## Ranked implementation opportunities

The ranking combines the concrete trial failures with the references above. It is an implementation proposal, not a new requirement to run models or a claim of current coverage. Follow `AGENTS.md`: convert an unconverted feature into its required/optional extension first, in a behavior-preserving commit, then change it.

| --- | --- | --- |
| 1 — launch correctness | Represent launching, waiting for a usable input state, submission and confirmed task activity separately. Use the declared protocol where available; an interactive adapter must inspect the current terminal state, refuse unknown menus and time out visibly. Never use stale scrollback as permission to press Enter. | Replay welcome → update/auth/trust dialog, repaint, delayed readiness and early exit. Assert no task text/Enter reaches a dialog; exactly one submission reaches a valid ready state; failed launches remain recorded. |
| 2 — unified spend authorization | Carry cost coverage and retained attempt totals through every new-session and in-session prompt boundary. Preserve the existing distinction between no session yet and a launched but unmetered session. Recheck immediately before dispatch or submission. |
| 3 — workspace retention | Lease the checkout to the unfinished task/review/delivery lifecycle rather than only the current session. Cleanup consults live references even if Git says the checkout is clean. Recovery identifies the original branch/base/checkpoint before restoring anything. | Exit a pristine implementation session, retry, and verify the same owned path/branch remains usable. | 4 — dependency isolation | For work allowed to install/build, require private mutable dependencies. Reuse existing APFS cloning or private setup; make fallback-to-shared a refused isolation requirement rather than a surprise downgrade. | 6 — recoverable attempts | Persist a launch/repair operation ID, receipt, checkpoint reference and workspace lease. | 7 — smaller handoffs and typed retries | Extend the existing goal capsule with prior attempt/checkpoint IDs, changed-file summary, failing checks, retained decisions, and next action. | 8 — throughput scheduling | Bound workers by independent writable resources, machine capacity and review capacity. Prefer one writer per checkout and a separate deterministic gate slot. Reserve parallel agents for disjoint work with a concrete integration owner. | Two tasks cannot concurrently install through the same mutable dependency target or write the same claimed checkout. The dependency-isolation priority is particularly inexpensive to start because the private-clone mechanism already exists. A resource lock alone can prevent simultaneous mutation but cannot make a shared installation independent; it is not a substitute for isolation.

For context efficiency, first measure injected bytes/tokens, tool-result sizes, cumulative input versus included cached input, repeated reads, time waiting for commands, and model turns with no new artifact or useful observation. Use paths and bounded evidence excerpts so the next agent can fetch missing detail. Do not suppress repository instructions or required checks to reduce token counts. Any semantic compaction must respect the repository's backend consent and content-routing rules.

## Retry and effort choices: optimize the whole policy

Treat `(provider profile, harness version, model, legal effort, context policy)` as the candidate, not a model label alone. Keep task scope fixed. The current JEV confidence is not an observed acceptance probability, and low dollar price per token does not establish low total cost.

A useful *illustrative model*, not a fitted Relay result, is a cheap attempt followed by one stronger attempt only on failure:

```text
expected cost = initial attempt cost
              + P(initial failure) × E(fallback cost | initial failure)

acceptance probability = P(initial acceptance)
                       + P(initial failure) × P(fallback acceptance | initial failure)
```

Include verification, routing, handoff, review and integration costs in the relevant terms. The fallback sees selected hard cases and possibly a partial patch; its conditional acceptance rate is not its general benchmark score. Attempt outcomes are not assumed independent. In production use the measured whole-policy ratio, not this sketch with invented probabilities.

Keep separate retry allowances for transient infrastructure recovery and code repair, within one total task allowance. Backoff does not repair incorrect code; a larger reasoning model does not repair a missing checkout. No fixed “always low effort first” or “always escalate after one failure” rule is justified by the sources. The deterministic failure class should narrow the choices before a paid judgment is considered.

## Evaluation design for accepted work per dollar and per hour

This is a proposed authorized pilot, not a claim that an evaluation has run.

1. **Define the denominator before launch.** Choose a finite cohort of real small edits, bug fixes, integration changes and higher-risk tasks. Freeze each task's starting commit, requirements and acceptance rubric. Keep these strata separate so splitting one task into many trivial tasks cannot inflate throughput. Include all scheduled tasks, including eventual failures and withdrawals, under a predeclared accounting rule.
2. **Start with reliability tests that cost no model tokens.** Reproduce the launch, retention, dependency and crash cases above against production code and controlled process boundaries. Then use deliberately authorized integration probes for actual harness behavior. Do not claim a mocked process proves native startup or billing.
3. **Compare policies with minimal confounding.** Use paired tasks, randomized execution order and independent mutable environments. Hold harness version, toolchain, required gates, acceptance review and resource limits fixed unless that variable is under test. Record dependency-cache and provider-cache conditions; do not allow one run's edits, handoff or evaluator feedback into another's independent baseline. Start with fixed model/effort routes and one candidate retry/context policy before testing a complex router.
4. **Use repeated trials and honest uncertainty.** Report first-attempt acceptance and whole-policy acceptance under the declared retry allowance. Repeats measure reliability; they are not extra free opportunities hidden inside a score. Preserve correlated task groupings when estimating uncertainty. A small pilot finds failure modes and estimates variability; it cannot establish small percentage improvements reliably.
5. **Grade behavior and maintenance.** Verify requested behavior, retained existing behavior, public-interface compatibility, meaningful UI interaction when relevant, and current checkout identity. Human review checks clarity, maintainability, scope and product usefulness. Audit invalid tests rather than repeatedly paying an agent to satisfy an unstated implementation detail. Keep test/graded-outcome access consistent across policies.
6. **Measure the full workflow.** Retain every routing, planning, implementation, repair and optional-review attempt; actual model/effort; native usage; elapsed time; command time; human intervention; failure class; and final decision. Report startup/environment failures separately while keeping their cost and time in the end-to-end totals. Track later reopenings/regressions under a fixed observation window; first approval is not proof of lasting quality.

For a fixed, fully cost-observed cohort:

```text
cost per accepted task = total spend on every cohort task and every attempt
                       / number of tasks finally accepted

accepted throughput = finally accepted tasks / elapsed observation time
operator productivity = finally accepted tasks / measured operator time
```

Specify the spend basis: provider dollars; separately measured execution costs where available; estimates with their rate/version; and unpriced consumption. Do not merge unpriced sessions into zero-dollar totals or drop failed tasks from the numerator. If acceptance count is zero, the ratio is undefined. If cost coverage is incomplete, a reported-spend ratio is only a partial accounting view, not the total-cost objective. Show token/latency/operator measures alongside it; cached input is already included in the cited native input counters and must not be added a second time.

Use a predeclared quality floor and monitor regressions while comparing cost and time. Human review waiting, integration and infrastructure repair belong in end-to-end latency; show active execution time separately to locate the bottleneck. Extra concurrency may improve one metric and worsen another. Promote a policy only when the paired evidence supports the intended tradeoff, with uncertainty visible.

The three existing trials are valuable integration evidence, but their native coding sessions are unpriced and their final human decisions were not fabricated. They do not yet supply a measured dollar cost per accepted result, a calibrated effort policy, or a causal savings estimate.

## Addendum: OpenRouter, hosted open weights and local models

Inspected 2026-09-19. **Recommendation:** qualify a small set of backend/model combinations through an existing harness first; add a proper OpenCode runtime extension when broader open-weight support is required. “OpenAI-compatible” and “available in a catalog” are insufficient eligibility tests. This is an integration design, not evidence that these routes run inside Relay today. Pricing API research is in [the open-model economics report](2026-09-19-relay-open-model-economics.md).

### What Relay can already reuse, and what blocks expansion

- [`providers.ts`](../../src/main/providers.ts) separates harness, backend, profile fingerprint, launch arguments and capabilities; GLM/DeepSeek already reuse the Claude harness with different backends. `effectiveProviderBackendId:371–374` namespaces local backend identities by pack. Preserve that privacy boundary.
- [`relay.ts`](../../src/main/relay.ts), `profileFor:174–212`, selects model/effort candidates **inside one selected profile**, intersecting declared choices with its catalog. Cross-profile cheapest-route search is additional policy, not something a larger catalog automatically supplies.
- **Confirmed local catalog defect:** [`launch-choices.ts`](../../src/main/launch-choices.ts):160–167 compares the effective backend ID against raw `profile.backend.id`. [`provider-packs.ts`](../../src/main/provider-packs.ts):1419 and 1708 retain that raw ID. Consequently, a normal local pack's declared live catalog is not selected through `providerModelCatalogue`; static choices may conceal the gap. An offline probe of the actual transpiled module, with registry/dependency stubs and no network call, produced `rawBackendReader: "function", effectiveLocalBackendReader: "undefined"`. Reproduction: `/private/tmp/wanigan-local-catalogue-probe.cjs`, Node 22.23.2. This is a controlled module reproduction, not a live pack/UI test.
- [`backend-catalog.ts`](../../src/shared/backend-catalog.ts):25–40 returns model ID, label and source; the declared-catalog mapper in `launch-choices.ts:187` supplies no per-model effort metadata. Tool support, context capacity and supported reasoning parameters need their own validated capability evidence. A route must not inherit every harness effort merely because its catalog supplies no narrower range.
- Pack v1 accepts only Claude, Codex and generic CLI harnesses; generic CLI is explicitly `headless: none` (`provider-packs.ts:649–713`). Adapter v1 proves bounded capabilities; it cannot translate a new runtime. [`headless.ts`](../../src/main/headless.ts):306–363 has only Claude/Codex JSON launchers, and 620–655 refuses unproven protocols. An Aider/OpenCode terminal pack alone is not full unattended Relay support.

### Minimum integration contract

1. **Qualify routes before optimizing them.** Start with explicit model IDs and a small approved provider set. For a narrow existing-harness pilot, prove credentials, endpoint and native events without claiming support for the entire aggregator catalog. For broad open weights, add OpenCode through a versioned execution extension covering start, events, cancellation, usage, exact continuation and required verification. Keep catalog, execution and routing policy separate. Existing unconverted surfaces must follow the repository's conversion rule before behavior changes.
2. **Make inference identity explicit.** Freeze profile/pack digest, harness version, intended model/effort, endpoint, account and privacy policy. Separately record reported model, serving provider, request/generation IDs and effective effort when observable. A publisher prefix such as `openai/` is not proof that OpenAI directly processed the request; `backendId` remains an opaque privacy identity, with gateway/processor lineage as additional evidence. Record unavailable identity as unknown. Pin local model digest, quantization, server/context settings and hardware for comparisons. Existing `backendCostBasis` deliberately marks unknown backends unverified; retain that honesty until actual accounting is integrated.
3. **Authorize the backend hop before sending context.** An OpenRouter route can involve both the gateway and another processor. Use an approved provider allowlist, constrained fallback behavior, required-parameter handling and the user's data policy. OpenRouter documents `only`, `allow_fallbacks`, `require_parameters`, `data_collection` and `zdr`; availability and strength vary by selected endpoint, so verify the controls actually reach the gateway. If the harness cannot enforce the agreed policy, refuse that automatic route. These are provider-declared policies, not a local proof of retention behavior. [Provider-routing contract](https://openrouter.ai/docs/guides/routing/provider-selection).
4. **Preserve same-backend semantic learning.** [`learning-service.ts`](../../src/main/learning-service.ts):1560–1578 already rejects cross-backend semantic projections. An aggregator must not let a changed downstream processor inherit private semantic content merely because the gateway hostname stayed constant. Fingerprint the permitted processing route and invalidate eligibility when it changes. Operational success/latency counts can cross providers; task context and semantic memory need their existing content/consent rules. [`egress.ts`](../../src/main/egress.ts):95–117 correctly distinguishes declared pack endpoints from observed traffic. A loopback inference URL alone must not earn a “local-only” label: server cloud forwarding and agent tool networking are separate facts.

### Acceptance tests before automatic routing

Use offline event fixtures and a local fake endpoint first. Then obtain explicit authorization for a tiny real compatibility task on each intended route; no such provider tests were run in this research.

- Confirm the exact endpoint and credential destination, absent ambient-account fallback, correct wire protocol, and frozen route metadata. Keep runtime configuration under Wanigan user data. Include a negative cross-backend semantic-memory test.
- Require a tool-call/result round trip, a real file edit, deterministic passing/failing verification, cancellation, interrupted-stream recovery and exact continuation of the same retained checkout. Process exit and a successful greeting do not establish coding capability.
- Test every offered effort, unsupported-parameter refusal and effective context limit. Exercise missing usage, duplicated final usage, partial streaming failure, retries and subordinate calls; unknown dollars remain unknown and authorization applies before each paid continuation.
- Test gateway-provider failure without an unauthorized fallback, then verify actual processor/model attribution where available. For local routes, test insufficient context/memory and distinguish inference locality from unrestricted tool egress.
- Compare the qualified routes on the same held-out task cohort and final acceptance process described above. Include model loading, environment preparation, retries and human repair. Hosted open weights and local inference are candidates for a better tradeoff; this research establishes no causal savings or universal quality ordering.
