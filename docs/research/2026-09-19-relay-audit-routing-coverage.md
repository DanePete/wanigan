# Relay routing audit: coverage and next-session cases

Audited source: `324bca7f137198a78583ec9b8cb07cfd1c667c71`, 2026-09-19. This is a source-and-test inventory and an execution plan, not a new test result. No hosted requests, credential changes, installs or application-source edits were made for this memo. The next session has one **$50 total API allowance**, including JEV, failed attempts, repairs and paid review. The allowance is shared across the whole audit, not repeated per agent, task or provider.

The current implementation has substantial evidence for **admissible routing and honest accounting**. It does not yet demonstrate the cheapest accepted coding result. JEV receives a cost-oriented instruction plus bounded model descriptions; the independent price explorer ranks an explicit sample workload. Neither is a learned predictor of accepted-result cost, and the price explorer is not wired into Relay's model selection. ## Highest-value unanswered questions

1. **Does routing improve the outcome for the money?** “Lower cost” currently changes JEV's objective, not a measured optimizer. Hypothesis: a cheap first model may lose after retries, while conservative low-confidence fallback may spend more than necessary. Compare complete attempts before changing thresholds or calling a route cheapest.
2. **What can this exact account actually use?** The current stage candidate/profile path does not combine remaining subscription quota, rate-limit windows, account-specific model access or pending reservations into route eligibility. Account pins and token usage are not remaining allowance. The parent audit should add a dated capability/access/quota inventory, including MCP readiness and evidence sources, before presenting an intelligently available route. Do not infer quota from accumulated tokens. [Candidate path](../../src/main/relay.ts#L176), [account resolution](../../src/main/accounts.ts), [Codex usage shape](../../src/main/codex-usage.ts#L10).
3. **Can a live OpenRouter coding turn be attributed and bounded?** A working response is only the first hurdle. Model, upstream, tools, every request and billed cost need matching identities. Current direct CLI wiring supplies no such billing integration and remains ineligible for automatic work even if a manual experiment succeeds.
4. **Are confidence and fallback stable across tasks and changing service versions?** The requested alias is `jev-latest`, with the actual returned version recorded when available. A small $50 pilot can expose severe defects and route instability; it cannot calibrate a general 0.8 success threshold. [Policy/model identity](../../src/shared/suggest-questions.ts#L306).
5. **Do asynchronous changes invalidate stale authority everywhere?** Receipts, profile availability, automatic permissions and budget evidence now have explicit guards. Test their actual orchestration boundaries, including failures and retry, instead of only hashing two fixed inputs.

## Twelve concrete next-session cases

### R01 — Three confidence gates, independently (offline, first)

Feed model/selected-effort/pipeline answers independently at `0.79`, `0.8`, `0.81`, null, NaN, strings and out-of-range values; include a confident answer for the *unselected* model and a high deliberation score. Also remove the chosen/default model between candidate snapshots.

Pass: only legal model/effort pairs survive; weak effort leaves that selected model's legal default; weak model uses the profile fallback; weak pipeline keeps stages; mandatory stages survive every answer; no sequential inference is purchased. Record source, fallback reason and full selected-effort evidence. Extend the existing [pure boundary matrix](../../src/shared/suggest-questions.test.ts#L235), then one [transport fixture](../../src/main/smoke-suggest.ts#L163). Do not force a live confidence value and call it natural model behavior.

### R02 — Manual choices and paid-call count (offline, then minimal live)

With both JEV capabilities enabled, preview/create Manual with model-only, effort-only, both, account inheritance and explicit-null account. Repeat Auto cost/balanced/quality; use an unchanged receipt to create. Toggle automatic progress after preview so its different question set must invalidate the old receipt. Distinguish model selection Auto from automatic stage progress.

Pass: Manual sends no JEV request; each Auto preview sends at most one batch; unchanged create sends none; invalid overrides refuse before inference/write; exact node route/account matches proof and actual launch. Include deterministic verification having no agent route in automatic-progress mode. Existing anchors: [routing smoke](../../src/main/smoke-relay.ts#L324), [request exclusion](../../src/main/relay.ts#L303), [composer](../../src/renderer/src/relay/RelayComposer.tsx).

### R03 — Receipts under mutations and races (offline)

Repeat after preview but before create. Test two simultaneous creates, exactly 15-minute expiry, 33-preview eviction and app restart.

Pass: changed or absent authority refuses without a second paid request or partial docket; one unchanged receipt creates exactly one docket; renderer-edited model/usage cannot replace the stored decision. ### R04 — Hostile content cannot widen authority (offline)

Pass: automatic request construction contains only the intended bounded intent and allowed candidate metadata; no planted repository/output canary appears; model/effort sets and mandatory stages cannot widen. ### R06 — Catalog transport, freshness and restart (offline, public GET optional)

### R07 — Current live JEV protocol (small paid conformance batch)

### R08 — Real OpenRouter tool round trip (paid, manual only)

Through the actual OpenRouter profile, ask Codex to inspect a file, change it, run the test and explain the result; then send one follow-up referencing its observed output. Require physical diff/test evidence, not text claiming tools ran. Keep update/trust/auth menus and CLI version in the run record.

Pass: the real CLI sends the initial prompt once, completes a genuine tool-result continuation, edits only the intended fixture and reports observed failures honestly. Record any rejected Responses parameter, unsupported tool schema, lost tool-call ID or effort incompatibility. ### R09 — OpenRouter costs and upstream identity (paid only after admission)

### R11 — Small accepted-result pilot (paid, last)

Only after tool/access/cost prerequisites, predeclare two useful bounded tasks and their acceptance tests: one mechanical change and one interaction/error-path change. Start each arm from the same base revision and private dependencies. Compare at most three exact model/effort routes: a fixed manual baseline, the frozen JEV cost choice and one more capable route. If two select the same route, do not purchase a duplicate merely to fill the table.

Keep pipeline policy, harness/account conditions, task text, tools/MCP, tests, retry ceiling and review rubric fixed; record unavoidable cache/quota differences. Rotate run order and have the reviewer inspect patches without price/model labels where practical. Count all paid attempts, JEV and paid review toward the shared allowance. Report accepted fraction, total observed API cost per accepted result, time to accepted result and human review/repair minutes. Unpriced attempts remain visible but cannot win a dollar ranking; zero accepted results have no finite cost-per-accepted-result score. This is a descriptive pilot, not proof of global optimality or calibrated success probabilities. [Attempt accounting](../../src/main/control-outcomes.ts#L13), [mixed/unknown evidence tests](../../src/main/smoke-control-outcomes.ts#L61).

Test missing versus explicit-zero cost, duplicate completion ticks, stale passed checkout, and transient completion rejection followed by retry with the same evidence after the throttle. Try the OpenRouter profile through both Relay and ordinary Control autopilot, including stage overrides.

Pass: no new paid action after authority changes or with unknown prior spend; generic/manual-only routes refuse before spawn; deterministic verification can finish without purchasing a verification model; stale tests cannot authorize completion; retry ceilings hold; final human acceptance/commit/deploy remain explicit. ## Spend and reporting handoff

Run R01–R06 and R10/R12's offline parts first. Then R07, one R08/R09 conformance pair, and only then R11. The root plan should reserve per-run money from the single $50 pool and reconcile between launches; no agent receives its own $50 allowance. Do not treat Relay's pre-turn budget check as a hard provider billing cap: a running turn can exceed it, and JEV is separately metered. Confirm how the chosen account can bound the experiment before spending; stop further launches when attributable remaining funds cannot be established. [Budget semantics](../../src/shared/automatic-spend.ts), [UI disclosure](../../src/renderer/src/relay/RelayComposer.tsx).

For each case retain: exact app/CLI revision, synthetic task hash and fixture commit, provider/profile fingerprint, account identifier without credentials, requested versus observed model/effort, routing settings/policy/JEV version, receipt ID, price snapshot IDs, request/session/attempt IDs, cost provenance and coverage, timestamps, tests/current-tree proof, human decision and failures. Keep raw secrets and unrelated conversations out of artifacts. Preserve failed attempts instead of restarting history to make a route look cheaper.

The next decision should be whether these observations justify a specific policy change or one missing integration. A valid final result may be “this route works manually but cannot yet be compared in dollars,” “JEV legally falls back but offers no measured advantage on these tasks,” or “account quota/MCP availability prevents the proposed route.” Those are actionable findings; a fabricated cheapest-model leaderboard is not.
