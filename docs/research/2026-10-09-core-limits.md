# Core Already Removes Most of Wanigan's Refusals

Most of what Wanigan 2's live view and design layer tells an owner it cannot do on a Drupal or WordPress site is a choice the site helper made, not a limit of core. Of 39 limitations checked against Drupal core 11.4.8 and WordPress core 7.1.3 on disk, **12 are possible through core as shipped, 14 are possible under conditions the helper must check, 8 split into a part that works and a part that never will, and only 5 are genuinely impossible**. On Drupal, formatted text, translations, the true field item, revision ids, configuration words, content menu links, Layout Builder inline blocks and image alt text all have core save paths. On WordPress, core already contains the exact rich-text splice the helper refuses to attempt (`WP_Block::replace_html()`), plus REST write paths for templates, synced-pattern overrides, navigation labels, any `WP_Widget`, attachment alt text and global styles. WordPress 7.0 and 7.1 also moved the style line: per-instance custom CSS, hover and focus on buttons and navigation links, and native mobile and tablet breakpoints are stored as data with revisions, which makes the layer's "a token is a code change" and "phase 1 reads no breakpoints" wrong for block themes. What core genuinely cannot do is narrow and has one cause: the thing is code, or core deliberately stores nothing — literal Twig and PHP template text, a static WordPress block's settings that only its JavaScript `save()` writes, a stable WordPress block id, per-language WordPress content, a Drupal component placed without code, Drupal per-instance style outside three small homes, and any "page as it was" for configuration and code. Defects in the current Drupal save route matter more than any new feature — four of its seven are unsafe, because it ignores content-moderation violations, saves over pending drafts, reports an inline-block edit as saved when nothing displays it, and cannot see a concurrent edit — and the design layer cannot save a single WordPress word today because it calls a route the WordPress helper refuses. Nothing here was run against a site; every verdict was read from source or an official page and needs a fixture test on the Northstar and Fieldnotes demos before the app claims it.

## 39 limitations checked; five survive whole

This report checks the places where Wanigan 2 currently says something cannot be done on a site: the design layer's `implement()` refusals (`src/main/live-layer.ts:430-464`), the Drupal helper's word save (`src/core/live-helper-drupal.ts:445-493`), the WordPress helper's edit-target reasons (`src/core/live-helper-wordpress.ts:1702-2333`), the "not built" list (`docs/design/2026-10-08-live-view.md:29-31`), the design router and phases (`docs/design/2026-10-09-design-layer.md`, "The router" and "Phases"), and the README's library note (`README.md:198`). Each was checked against core as it sits in the two made-up demo sites, **Northstar** on Drupal and **Fieldnotes** on WordPress, and against official documentation and change records. Core only: a contributed module or plugin never counts as a way to do something, and the helper is allowed only what any site running plain core would offer it.

Path conventions are fixed throughout. Drupal paths are relative to Northstar's `web/core/` (`VERSION = '11.4.8'` at `lib/Drupal.php:79`), and Twig paths start `vendor/`. WordPress paths are relative to the Fieldnotes root (`$wp_version = '7.1.3'` at `wp-includes/version.php:19`). Wanigan paths start `src/`, `docs/` or `README.md` and are relative to the beta5 worktree; the helpers' PHP lives as strings inside `src/core/live-helper-*.ts`, so their line numbers are TypeScript lines. Doc links the researchers did not open in this pass are marked *(unread)*. The three verdicts are used strictly: **possible through core** means core ships the API and the helper only has to call it; **possible with conditions** means core ships it but the helper must enforce a rule, ask the owner, or accept a stated cost; **genuinely impossible through core** means no core API reaches it, and only code, a contrib module or a site change could.

## Drupal content: only what lives in code survives a check against core

### Formatted text is a splice and a render comparison away

**Verdict: possible with conditions.** Core stores a `text*` item raw, as `value` plus a `format` id, and computes `processed` only at render (`modules/text/src/Plugin/Field/FieldType/TextItemBase.php:77-95`); every filter runs in `ProcessedText::preRenderText()` when the text is shown (`modules/filter/src/Element/ProcessedText.php:82-127`). Entity validation checks only that the logged-in user may use the stored format, through `AllowedValues` on the `filter_format` data type (`lib/Drupal/Core/TypedData/TypedDataManager.php:283-284`; `modules/filter/src/Plugin/DataType/FilterFormat.php:20-66`; the current user is passed at `lib/Drupal/Core/Validation/Plugin/Validation/Constraint/AllowedValuesConstraintValidator.php:50-54`). Nothing on the field validates markup against allowed HTML or CKEditor 5: the CKEditor 5 constraints attach to editor configuration, not content (`modules/ckeditor5/config/schema/ckeditor5.schema.yml:95-107`). So **changing one run of words inside one stored text node cannot introduce markup**, and the helper's refusal at `src/core/live-helper-drupal.ts:465` is stricter than core. The helper would mark the property (`value` or `summary`) and the true delta at render, treat the value as literal text when the format has `filter_html_escape` (`modules/filter/src/Plugin/Filter/FilterHtmlEscape.php:26-27`), and otherwise `Html::load()` it (`lib/Drupal/Component/Utility/Html.php:266-290`) and require the normalised `before` to occur exactly once inside a single text node, refusing words that span inline markup. It prefers a byte splice of `Html::escape(after)` (`Html.php:433`) where the escaped `before` is unique in the raw string, and re-serialises with `Html::serialize()` only when `Html::normalize(stored) === stored` (`Html.php:261-264`), since otherwise re-serialising would rewrite markup elsewhere. The decisive guard is to render old and new through the same format and langcode as a `processed_text` element — `check_markup()` is deprecated in 11.4.0 ([change record](https://www.drupal.org/node/3588040)) — and confirm the visible text differs only by `before`→`after`, once. That one comparison catches autop turning a typed newline into `<br>`, a restrictor dropping something, and any non-core filter.

The helper must still refuse words that filters **generate** rather than store: captions that live in a `data-caption` attribute (`modules/filter/src/Plugin/Filter/FilterCaption.php:65-134`), words inside `<drupal-media>`, which belong to the media entity (`modules/media/src/Plugin/Filter/MediaEmbed.php:230-237`), link text shortened by `filter_url` (`modules/filter/src/Plugin/Filter/FilterUrl.php:232-276`), core's "Image removed." alt (`modules/filter/src/Hook/FilterHooks.php:78-79`) and the cut point of a trimmed summary (`modules/text/src/Plugin/Field/FieldFormatter/TextTrimmedFormatter.php:72-93`). Inline-image file usage follows any Entity API save on its own (`modules/editor/src/Hook/EditorHooks.php:195-275`). Unverified: how entity spellings such as `&nbsp;`, numeric references and `\r\n` behave in the splice, which needs fixture tests; what CKEditor 5's client-side normalisation does the next time someone opens a non-canonical document; and whether a contributed markup filter keeps a text run 1:1 with storage, which only the render comparison would catch.

### Translations and the true item are already on the render array

**Verdict: possible through core.** The page renders a negotiated translation, which can be a **fallback** different from the page language: `EntityViewBuilder::viewMultiple()` calls `getTranslationFromContext()` (`lib/Drupal/Core/Entity/EntityViewBuilder.php:160-166`), which walks fallback candidates down to the default (`lib/Drupal/Core/Entity/EntityRepository.php:94-124`). The field element already carries that translation as `#object` and its langcode as `#language` (`lib/Drupal/Core/Field/FormatterBase.php:121-128`), but the helper's `data-wl-field` mark records neither (`src/core/live-helper-drupal.ts:259-276`) and the save loads the default translation (`:456`). The helper would add the rendered langcode to the mark, refuse when `!hasTranslation($langcode)` because the words then belong to another language (creating a translation with `addTranslation()` is a separate action to offer explicitly), and edit `getTranslation($langcode)` (`lib/Drupal/Core/Entity/ContentEntityBase.php:893`). Core's own `EntityUntranslatableFields` constraint forbids changing untranslatable fields from a non-default translation or in a pending revision (`lib/Drupal/Core/Entity/Plugin/Validation/Constraint/EntityUntranslatableFieldsConstraintValidator.php:50-85`; change records for [8.5](https://www.drupal.org/node/2938191) and [8.6](https://www.drupal.org/node/2975280)), so those refusals come from core and should be mapped to a 409 that says "change it in the original language". A non-default translation also needs `ContentTranslationHandler::getTranslationAccess()` (`modules/content_translation/src/ContentTranslationHandler.php:251-263`). Configuration text shown in a non-source language lives in a `LanguageConfigOverride` (`modules/language/src/Config/LanguageConfigFactoryOverride.php:77`), not in the base config, which `getEditable()` returns without overrides (`lib/Drupal/Core/Config/ConfigFactory.php:81`, `:103-114`); writing it needs "translate configuration".

The "first item whose words match" rule (`src/core/live-helper-drupal.ts:467-476`) is replaceable the same way. Rendered positions are not stored deltas: `FieldPreprocess::preprocessField()` renumbers render children from 0, and reference formatters drop items the viewer cannot access. Core's own comment names the sanctioned fix — modules add `$item->_attributes` in `hook_entity_prepare_view()` and `field.html.twig` prints them on each item (`lib/Drupal/Core/Field/FieldPreprocess.php:58-79`). The helper stamps `data-wl-delta` there and saves `$field->get($delta)` only if its words still equal `before`. The risk is cache: `hook_entity_prepare_view()` runs only on a render-cache miss, and although the helper already varies entity and block renders on its `X-Wanigan-Live` header, nobody has confirmed that every field render under the live view is a miss. Also unverified: a cheap per-value test for whether a config string on the page came from an override.

### Revision ids, drafts and concurrent edits: carry what the page showed

**Verdict: returning the revision id is possible through core; choosing the right revision and detecting a concurrent edit are possible with conditions.** The id is on the object after save, because SQL storage writes the revision key back and `doPostSave()` updates the loaded revision id (`lib/Drupal/Core/Entity/Sql/SqlContentEntityStorage.php:967-970`; `lib/Drupal/Core/Entity/ContentEntityStorageBase.php:920-924`) — one line, and the design layer already reads `saved.revision` (`src/main/live-layer.ts:464`) that the Drupal helper never sends (`src/core/live-helper-drupal.ts:493`). Which revision to edit is the harder problem. The canonical page shows the **default** revision, while content moderation makes every moderated edit route load the **latest** (`modules/content_moderation/src/Routing/ContentModerationRouteSubscriber.php:57-79`), and a moderated save becomes the new default only for a default-revision target state (`modules/content_moderation/src/EntityOperations.php:105-127`), validated against a per-transition permission `use {workflow} transition {transition}` (`modules/content_moderation/src/Plugin/Validation/Constraint/ModerationStateConstraintValidator.php:82-130`; `modules/content_moderation/src/StateTransitionValidation.php:57`). Visitors keep seeing the published version while a draft sits in "Latest version" ([Content Moderation overview](https://www.drupal.org/docs/8/core/modules/content-moderation/overview)), and core's own guidance is that "the active variant should always be retrieved when editing", with the caller responsible for access ([EntityRepositoryInterface::getActive](https://api.drupal.org/api/drupal/core%21lib%21Drupal%21Core%21Entity%21EntityRepositoryInterface.php/function/EntityRepositoryInterface%3A%3AgetActive/11.x)).

The helper would carry the shown revision id on the page and follow one decision table. When the page shows default revision R and R is also the latest translation-affected revision, it edits R as a new revision and sets `moderation_state` explicitly: keeping `published` needs the publish transition and changes the live page at once, while `draft` creates a pending revision and leaves the live page alone, and the owner is told which. When a newer draft D exists, it refuses, or — only if `before` is found in the same item of D — edits D and keeps it a draft; it never saves over D from R, which would publish a version without D's changes and strand D. On `/latest` it edits D in its own state. For concurrency, core forms rely on `EntityChanged`, which compares the stored default revision's `changed` per translation with the object being saved (`lib/Drupal/Core/Entity/Plugin/Validation/Constraint/EntityChangedConstraintValidator.php:16-41`), and `NodeForm` posts `changed` as a hidden field for exactly this (`modules/node/src/Form/NodeForm.php:133-137`). A fresh load at save time can never trip it. The helper's 409 rules, in order, are: shown revision ≠ `getLatestTranslationAffectedRevisionId($id, $langcode)` (`ContentEntityStorageBase.php:509`), which catches drafts that `EntityChanged` misses; for non-revisionable types, page `changed` ≠ stored (one-second resolution, `lib/Drupal/Core/Field/Plugin/Field/FieldType/ChangedItem.php:44-66`); words ≠ `before`; any `EntityChanged` violation. Core has no compare-and-swap, so a race between `validate()` and `save()` remains exactly as it does for core's forms. Not traced: behaviour with Workspaces and Content Moderation both on, since Workspaces forces non-default revisions in a non-live workspace (`modules/workspaces/src/Hook/EntityOperations.php:217-221`).

### Configuration words save through the Config API, with two duties core leaves to the caller

**Verdict: possible with conditions.** A block label persists through `getPlugin()->setConfigurationValue('label', …)` and `save()`, because the plugin collection is copied back on `preSave()` (`modules/block/src/Entity/Block.php:173-178`; `lib/Drupal/Core/Config/Entity/ConfigEntityBase.php:302-311`), behind `administer blocks` (`Block.php:52`). Site name and slogan are `label` values in `system.site` behind "administer site configuration" (`modules/system/config/schema/system.schema.yml:3-21`; `modules/system/system.routing.yml:16`). A Views header, footer or empty text is reached through `View::getDisplay()` (`modules/views/src/Entity/View.php:231`), written to the display that owns the option according to `isDefaulted()` (`modules/views/src/Plugin/views/display/DisplayPluginBase.php:776`), and the `text` area is formatted text again (`modules/views/src/Plugin/views/area/Text.php:54`, `:76-81`), so the previous section's rules apply. Field labels use `FieldConfigBase::setLabel()` (`lib/Drupal/Core/Field/FieldConfigBase.php:332`), and a base field's label per bundle uses `BaseFieldOverride::createFromBaseFieldDefinition()` (`lib/Drupal/Core/Field/Entity/BaseFieldOverride.php:77`). Content menu link titles are plain, translatable, revisionable `string` fields (`modules/menu_link_content/src/Entity/MenuLinkContent.php:303-307`), so the existing plain-text save applies once they carry a field mark; YAML-defined links take their title from code and cannot store one (`lib/Drupal/Core/Menu/MenuLinkDefault.php:16-22`, `:52-54`), which leaves only interface translation.

The two duties are validation and permission. `Config::save()` casts to schema but runs no constraints (`lib/Drupal/Core/Config/Config.php:201-225`), so the helper validates explicitly with `config.typed`'s `createFromNameAndData()->validate()` (`lib/Drupal/Core/Config/TypedConfigManager.php:428`) or a config-entity typed-data adapter; only types marked `FullyValidatable` get strict validation ([change record](https://www.drupal.org/node/3404425)), and `system.site` and `views.view.*` are not, so the form-only rules — site name required, slogan at most 255 characters (`modules/system/src/Form/SiteInformationForm.php:83-94`) — must be copied. Config objects have no access handler, so the helper checks the admin permission the form route needs. Every success message should also say that this is configuration and will be lost on the next config import unless exported; that follows from how config sync is used, and `ConfigImporter` itself was not examined. Views words that came from tokens or replacement patterns are refused, and the Views UI's own tempstore lock (`modules/views_ui/src/ViewUI.php:890-919`) must refuse a save too. Unverified: which Views area plugins beyond `text` and `text_custom` hold literal words.

### Inline blocks must be saved through their layout, never directly

**Verdict: possible with conditions.** An inline block's words live in a non-reusable `block_content` entity, but the layout component pins one revision of it in `block_revision_id` and renders exactly that one, or the edited copy in `block_serialized` (`modules/layout_builder/src/Plugin/Block/InlineBlock.php:102-107`, `:204-235`). Saving the block directly therefore creates a revision nothing displays. Core's path keeps layout and revisions consistent: put the edited block into `block_serialized`, save the section storage, and let `InlineBlockEntityOperations::handlePreSave()` save a new block revision and update the pin — core's reason is that "since multiple parent entity revisions may reference common block revisions, when a block is modified, it must always result in the creation of a new block revision" (`modules/layout_builder/src/InlineBlockEntityOperations.php:146-170`). The helper resolves the section storage (override or default), refuses while the tempstore has unsaved work (`modules/layout_builder/src/LayoutTempstoreRepository.php:65-75`) or on a non-default translation, where core denies overrides outright (`modules/layout_builder/src/Plugin/SectionStorage/OverridesSectionStorage.php:369-373`), gets the component by UUID (`modules/layout_builder/src/Section.php:194`), confirms its `block_revision_id` equals the rendered revision, applies the word change, writes `block_serialized` through `SectionComponent::setConfiguration()` (`modules/layout_builder/src/SectionComponent.php:202`), and saves the parent as a new revision under the moderation rules above (`OverridesSectionStorage.php:319-321`). On a **default** layout the display is not revisionable, so the text changes for every entity of that bundle without an override; the owner must hear that before saving. Not traced: `block_content` translations inside a layout.

### Images and alt text save like words; replacing a file is core's upload handler

**Verdict: possible with conditions; images printed by a theme or template are genuinely impossible.** Alt and title are plain properties of an image item (`modules/image/src/Plugin/Field/FieldType/ImageItem.php:155-163`), with alt capped at 512 characters (`:110-116`) and `alt_field`/`alt_field_required` defaulting on (`:83-84`). Core enforces "alt required", "is an image" and dimensions **only in the widget** (`modules/image/src/Plugin/Field/FieldWidget/ImageWidget.php:148-152`, `:175`, `:267-271`), so the helper re-applies them before saving. On a media item it also sets `thumbnail.alt`, because `Media::updateThumbnail()` refreshes the thumbnail only when the source field's main property changes, and an alt-only edit leaves it stale (`modules/media/src/Entity/Media.php:178-189`, `:349-367`). A `<drupal-media alt="…">` attribute is a per-embed override (`modules/media/src/Plugin/Filter/MediaEmbed.php:392-431`), so for an embedded image the helper asks whether to change this embed (a formatted-text attribute edit) or the media item everywhere. Replacing the file streams new bytes through `FileUploadHandler::handleFileUpload()` with the field's validators plus `FileIsImage` and `FileImageDimensions` (`modules/file/src/Upload/FileUploadHandler.php:56-85`; `modules/file/src/Upload/InputStreamUploadedFile.php:17-22`), points `target_id` at the new file and saves; `ReferenceAccess` and `FileValidation` run in `validate()` (`modules/file/src/Plugin/Field/FieldType/FileItem.php:37`), and usage and permanence follow the save (`modules/file/src/Plugin/Field/FieldType/FileFieldItemList.php:21-70`; `modules/file/src/FileUsage/FileUsageBase.php:33-36`). A logo, background or placeholder printed by a template has no content home; the one exception is the branding logo's alt, which is the translatable string `{{ 'Home'|t }}` (`modules/system/templates/block--system-branding-block.html.twig:21`). Unverified: where theme-settings logo paths are stored and whether the helper could write them safely, and how `translation_sync` treats an alt-only change on a translation.

### Template text: interface translation reaches `t()` strings, nothing reaches literal Twig

**Verdict: `t()` strings possible with conditions; literal Twig text genuinely impossible.** Words typed literally into a Twig template change only by changing the template file, which is code; core has no stored override for templates, and `locale_custom_strings_<lang>` lives in settings.php, which is code too (`lib/Drupal/Core/StringTranslation/Translator/CustomStrings.php:40`). Words printed through `|t`, `|trans` or `{% trans %}` compile to `t()` (`lib/Drupal/Core/Template/TwigExtension.php:125-126`; `lib/Drupal/Core/Template/TwigNodeTrans.php:66`), and the core `locale` module can change those without code, using the same sequence its edit form uses — `createTranslation()`, `setCustomized()`, `save()`, then refresh (`modules/locale/src/Form/TranslateEditForm.php:207-240`; `modules/locale/src/StringDatabaseStorage.php:57`, `:232`). Core does not record which rendered words came from which string, so the helper would register its own translator service with core's `string_translator` tag at a priority above locale (`lib/Drupal/Core/StringTranslation/TranslationManager.php:66`, `:87`) that records each `(langcode, source, context)` during a traced render and returns `FALSE` so the real translators still answer; it then offers an override only when exactly one recorded string renders the selected words, showing its source, context and how many places use it. The costs are real: the change applies to every use of that string in that language; English is untranslatable unless `locale.settings:translate_english` is on, and it is off by default (`modules/locale/src/LocaleTranslation.php:113-143`; `modules/locale/config/install/locale.settings.yml:2`); enabling `locale` or that flag is a site change the owner must choose, never a side effect; and a fragment served from the render cache never calls `t()`, so the recorder sees only misses. Literal Twig stays what the app already offers: a template copy in the owner's theme, as a reviewed diff.

## WordPress content: core already ships the splice the helper refuses to do

### The layer cannot save a WordPress word today because it calls the wrong route

**Verdict: possible through core.** The design layer makes text real only through `helperSave`, which posts to `/_wanigan/save` (`src/main/live-view.ts:557-562`), and only for an element inside a `data-wl-field` mark (`src/main/live-layer.ts:456`). Only the Drupal helper stamps that mark (`src/core/live-helper-drupal.ts:270`), and the WordPress helper answers that route with a 409, "This WordPress helper saves through /_wanigan/edit" (`src/core/live-helper-wordpress.ts:4925`). So every WordPress word edit in the layer ends in "they come from a template, a setting or formatted text", although the WordPress helper already saves title, excerpt, slug, status, featured image, registered meta and block attributes through the post's REST route with `rest_do_request()` (`:1691-1754`, `:4131-4146`, `:4261-4271`). That route is the editor's own: `WP_REST_Posts_Controller` checks `edit_post` and the extra capabilities for author, sticky and terms, then calls `wp_update_post()` (`wp-includes/rest-api/endpoints/class-wp-rest-posts-controller.php:893-1010`), which runs kses for users without `unfiltered_html` (`wp-includes/kses.php:2606-2613`) ([REST API Posts](https://developer.wordpress.org/rest-api/reference/posts/); [wp_update_post](https://developer.wordpress.org/reference/functions/wp_update_post/)). The fix is routing, not new capability: the layer's text implementation should resolve WordPress targets by the trace's block identity and call `/_wanigan/edit`. Core's REST update has no stale-write check (`class-wp-rest-posts-controller.php:944-1010`), so the helper's content hash and its refusal while any edit lock is live, including the owner's own (`src/core/live-helper-wordpress.ts:1774-1784`), go beyond core and should stay; core's `wp_check_post_lock()` returns false for one's own lock (`wp-admin/includes/post.php:1729-1758`), which is exactly the case where an open editor would later overwrite Wanigan's save.

### Formatted block text and nested blocks: copy `WP_Block::replace_html()`

**Verdict: possible with conditions.** When block bindings render, core itself splices sanitised rich text into a block's element by byte offset. `WP_Block::replace_html()` finds the selector element and calls `replace_rich_text( wp_kses_post( $source_value ), $inner_block_offsets )` (`wp-includes/class-wp-block.php:376-418`, kses at `:411`), using `get_block_bindings_processor()`, an anonymous subclass of `WP_HTML_Processor` built with `CONSTRUCTOR_UNLOCK_CODE` that bookmarks the opener, walks to the matching closer by depth and pushes a text replacement onto the protected `lexical_updates` (`class-wp-block.php:438`, `:456-505`; `wp-includes/html-api/class-wp-html-processor.php:6663`; `wp-includes/html-api/class-wp-html-tag-processor.php:767`, `:815`). Because those members are protected, a subclass is the supported route. Core marks the gap it fills — "TODO: Use `WP_HTML_Processor::set_inner_html()` once it's available" (`class-wp-block.php:403`) — and that API has not shipped ([HTML API progress report](https://make.wordpress.org/core/2024/09/11/progress-report-html-api-3/)). Since 7.1 the splice stops at the first inner block's offset, so a nested list inside a list item is kept (`class-wp-block.php:365-367`, `:482-497`), which removes the "inner blocks" refusal (`src/core/live-helper-wordpress.ts:2053`) as well as the "formatting" refusal (`:2065`, `:2075`). For a text-only change inside one text node, `WP_HTML_Tag_Processor::set_modifiable_text()` replaces and escapes that node (`class-wp-html-tag-processor.php:3965-3981`; [reference](https://developer.wordpress.org/reference/classes/wp_html_tag_processor/set_modifiable_text/); [HTML API in 6.7](https://make.wordpress.org/core/2024/10/17/updates-to-the-html-api-in-6-7/)); the escaped `&apos;` and `&quot;` it writes should still validate, because the editor decodes character references and normalises whitespace before comparing (`wp-includes/js/dist/blocks.js:4628-4672`, `:4798-4830`; [Block Edit and Save](https://developer.wordpress.org/block-editor/reference-guides/block-api/block-edit-save/)).

The helper would find the block, find the sourced attribute's selector element (paragraph `content` is rich text on `p`, heading on `h1`–`h6`, list item on `li`, button `text` on `a,button`, per each `block.json`), splice the new inline HTML between opener and closer up to the first inner block, run the fragment through `wp_kses_post()` and `WP_HTML_Processor::normalize()` so it cannot close its element early, and save through REST. It must kses the fragment itself, as core's renderer does whatever the user's capabilities, because an `unfiltered_html` user's save is not kses'd. The risks are editor validation and parser limits. Nobody has confirmed whether RichText re-serialises `<b>` as `<strong>`, so the inline-tag allowlist should be restricted to the editor's registered formats; `WP_HTML_Processor` bails on some markup (`get_last_error()`, `class-wp-html-processor.php:647`), which must become a refusal with a reason; and the first edited post must be opened in the block editor on Fieldnotes to see that it does not report "Block contains unexpected or invalid content" (`wp-includes/js/dist/block-editor.js:21691`).

### Splice one block, not the whole document

**Verdict: possible through core.** The helper refuses any store whose saved markup does not survive `serialize_blocks(parse_blocks())` byte for byte (`src/core/live-helper-wordpress.ts:2029`, `:2498`, `:2699-2702`). That is stricter than core needs: `serialize_block_attributes()` re-encodes attribute JSON with its own flags and escapes (`wp-includes/blocks.php:1705`), so markup written by another tool can fail the round trip while being perfectly valid. WordPress 6.9's streaming `WP_Block_Processor` gives each block's byte span (`next_block()`, `get_span()`, `extract_full_block_and_advance()` at `wp-includes/class-wp-block-processor.php:631`, `:1903`, `:1257`), and its own documented example replaces one block as `substr(…, 0, $at) . serialize_block($new) . substr(…, $ends_before)` (`:1205-1256`; [streaming block parser in 6.9](https://make.wordpress.org/core/2025/11/19/introducing-the-streaming-block-parser-in-wordpress-6-9/)). Core uses the same surgical approach elsewhere: `wp_strip_custom_css_from_blocks()` uses `WP_Block_Parser::next_token()` to "surgically replace only the attribute JSON that changed — no parse_blocks() + serialize_blocks() round-trip needed" (`wp-includes/block-supports/custom-css.php:186-199`). The helper keeps its content hash and block fingerprint as the base check, re-serialises only the target block, and leaves every other byte alone.

### Bound text saves to post meta, and synced patterns save per page

**Verdict: bound text possible with conditions; synced patterns possible through core.** A block with `metadata.bindings` shows another source's value, and the helper currently lists it read-only (`src/core/live-helper-wordpress.ts:2001`). For `core/post-meta`, the editor's own `setValues()` writes the meta through `editEntityRecord()`, and its `canUserEditValue()` refuses inside a Query, for an unregistered key, when the custom-fields panel is on, or when the user cannot update the post (`wp-includes/js/dist/editor.js:101820-101870`); the server source returns nothing for protected or non-`show_in_rest` keys (`wp-includes/block-bindings/post-meta.php:38-48`). The helper saves through the post's REST `meta`, which checks `edit_{type}_meta` per key (`wp-includes/rest-api/fields/class-wp-rest-meta-fields.php:282`, `:392`) and needs the post type to support custom fields (`wp-includes/meta.php:1420-1424`; [register_meta](https://developer.wordpress.org/reference/functions/register_meta/)). Supported binding attributes in 7.1.3 are paragraph, heading and list-item `content`, image `id,url,title,alt,caption`, button `url,text,linkTarget,rel`, post-date `datetime` and navigation `url` (`wp-includes/block-bindings.php:134-186`; [Bindings reference](https://developer.wordpress.org/block-editor/reference-guides/block-api/block-bindings/); [6.9 improvements](https://make.wordpress.org/core/2025/11/12/block-bindings-improvements-in-wordpress-6-9/)).

A synced pattern is one `wp_block` post with revisions at `/wp/v2/blocks` (`wp-includes/post.php:303-355`); editing its own content changes every page that shows it, which the helper already flags as `shared` (`src/core/live-helper-wordpress.ts:2633-2634`). Pattern overrides are the per-page alternative and **the safest write in WordPress**: the per-instance value is plain JSON in the host's void `core/block` delimiter, `content[metadata.name][attribute]` (`wp-includes/blocks/block.php:59-74`; read server-side at `wp-includes/block-bindings/pattern-overrides.php:22-28`), written by the editor in the same shape (`wp-includes/js/dist/editor.js:101645-101660`). There is no markup to keep consistent, only overridable attributes qualify (`wp-includes/block-bindings.php:142-153`), and the host saves through its own REST route.

### Templates, parts and navigation each have a REST controller

**Verdict: templates and parts possible through core; words from a `core/pattern` reference and navigation labels possible with conditions.** Sending edited markup to `/wp/v2/templates/<theme//slug>` or `/wp/v2/template-parts/…` updates a customised template with `wp_update_post()` or, for a theme file, creates a `wp_template` post that shadows the file, which is never written; sending `source: theme` reverts (`wp-includes/rest-api/endpoints/class-wp-rest-templates-controller.php:367-398`, `:375-383`), behind `edit_theme_options` (`:184-191`), with revisions and autosaves (`wp-includes/post.php:368-403`, `:433-468`). The REST path also runs `inject_ignored_hooked_blocks_metadata_attributes()` (`wp-includes/default-filters.php:822-823`; `wp-includes/block-template-utils.php:1711`), which a direct `wp_update_post()` would skip, so the helper stays on REST. Its block saves already work in `tpl:` and `tp:` stores (`src/core/live-helper-wordpress.ts:4216-4258`), so the template "Edit" links (`:2225`, `:2238`) can become word targets for each block inside. Words from a `core/pattern` reference are not in the template at all, because the pattern renders from the registry at request time (`wp-includes/blocks/pattern.php:33-69`); the honest edit inlines the registered content in place of the delimiter and edits it, in one save, and tells the owner that translatable strings in a PHP pattern become fixed text in the site's current language. Not verified: what the Site Editor itself does with a `core/pattern` block when a template is edited.

A navigation link's label is a plain attribute on a dynamic block, rendered as `wp_kses_post( $attributes['label'] )` (`wp-includes/blocks/navigation-link.php:259-263`), inside a `wp_navigation` post with revisions at `/wp/v2/navigation` (`wp-includes/post.php:539-575`). The helper's rule that any attribute of a dynamic block with no saved markup is writable (`src/core/live-helper-wordpress.ts:1971-1975`) already covers it, once the trace attributes each rendered link to its `post:<wp_navigation id>` store — and that attribution is unverified, because the navigation block parses its referenced post itself. A navigation block with no `ref` renders a fallback; editing one of its labels first needs a real `wp_navigation` post from `WP_REST_Navigation_Fallback_Controller`, a structural change the owner must agree to. Classic menu labels already save through `/wp/v2/menu-items` (`wp-includes/rest-api/endpoints/class-wp-rest-menu-items-controller.php:232`, `:421-424`).

### Any `WP_Widget` saves through its encoded instance and hash

**Verdict: `show_instance_in_rest` off is possible through core; "not a WP_Widget" is possible with conditions; a display-only widget is genuinely impossible.** `WP_REST_Widgets_Controller::save_widget()` accepts three forms. `instance.raw` needs `show_instance_in_rest`, but `instance.encoded` plus `hash` is accepted for any `WP_Widget` when `hash_equals( wp_hash( $serialized ), hash )`, and `form_data` is accepted as is; all three reach the widget's own registered update callback (`wp-includes/rest-api/endpoints/class-wp-rest-widgets-controller.php:571-579`, `:580-590`, `:604-605`, `:613-623`), behind `edit_theme_options` (`:486-487`) ([REST API Widgets](https://developer.wordpress.org/rest-api/reference/widgets/)). Running inside WordPress, the helper can build `encoded` and `hash` exactly as a GET in edit context returns them (`:718-725`), so the refusal at `src/core/live-helper-wordpress.ts:2268` disappears — the classic Text widget is the common case, since it lacks the flag but kses's its own text (`wp-includes/widgets/class-wp-widget-text.php:371-389`). A widget registered outside `WP_Widget` with an update callback can be saved through `form_data` if the helper knows its form field names (`wp-includes/widgets.php:577-586`); one registered with a display callback and no control has no write path, because the controller refuses any `id_base` missing from the registered updates (`class-wp-rest-widgets-controller.php:554-560`). Words inside a block widget are block markup in `instance.content` (`wp-includes/widgets/class-wp-widget-block.php:17-39`), so the block-word save applies there.

### Two alts and one upload: images on WordPress

**Verdict: possible with conditions.** Core keeps two alts apart. The image block's `alt` is attribute-sourced from `img[alt]` in the post's markup (`wp-includes/blocks/image/block.json`), rendered from the saved markup without consulting the attachment (`wp-includes/blocks/image.php:195`), and is already writable under the helper's attribute rule when the block has no inner blocks. The attachment's alt is `_wp_attachment_image_alt`, written through `/wp/v2/media/<id>` `alt_text` (`wp-includes/rest-api/endpoints/class-wp-rest-attachments-controller.php:971-991`) and printed wherever core prints the attachment — `wp_get_attachment_image()` (`wp-includes/media.php:1169-1186`), the featured image unless it links (`wp-includes/blocks/post-featured-image.php:29-38`) and the site logo (`wp-includes/general-template.php:1295-1330`). The helper offers both targets and says which one this page used ([REST API Media](https://developer.wordpress.org/rest-api/reference/media/)). Replacing an image uploads the bytes with a multipart `POST /wp/v2/media` as the logged-in user — not the 7.1 `url` form, which refuses private and local hosts (`class-wp-rest-attachments-controller.php:325-335`) — and then, in one block save, sets `attrs.id`, `img[src]`, swaps the `wp-image-OLD` class for `wp-image-NEW`, and drops or replaces `width`, `height` and `sizeSlug`. The class matters twice: `wp_filter_content_tags()` uses it to add `srcset` and sizes (`wp-includes/media.php:1987-2009`), and the editor's `save()` writes it from `id`, so a stale class would mark the block invalid. Which other image attributes `save()` turns into classes was not checked; test a replacement in the editor first.

### Classic content saves; classic templates do not

**Verdict: classic post content possible with conditions; words printed by classic theme PHP, shortcodes or plugins genuinely impossible.** Classic content is one freeform block (`wp-includes/class-wp-block-parser.php:311-312`) saved through the same REST route, so saving is easy and **mapping** is the work: the rendered page has passed through `wptexturize`, `wpautop`, `do_shortcode` (after autop) and `wp_filter_content_tags` (`wp-includes/default-filters.php:201-210`). The helper would walk stored text nodes with `WP_HTML_Tag_Processor::next_token()` (`class-wp-html-tag-processor.php:947`), match the edited rendered node in order after texturising the stored text, replace it with `set_modifiable_text()` or a kses'd splice, and refuse inside shortcode output. No core function maps rendered `the_content` back to source offsets, so this mapping is Wanigan's own and needs tests on classic content. Strings echoed by theme or plugin PHP — archive title prefixes, "Leave a reply", footer credits — are code; the only routes are a theme-file edit (the helper's child-theme copy) or a translation file.

### What WordPress core cannot save from PHP

**Verdict: three genuine impossibilities.** First, **a static block's non-sourced settings** (heading `level`, which becomes the tag; `textAlign`, which becomes a class) are written into markup by the block's JavaScript `save()`, and core has no PHP `save()`; editing only the comment-delimiter JSON leaves markup the editor rejects. The helper's refusals at `src/core/live-helper-wordpress.ts:2006-2007` are correct, and the helper already uses the block's own editor script when it needs a static block's markup (`:3150-3198`). Second, **a stable block id**: every block type gets exactly two global attributes, `lock` and `metadata`, neither holding an id (`wp-includes/class-wp-block-type.php:276-285`); `metadata.name` is a user label that pattern overrides deliberately share; `anchor` is a user-chosen HTML id; real-time collaboration, which kept block `clientId`s in a separate `_crdt_document`, "will not ship in WordPress 7.0" ([Make Core, 8 May 2026](https://make.wordpress.org/core/2026/05/08/rtc-removed-from-7-0/)), and its files are deleted by the 7.0.2 updater (`wp-admin/includes/update-core.php:905-909`); the follow-up "stable block and text range identifiers" is an experiment "not ready for Core inclusion" ([Make Core, 18 Sep 2026](https://make.wordpress.org/core/2026/09/18/moving-to-a-server-aware-approach-for-collaboration/)). The helper's store, path, name and fingerprint with a sibling re-find (`src/core/live-helper-wordpress.ts:2391-2399`, `:2672-2696`) is the best core allows, and `WP_Block_Processor::get_breadcrumbs()` (`class-wp-block-processor.php:1171`) makes the re-find exact. Writing a private id into `metadata` was rejected: it alters the owner's content, the editor's `cloneBlock` copies it on duplicate (`wp-includes/js/dist/blocks.js:3304`), and nobody has confirmed the editor keeps unknown `metadata` keys. Third, **per-language content**: core localises code strings and picks one locale per request (`wp-includes/l10n.php:30`, `:124`), and a post, template or option holds one value; multilingual content is a plugin feature.

## Placing, naming and finding parts: core records configuration, not code

### Drupal where-used is cheap for configuration and a scan for overrides

**Verdict: possible through core, with Layout Builder overrides possible with conditions.** Core finds block placements by plugin exactly as `BlockContent::getInstances()` does, with `loadByProperties(['plugin' => …])` (`modules/block_content/src/Entity/BlockContent.php:187-189`), and plugin ids name what they show: `views_block:{view}-{display}` (`modules/views/src/Plugin/Derivative/ViewsBlock.php:88`), the menu's machine name for a menu block (`modules/system/src/Plugin/Block/SystemMenuBlock.php:189-190`), `block_content:{uuid}` for a reusable block. Derivative plugins declare config dependencies — on `system.menu.{menu}`, on the view, and a content dependency on the block_content entity (`modules/system/src/Plugin/Derivative/SystemMenuBlock.php:50`; `ViewsBlock.php:110-112`; `modules/block_content/src/Plugin/Derivative/BlockContent.php:53-54`) — and a Layout Builder default adds a dependency on every component's plugin (`modules/layout_builder/src/Entity/LayoutBuilderEntityViewDisplay.php:395-401`). So `ConfigManager::findConfigEntityDependencies()` (`lib/Drupal/Core/Config/ConfigManager.php:270-295`) answers "which placements and default layouts use this menu, view, block or field" in one call; for a field it replaces the Views UI report's load-every-view walk (`modules/views_ui/src/Controller/ViewsUIController.php:48-75`). Indexed lookups cover the rest: `inline_block_usage` for inline blocks (`modules/layout_builder/layout_builder.install:13-41`; `modules/layout_builder/src/InlineBlockUsage.php:82-88`), `file.usage` for files, `MenuLinkManager::loadLinksByRoute()` for menu links to an entity (`lib/Drupal/Core/Menu/MenuLinkManager.php:297-303`), and one indexed entity query per entity-reference field from `getFieldMapByFieldType()` (`lib/Drupal/Core/Entity/EntityFieldManager.php:586`), since core keeps no reference usage tracker.

Layout Builder **overrides** are the expensive case: each is one serialized `Section` per delta in a blob column (`modules/layout_builder/src/Plugin/Field/FieldType/LayoutSectionItem.php:69-72`), which an entity query can only test for existence. The helper takes each bundle whose display allows overrides, queries `exists('layout_builder__layout')`, loads in batches and walks `getSections()`; a cheaper LIKE pre-filter on the raw table relies on the plugin id surviving inside the serialized blob. Unverified: the wildcard config query on the sections path (`lib/Drupal/Core/Config/Entity/Query/Condition.php:108-117` supports `*`), the LIKE pre-filter, and the table and column names. **Counting pages is genuinely impossible** for a placement with path, role or bundle visibility, because those conditions are evaluated per request; the honest wording is "shows on", with a count only for a bundle-limited placement or a default layout (the bundle's entities without an override).

### No registry of component uses exists; a Twig parse finds the static ones

**Verdict: static uses possible with conditions; dynamic uses genuinely impossible.** Core records no callers of a single-directory component: `ComponentNodeVisitor` rewrites only the component's own template, injecting library attachment, context and prop validation (`lib/Drupal/Core/Template/ComponentNodeVisitor.php:45-52`, `:65-93`, `:118-131`), and stores nothing about the including template. The helper can still find every static use without a regex by running Drupal's `twig` service: strip YAML front matter as `TwigEnvironment::compileSource()` does (`lib/Drupal/Core/Template/TwigEnvironment.php:108-125`), call `tokenize()` and `parse()` (`vendor/twig/twig/src/Environment.php:544`, `:566`), walk the tree for `EmbedNode` names, `IncludeNode` and `include()` targets that are constant expressions (`vendor/twig/twig/src/Node/EmbedNode.php:28-32`; `vendor/twig/twig/src/Node/IncludeNode.php:27-34`), keep names `plugin.manager.sdc->find()` accepts (`lib/Drupal/Core/Theme/ComponentPluginManager.php:138`), and map each template to its theme hook through the registry (`lib/Drupal/Core/Theme/Registry.php:292`), so the answer reads "used by the Article teaser template". Each file needs its own try/catch, because parsing runs `validateSlots()`, which can throw on a broken component; whether `parse()` has side effects beyond the code is unconfirmed, and nothing was benchmarked. Out of reach of any parse: names chosen by a variable or concatenation, ids chosen in preprocess, includes by path, and components placed from PHP as `#type => component`, which core's own Navigation module does (`lib/Drupal/Core/Render/Element/ComponentElement.php:61`, `:136`, `:165`; `modules/navigation/src/Plugin/TopBarItem/PageContext.php:94`). Which **pages** use a component needs rendering.

### A Drupal component cannot be placed alone through core

**Verdict: genuinely impossible through core.** Core has no block, field formatter, layout, Layout Builder plugin or UI that places a single-directory component, and it builds no form from a component's JSON Schema; the schema is used only to validate (`lib/Drupal/Core/Theme/Component/ComponentValidator.php:172`). A component reaches a page only through code — `{% include %}`/`{% embed %}` in a template, or `#type => component` with `#props` and `#slots` in a module or theme (`ComponentElement.php:15-25`). Drupal's own overview still describes generated forms and placement as future work: "contributed modules (and eventually Drupal core) can automatically generate forms … in the future, we'll be able to add components directly from systems like Layout Builder" ([About Single-Directory Components](https://www.drupal.org/node/3352688)); today that is contrib territory ([UI Patterns](https://www.drupal.org/project/ui_patterns); [Drupal Canvas](https://www.drupal.org/project/canvas)). The README's "what core cannot place alone … says so" (`README.md:198`) and the helper's props refusals (`src/core/live-helper-drupal-edit.ts:404-411`) are therefore accurate. What the helper can offer honestly is the picture alone, which it already does; placement as a code change, a template override in the owner's theme that embeds the component; and a props form rendered from the schema and validated with core's `ComponentValidator`, which has somewhere to save only when the props come from stored data. A helper-provided "component block" plugin was rejected: the site's block config would depend on Wanigan's module, and removing the helper would leave broken blocks.

### Layout Builder components are named by storage plus UUID, and core's move keeps them

**Verdict: possible through core.** A component's UUID reaches every front-end render, but only as an array key, `content['_layout_builder'][delta][region][uuid]` (`modules/layout_builder/src/Section.php:85-104`; [SectionComponent](https://api.drupal.org/api/drupal/core%21modules%21layout_builder%21src%21SectionComponent.php/class/SectionComponent/11.x)); only the builder UI writes it as an attribute (`modules/layout_builder/src/Element/LayoutBuilder.php:311-314`). UUIDs are **not unique across the site**, because an override starts as a copy of its default's sections with the same UUIDs (`modules/layout_builder/src/EventSubscriber/PrepareLayout.php:73-81`), so identity is the section storage plus the UUID. Core's drag-and-drop move runs `getComponent`, `removeComponent`, `setRegion`, then `insertAfterComponent()` or `insertComponent(0, …)`, and stores the tempstore (`modules/layout_builder/src/Controller/MoveBlockController.php:65-89`); it moves the same `SectionComponent` object, so identity survives. The helper already stamps components from the array keys and refuses while the tempstore holds changes; a sturdier tag would come from its own subscriber below priority 100 on `SECTION_COMPONENT_BUILD_RENDER_ARRAY` (`modules/layout_builder/src/EventSubscriber/BlockComponentRenderArray.php:50-51`), reading `$event->getComponent()`. Whether a `#lazy_builder` build can carry that tag is the same unverified limit the helper hits today. A move in a default layout changes every entity of that bundle without an override and is exported configuration. Menus need nothing new: `#menu_name`, the `menu_name` template variable and the `config:system.menu.{name}` cache tag are on any non-empty menu (`lib/Drupal/Core/Menu/MenuLinkTree.php:123-151`), and each link carries its plugin id; a menu with no visible links renders nothing to name.

### WordPress where-used is a search, closed over references

**Verdict: possible with conditions.** Core keeps no usage index, and `has_block()` only tests one string for `<!-- wp:name ` without following `ref` or `slug` (`wp-includes/blocks.php:909-945`). The core-only method has four steps. Pre-filter `wp_posts.post_content` across posts, pages, `wp_template`, `wp_template_part`, `wp_block` and `wp_navigation` with a `LIKE` needle (`<!-- wp:acme/card `, `"ref":123`, `"slug":"theme/hero"`, `"patternName":…`), through `WP_Query` with `search_columns => ['post_content']`, `sentence` and `fields => 'ids'` (`wp-includes/class-wp-query.php:784-785`, `:1446`, `:1465-1487`) or a prepared `$wpdb` query that avoids search plugins hooking `posts_search`. Confirm each hit with `WP_Block_Processor::next_block($type)`, whose documented uses include "Counting block types in a document" (`wp-includes/class-wp-block-processor.php:8-30`, `:631`), and record breadcrumbs so the result matches the helper's block identity. Add theme-file templates through `get_block_templates()` (`wp-includes/block-template-utils.php:1119`), registered pattern contents (`wp-includes/class-wp-block-patterns-registry.php:204`, `:229`) and `widget_block` instances. Then close over references — a block inside synced pattern 12 shows wherever `ref:12` is used — because core does not. A `LIKE '%…%'` is one full scan per search and was not benchmarked; multisite was not examined. Genuinely impossible: the provenance of an inserted unsynced pattern with more than one root block, because core writes `metadata.patternName` only when there is exactly one root (`wp-includes/blocks.php:1972`; `wp-includes/js/dist/block-editor.js:14082-14097`); blocks inserted by Block Hooks, which never appear in stored content (`wp-includes/blocks.php:1008`, `:1162`); and blocks rendered from a classic theme's PHP.

### Placing a WordPress block or pattern is a markup splice through REST

**Verdict: possible with conditions.** Core's save path is markup: parse the target, splice blocks in, serialize (`wp-includes/blocks.php:1795`, `:1837`, `:2550`), and save through REST, where a theme-file template becomes a `wp_template` post on its first save. A pattern goes in as a `core/pattern` reference, which renders from the registry but is replaced by its blocks the next time the editor loads the template (`wp-includes/rest-api/endpoints/class-wp-rest-templates-controller.php:684-690`), or inlined, where only a single-root pattern keeps `metadata.patternName`; the reference is better for where-used and inlining matches the editor, a product choice. A synced pattern goes in as `core/block {"ref":id}`. There is **no PHP block validator**: validation runs only in the editor, comparing a static block's saved HTML with its `save()` output (`wp-includes/js/dist/blocks.js:4866`, `:4899`), so a static block's markup must come from that block's own editor script, as the picture path already does (`src/core/live-helper-wordpress.ts:3150-3198`). Not checked: whether the post editor, as opposed to the site editor, also inlines `core/pattern` on load.

## Styles, tokens and breakpoints: WordPress 7.1 moved the line, Drupal did not

### WordPress one-instance styles split on whether the server renders the support

**Verdict: possible through core for server-rendered supports, the 7.1 states and breakpoints, and per-instance custom CSS; possible with conditions for colour, typography, spacing, border, shadow and dimensions on static blocks.** One block's style lives in its comment-delimiter attributes: presets as `backgroundColor`, `textColor`, `fontSize` and friends, or as `var:preset|<type>|<slug>` inside `style`, and raw values inside `style`, mapped to CSS by `WP_Style_Engine` (`wp-includes/style-engine/class-wp-style-engine.php:54-369`, preset parsing at `:385-419`). The trap is that the two halves render differently. Colour, typography, spacing, border, shadow and most dimensions are applied by `apply_block_supports()`, whose only caller is `get_block_wrapper_attributes()` — "If no render_callback, assume styles have been previously handled" (`wp-includes/class-wp-block-supports.php:114-145`, `:203-205`) — so for a static block (paragraph, heading, group) the editor's `save()` wrote the classes and inline style into the saved HTML ([Block Supports API](https://developer.wordpress.org/block-editor/reference-guides/block-api/block-supports/)). Changing only the attribute JSON there changes nothing on the front end and makes the editor flag the block (`wp-includes/js/dist/blocks.js:4878`, `:4890`). By contrast, background, aspect ratio, position, layout, elements, states, custom CSS, visibility and duotone are rendered on the server from the attributes alone by `render_block` filters (`wp-includes/block-supports/background.php:131`; `dimensions.php:123-148`; `position.php:151`; `layout.php:1450`; `elements.php:307-308`; `states.php:749`; `custom-css.php:153-155`; `block-visibility.php:132`; `duotone.php:44`), so an attribute-only write is enough for the front end, and so is any attribute on a dynamic block. One gap covers every static-block case here: nobody has read the editor's JavaScript style-engine path table, so it is unconfirmed that a static block's `save()` leaves `@mobile`, `@tablet`, `:hover` and `css` out of the inline style it writes (the editor builds that style from the engine, `wp-includes/js/dist/block-editor.js:94584-94590`), and the first such write must be opened in the block editor on Fieldnotes before the route is trusted. The helper writes attribute JSON surgically, as `wp_strip_custom_css_from_blocks()` does, and prefers preset references, which follow later token edits.

WordPress 7.0 and 7.1 added three native homes the design router does not use. **Per-instance custom CSS** lives in `attrs.style.css`, defaults on, refuses CSS containing markup, and renders as `:root :where(.wp-custom-css-<hash>){…}` through the `wp-block-custom-css` handle (`wp-includes/block-supports/custom-css.php:41-57`, `:79-86`; `wp-includes/class-wp-theme-json.php:2048-2100`); it is stripped on save unless the user has `edit_css`, which maps to `unfiltered_html` and is refused under `DISALLOW_UNFILTERED_HTML` and to non-super-admins on multisite (`custom-css.php:278-306`; `wp-includes/capabilities.php:594-603`), it is off for seven blocks including `core/html` and `core/shortcode`, and "media queries are not supported" ([Custom CSS for individual block instances in 7.0](https://make.wordpress.org/core/2026/03/15/custom-css-for-individual-block-instances-in-wordpress-7-0/)). The helper checks `current_user_can('edit_css')` and answers "no native route" when it fails, and verification must catch a more specific theme rule winning over its 0-1-0 specificity. **Per-instance pseudo-states** (`style[':hover']`, `:focus`, `:focus-visible`, `:active`) exist only for `core/button` and `core/navigation-link` (`class-wp-theme-json.php:664-667`) and are emitted with `!important` on a hashed class (`wp-includes/block-supports/states.php:434-447`, `:676-700`). **Per-instance breakpoints** are covered in the breakpoint section below. Generated classes such as `wp-custom-css-*`, `wp-states-*` and `wp-container-*` are content hashes, so verification must compare computed styles, never these selectors. For static-block colour, typography and spacing, the remaining route is a PHP port of the style engine's class and inline-style output, tested block by block against the editor — nobody has read the exact strings each `save()` emits, so this is the riskiest style write and belongs last.

### Every instance and every token on a WordPress block theme is a REST write to global styles

**Verdict: possible through core.** The layer's refusal "A token is the theme's: changing it natively is a code change" (`src/main/live-layer.ts:441`) is wrong for block themes. The user layer of global styles is a `wp_global_styles` post per theme stylesheet, created on demand and merged last after core, blocks and theme (`wp-includes/class-wp-theme-json-resolver.php:478-518`, `:644-668`), written over REST at `/wp/v2/global-styles/<id>` with `edit_theme_options` and kept with a revisions controller (`wp-includes/post.php:495-520`; `wp-includes/rest-api/endpoints/class-wp-rest-global-styles-controller.php:211-226`, `:238-290`) ([Global Styles REST](https://developer.wordpress.org/rest-api/reference/global-styles/) *(unread)*). It accepts `styles.blocks.<name>` with every property in `VALID_STYLES` plus `css`, `styles.elements.*` with pseudo-states for link and button, block style variations, and since 7.1 `@mobile`/`@tablet` sub-objects (`wp-includes/class-wp-theme-json.php:572-634`, `:653-656`, `:1303-1350`). Tokens are theme.json presets — palette, font sizes and families, spacing sizes, shadows, gradients, duotone, aspect ratios, radius sizes — emitted as `--wp--preset--<type>--<slug>` on `:root` plus `!important` utility classes (`class-wp-theme-json.php:132-220`, `:2658`), so a value change repaints every place that references the preset, and overriding the custom property on `:root` previews it exactly ([theme.json reference](https://developer.wordpress.org/block-editor/reference-guides/theme-json-reference/theme-json-living/) *(unread)*). This is database content, out of the owner's repository, with native undo; the theme's own `theme.json` is the code alternative for a custom theme.

Four conditions apply. The helper changes values and **never slugs**, because renaming one orphans every `var:preset|color|<old>` and `has-<old>-color` reference in content. The user post is keyed to the active stylesheet, so a theme switch loses it. Instance attributes and inline styles beat global styles, so instances styled one by one stay as they were, and reach must be shown per instance. And for users without unfiltered HTML, kses runs `WP_Theme_JSON::remove_insecure_properties()` on the content (`wp-includes/kses.php:2464-2475`). The main unverified point is how a value override of a **theme** preset should be keyed: presets are stored by origin and merged with `array_replace_recursive` (`class-wp-theme-json.php:1091-1120`, `:4328-4331`), and nobody has read which origin keys the Site Editor writes when an owner edits a theme preset. Also unverified: the `settings.custom` → `--wp--custom--*` path and how fluid typography changes "the same value" across widths.

### WordPress 7.1 breakpoints are native data, with two traps

**Verdict: possible through core.** The layer leaves out every edit for a named breakpoint because "phase 1 does not read the theme's breakpoints" (`src/main/live-layer.ts:17`), but WordPress 7.1 has them natively: `settings.viewport.mobile` and `tablet` default to `480px` and `782px` (`wp-includes/class-wp-theme-json.php:692-700`), sanitised to `px`, `em` or `rem` with `tablet` larger than `mobile` (`:754-859`), global only (`:1346-1348`), and turned into range queries `@media (width <= mobile)` and `@media (mobile < width <= tablet)` by `get_viewport_media_queries()` (`:703-751`). Responsive values go in `@mobile`/`@tablet` objects in a block instance's `style` attribute — "Responsive styles for an individual block are stored in the block's existing `style` attribute", with no `@desktop` key because the base style is desktop ([Responsive block styles and configurable viewports in 7.1](https://make.wordpress.org/core/2026/08/05/responsive-block-styles-and-configurable-viewports-in-wordpress-7-1/)) — rendered on the server by `wp_render_block_states_support()` with `!important` (`wp-includes/block-supports/states.php:540-670`), including responsive child layout (`wp-includes/block-supports/layout.php:976-995`) and per-viewport visibility (`wp-includes/block-supports/block-visibility.php:20-102`). The helper reads the breakpoints with `wp_get_global_settings(['viewport'])` and writes an attribute-only change on the instance, which the server renders even for a static block (subject to the editor-validation gap in the one-instance section), or `styles.blocks.<name>['@tablet']` in global styles for every instance.

The first trap is boundaries: the layer's preview must use exactly these non-overlapping range queries, or preview and result differ at exactly 480px and 782px. The second is that moving `settings.viewport` moves less than it seems: core's own block CSS keeps fixed media queries — columns stack at `max-width: 781px` and unstack at `min-width: 782px` (`wp-includes/blocks/columns/style.css:101`, `:121`, `:126`) — and theme stylesheets keep theirs, so verification must test widths either side of every relevant query. Only two breakpoints plus base exist; a design breakpoint that is neither, or a classic theme's own 1024px, has no native per-instance home, and per-instance custom CSS cannot hold `@media` (`class-wp-theme-json.php:2055-2075`). Unverified: whether REST-saved user global styles keep `@mobile` keys through `remove_insecure_properties()`.

### Classic WordPress themes have one native style home

**Verdict: possible with conditions.** Without theme.json, core's style store is Customizer Additional CSS: one `custom_css` post per stylesheet (`wp-includes/post.php:189`), written by `wp_update_custom_css_post()` (`wp-includes/theme.php:2084-2100`) and printed as `<style id="wp-custom-css">` at `wp_head` priority 101 (`theme.php:1969-1985`; `wp-includes/default-filters.php:365`); block themes merge it into `global-styles` (`wp-includes/script-loader.php:2600-2625`). It accepts media queries and serves one instance, a kind, the site or a breakpoint, but it is a hand-written rule, so specificity and load order decide whether it wins and verification is essential. The helper appends scoped rules inside a Wanigan-marked comment block so they can be undone. Unverified: whether `custom_css` posts keep revisions, and which capability callers must check, since the function does none itself. Theme mods (`wp-includes/theme.php:1026-1162`) are tokens only where the theme's PHP prints them as CSS.

### Drupal keeps per-instance style in three narrow places

**Verdict: genuinely impossible through core outside three homes.** Drupal 11.4.8 has no generic per-instance style store. Block config has no class field (`modules/block/config/schema/block.schema.yml:27-57`), and Layout Builder's `SectionComponent::$additional` and section third-party settings are stored and validated but **never rendered** by core (`modules/layout_builder/src/SectionComponent.php:52-56`, `:104-131`), so writing there has no effect without custom code. The three native homes are narrow. The **CKEditor 5 Style plugin** stores `{label, element}` pairs such as `<p class="lead">` in the text format's editor config, with the warning "These styles should be available in your theme's CSS file" (`modules/ckeditor5/src/Plugin/CKEditor5Plugin/Style.php:21-84`); setting or removing one of those classes on one element of a body field is a content write with a revision, safe because the plugin syncs those classes into the format's allowed HTML. **Layout Builder column widths** for two- and three-column sections render as a modifier class `layout--<template>--<width>` (`modules/layout_builder/src/Plugin/Layout/MultiWidthLayoutBase.php:17-55`). **Formatter settings** per component or display — image style, label display — change appearance through `EntityDisplayBase::setComponent()` (`lib/Drupal/Core/Entity/EntityDisplayBase.php:336-351`). Single-directory component variants exist since 11.2 ([drupal.org/node/3544193](https://www.drupal.org/node/3544193)) and core prints `data-component-id` and `data-component-variant` on the component (`lib/Drupal/Core/Template/ComponentsTwigExtension.php:80-84`), but a variant is chosen only in code. Everything else — "this card's padding" — needs a new hook in code (a variant or enum prop wired to a field) or a theme CSS rule scoped by those stable attributes, which is the agent path the design already describes.

### Drupal tokens are theme settings when a theme exposes them, and code otherwise

**Verdict: theme-setting tokens possible with conditions; CSS custom properties and component CSS are code.** Core has two token stores. A `<theme>.settings` config object, read through `ThemeSettingsProvider::getSetting()` (`lib/Drupal/Core/Extension/ThemeSettingsProvider.php:51`; `theme_get_setting()` is deprecated in 11.3, `includes/theme.inc:205-215`), can be written through the Config API with typed-config validation, but it becomes CSS only where the theme's own PHP prints it. Olivero is the core example: `base_primary_color` is a `color_hex` setting (`themes/olivero/config/schema/olivero.schema.yml:1-30`), converted to HSL and printed as `--color--primary-hue`, saturation and lightness on `<html>` (`themes/olivero/src/Hook/OliveroPagePreprocessHooks.php:36-39`), so overriding those three properties on `:root` previews the setting exactly. It is site configuration, so in a config-managed project the owner must export it, and Wanigan says so. Every other token is a custom property in theme CSS — Olivero's `--sp`, `--max-width` and friends live in `variables.pcss.css`, compiled to `variables.css` (`themes/olivero/css/base/variables.pcss.css:10-42`) — which is code, and a `.css` beside a `.pcss.css` is build output that the next build overwrites. "Every instance of a component" is likewise that component's own CSS file, attached as `core/components.<provider>--<name>` (`lib/Drupal/Core/Plugin/Component.php:86-89`); for a theme the owner did not write, the clean core route is a subtheme adding a plain CSS file with `libraries-extend` (`lib/Drupal/Core/Asset/LibraryDiscoveryParser.php:447-486`; `lib/Drupal/Core/Theme/ActiveTheme.php:240`) or replacing a component with the SDC `replaces` key (`lib/Drupal/Core/Theme/ComponentPluginManager.php:279-282`), both code.

### Drupal breakpoints are labels, not the CSS

**Verdict: reading possible through core; writing a breakpoint-specific value is code.** The breakpoint module is declarative metadata read through `breakpoint.manager`, whose `getBreakpointsByGroup($theme)` returns plugins with a label, weight, media query and multipliers (`modules/breakpoint/src/BreakpointManagerInterface.php:19`, `:27`; `modules/breakpoint/src/BreakpointInterface.php:16-56`) ([BreakpointManagerInterface](https://api.drupal.org/api/drupal/core%21modules%21breakpoint%21src%21BreakpointManagerInterface.php/interface/BreakpointManagerInterface/11.x) *(unread)*). Core consumes it only for responsive images and the toolbar, and nothing ties it to the theme's CSS: Olivero's yml declares `md` as `min-width: 700px` while its compiled CSS uses `(min-width: 43.75rem)` 66 times, and its source has a `--tabs-layout-switch` query the yml lacks (`themes/olivero/olivero.breakpoints.yml`; `themes/olivero/css/base/media-queries.pcss.css:3-18`). The layer should take its breakpoint list from the media queries on the element's matched rules, using declared breakpoints only as labels. Core has no store for a breakpoint-specific value, so every such edit is a change inside an `@media` block of theme CSS, deterministic only for a custom theme's hand-written file.

### Finding a rule's source: handles on WordPress, a scoped override on Drupal

**Verdict: possible with conditions on both; a source map for a Drupal aggregate is genuinely impossible.** On WordPress, every core-printed stylesheet carries its handle in its tag id, `<link id='<handle>-css'>` or `<style id="<handle>-inline-css">`, and every inline style ends with a `sourceURL` comment (`wp-includes/class-wp-styles.php:163`, `:205`, `:311-326`). The handle is the router: `global-styles` means global styles or `theme.json`, `core-block-supports` means the instance's attributes (`wp-includes/script-loader.php:3308-3340`), `wp-block-custom-css` the instance's `style.css`, `wp-custom-css` the Customizer post, and `wp-block-<name>` or `wp-block-library` core files that are never edited, so the change goes to global styles for that block type; a theme handle maps to its file through `wp_styles()->get_data($handle, 'path')`. Core ships no source maps. Setting `styles_inline_size_limit` to zero for Wanigan's token requests keeps every stylesheet a `<link>` at its own URL (`wp-includes/script-loader.php:3095-3107`).

On Drupal, the design's plan to "read styles with aggregation off" has no per-request switch in core: aggregation is decided from `system.performance:css.preprocess` and maintenance mode (`lib/Drupal/Core/Render/HtmlResponseAttachmentsProcessor.php:288-295`). The exact route is a helper service tagged `config.factory.override` that returns `css.preprocess: FALSE` only for token requests, with its own cache suffix (`lib/Drupal/Core/Config/ConfigFactoryOverrideInterface.php:20`, `:28`; `core.services.yml:437`). Stored config stays untouched, attachments are processed after Dynamic Page Cache stores the response (`modules/dynamic_page_cache/src/EventSubscriber/DynamicPageCacheSubscriber.php:303`; `lib/Drupal/Core/EventSubscriber/HtmlResponseSubscriber.php:39`, `:52`), the asset resolver caches unaggregated lists under a separate key (`lib/Drupal/Core/Asset/AssetResolver.php:242-243`), and each file arrives at its own URI (`lib/Drupal/Core/Asset/CssCollectionOptimizerLazy.php:82-83`). The reads must be authenticated or bypass the anonymous page cache, and the override must live in Wanigan's helper, never in the project's settings.php. With no override at all, the helper can decode an aggregate's `include=` parameter with `UrlHelper::uncompressQueryParameter()` (`lib/Drupal/Component/Utility/UrlHelper.php:103`) and map libraries to files through `library.discovery`. Two things are impossible: a source map for an aggregate, because `CssOptimizer` strips every comment, map comments included (`lib/Drupal/Core/Asset/CssOptimizer.php:220-236`), and maps that the theme's build never emitted; core themes ship none. Swapping a file per request through `hook_css_alter` would leak to other visitors, because its result is cached under a key that ignores the request. Unverified: whether the override's cache suffix must vary within a request, and whether the attachments processor is built after the request is on the stack under BigPipe and AJAX.

## Before, after and reach: what core can render, and what it cannot remember

### The page as it was is Wanigan's own capture, not a core feature

**Verdict: a "before" captured at save needs no core API; a past page for configuration and code is genuinely impossible through core.** The design layer admits its blind spot: a change that leaked beyond the touched elements is in both renders and passes — "a rule that also turned every paragraph blue passed" — and catching it "needs the page as it was before the implementation", which is "still to build" (`src/main/live-layer.ts:23-27`). Core versions content entities only. Drupal can render a node, media or term revision in the front-end theme on its own revision route (`modules/node/node.routing.yml:43-55`; the generic provider since 10.1, [change record](https://www.drupal.org/node/3160443)), but that page is not pixel-comparable: its title is "Revision of %title from %date" (`lib/Drupal/Core/Entity/Controller/EntityRevisionViewController.php:91-100`), the node template's `page` flag is false (`modules/node/src/Hook/NodeThemeHooks.php:176-181`), path-limited blocks disappear (`modules/system/src/Plugin/Condition/RequestPath.php:158-170`), and referenced entities render as today's default revision (`lib/Drupal/Core/Field/Plugin/Field/FieldFormatter/EntityReferenceFormatterBase.php:146`). WordPress has no front-end URL for a revision at all (`wp-includes/post.php:128-146`). The cheapest complete "before" is therefore a render Wanigan takes just before `helperSave` and keeps with the edit; it covers code and config changes too. For a "before" taken after the fact, for one entity, a Drupal helper can register its own param converter through core's `paramconverter` tag (`core.services.yml:1278-1287`) that, only on token requests carrying a revision id, returns that revision on the canonical route, so the page renders with the canonical title, path and blocks; its interaction with Dynamic Page Cache is unverified. On WordPress the same is done with request filters (next section). Configuration, theme code, options, widgets, classic menus and theme mods keep no history, so no API recreates them.

### Drupal Workspaces is the one complete preview, and it is the owner's choice

**Verdict: content previews possible with conditions; config, code and Layout Builder tempstore previews genuinely impossible.** Workspaces — "an API for staging and previewing content in a full site context" (`modules/workspaces/workspaces.info.yml:3`), stable since 10.3 ([Drupal 10.3 release](https://www.drupal.org/blog/drupal-10-3-0)) — is the only core mechanism that renders any page both ways at its real URL. The helper would save the native change inside a workspace Wanigan owns with `WorkspaceManager::executeInWorkspace()` (`modules/workspaces/src/WorkspaceManager.php:170`), render Live without a parameter as "as it was" and `?workspace=ID&token=T&persist=0` as "as it would be" for an authenticated user (`modules/workspaces/src/Negotiator/QueryParameterWorkspaceNegotiator.php:23-27`, `:73-91`), and publish on the owner's approval (`modules/workspaces/src/WorkspacePublisher.php:47-61`, `:85-96`). One mechanism would answer the before-render gap, the preview gap and phase 5's reach together. The costs are serious: it supports only types that are both revisionable and publishable — nodes, media, terms, block content, content menu links and path aliases (`modules/workspaces/src/Hook/EntityTypeInfo.php:34-63`) — and throws on others (`modules/workspaces/src/Provider/WorkspaceProviderBase.php:117-130`); publishing is all-or-nothing per workspace; an entity edited in a workspace cannot be edited in Live ([Using workspaces](https://www.drupal.org/docs/8/core/modules/workspace/using-workspaces)); and enabling the module adds a `workspace` cache context to every render on the site (`modules/workspaces/src/WorkspacesServiceProvider.php:40-42`). Turning it on is a site change Wanigan must never make on its own; it is a path for owners who already run it.

Without Workspaces, two lesser routes exist. Node preview stores a whole form state in the `node_preview` private tempstore and renders `/node/preview/{uuid}/full` with a preview bar (`modules/node/src/Form/NodeForm.php:254-270`; `modules/node/src/Controller/NodePreviewController.php:50-66`); it is nodes only, and building that form state without the form is unverified. The more general route writes nothing: inside its own token request the helper substitutes proposed values on the loaded entity (in `hook_entity_load` or a request-scoped param converter), and the page renders at its real URL; the helper already bypasses the render cache for traced requests (`src/core/live-helper-drupal-intercept.ts:636-651`). Save-time behaviour does not run, so the post-save verification stays authoritative. A Layout Builder tempstore layout renders only inside the builder UI with editing markup (`modules/layout_builder/src/Routing/LayoutTempstoreRouteEnhancer.php:21`), and core stages neither configuration nor code, so those previews do not exist.

### WordPress previews by filter, at the real URL, without a write

**Verdict: possible with conditions.** Core's own preview is narrow and writes: it swaps title, content and excerpt from the newest autosave of **any** author, plus opted-in meta, featured image and post format, only for the main query's post (`wp-includes/revision.php:869-907`, `:277-301`; [the_preview](https://developer.wordpress.org/reference/hooks/the_preview/); [revisioned post meta in 6.4](https://make.wordpress.org/core/2023/10/24/framework-for-storing-revisions-of-post-meta-in-6-4/)), and creating that autosave writes a revision, or the draft itself for its own author (`wp-includes/rest-api/endpoints/class-wp-rest-autosaves-controller.php:211-255`; [post revisions and autosaves](https://developer.wordpress.org/rest-api/reference/post-revisions/)). Core does, however, give the helper every filter it needs to substitute inside its own token request: post fields in `the_posts` or `posts_results` (`wp-includes/class-wp-query.php:3484`, `:3641`), meta in `get_post_metadata`, block attributes in `render_block_data`, templates in `pre_get_block_template(s)` (`wp-includes/block-template-utils.php:1139`, `:1315`), and user global styles in `wp_theme_json_data_user` (`wp-includes/class-wp-theme-json-resolver.php:564`, `:593`). Given a proposal, the page renders "as it would be" at its real URL, everywhere the post appears and not just in the main query; given a stored revision, it renders "as it was" for posts, templates, parts, navigation and global styles. Save-time processing — kses, `wp_insert_post_data`, slug uniqueness, other plugins' `save_post` work — does not run, so the post-save verify stays authoritative. Classic settings can be previewed site-wide through a draft Customizer changeset and `customize_changeset_uuid` (`wp-includes/theme.php:3536-3549`; [Customizer changesets](https://make.wordpress.org/core/2017/11/03/new-features-and-enhancements-with-customizer-changesets-in-4-9/) *(unread)*). `wp_theme_preview` on a scratch theme copy (`wp-includes/theme-previews.php:16-34`) would render changed theme files, but it writes a folder into `wp-content/themes` and is a probe, not a plan.

### Masking can be per part, and some noise can be removed instead

**Verdict: possible with conditions; variation that nothing declares is genuinely impossible to attribute.** Drupal declares most of its own variation: anything with a non-permanent max-age or a `user` or `session` context is placeholdered and rendered late (`core.services.yml:39-48`; `lib/Drupal/Core/Render/PlaceholderGenerator.php:57-80`), and the helper already records each part's cache tags, contexts, max-age and placeholder status (`src/core/live-helper-drupal-assemble.ts:295-310`). So the mask can be built from the trace rather than one page-wide noise floor: mask a part when it is placeholdered or uncacheable, its max-age is not permanent, or its contexts include `user`, `session`, `url.query_args`, `cookies:*`, `headers:*` or `ip`, and name it in the verdict — and never mask the edited part silently. Some variation can be removed for token requests: pin `REQUEST_TIME` with an early request subscriber so "time ago" output repeats (`lib/Drupal/Core/Datetime/DateFormatter.php:151-161`; `lib/Drupal/Component/Datetime/Time.php:38-68`), replace the Views `rand` order with a seeded one (`modules/views/src/Plugin/views/sort/Random.php:13-30`), and wait for BigPipe placeholders to settle or deny-list BigPipe per placeholder so the HTML arrives whole (`modules/big_pipe/src/Render/Placeholder/BigPipeStrategy.php:108-138`; `lib/Drupal/Core/Render/Placeholder/ChainedPlaceholderStrategy.php:37-62`). Unchecked: whether code reading `$_SERVER['REQUEST_TIME']` directly escapes the pin.

WordPress has no cache metadata, so variation is known by block type: gallery `randomOrder` (`wp-includes/blocks/gallery.php:484-502`), the calendar's today (`wp-includes/general-template.php:2645-2646`), relative post and comment dates (`wp-includes/blocks/post-date.php:63-68`), latest comments, RSS (`wp-includes/blocks/rss.php:22`), login/out, and a Query Loop ordered by `rand`. A `render_block` filter (`wp-includes/class-wp-block.php:717`, `:732`) can stamp `data-wanigan-vary="{reason}"` on each such block's root with `WP_HTML_Tag_Processor::set_attribute()`, which changes no layout. Two kinds can be removed: `pre_get_posts` can rewrite `rand` to `RAND(seed)` (`wp-includes/class-wp-query.php:1742-1745`, `:1916`), and the `human_time_diff` filter can recompute against one fixed now (`wp-includes/formatting.php:4010`); seeding the gallery's `shuffle()` with `mt_srand()` is plausible but unverified. `current_time()` and `time()` have no filter (`wp-includes/functions.php:78-95`), so the calendar can only be masked. On both platforms, a theme or module calling `rand()` or `time()` without declaring it, remote content and JavaScript-driven content are invisible to metadata; only the calibration render pair finds them.

### Reach is exact for content and placements, and only traced for code

**Verdict: split.** Drupal answers reach exactly for content and block placement: entity queries per bundle (`lib/Drupal/Core/Entity/Query/QueryInterface.php:115`, `:223`), block visibility conditions evaluated per placement (`modules/block/src/BlockRepository.php:56-75`), inline-block usage, file usage, the taxonomy index, and Views rows that choose a view mode (`modules/views/src/Plugin/views/row/EntityRow.php:155`). WordPress answers it by the scan above plus the template hierarchy (`wp-includes/block-template.php:153`; `_wp_page_template` at `wp-includes/post-template.php:1904-1911`), and a global style or token reaches every URL. Neither core keeps an index from a component, template or CSS rule to URLs; Drupal's nearest thing, the page-cache table, covers only anonymously cached pages on the database backend (`modules/page_cache/src/StackMiddleware/PageCache.php:370-375`). Views with contextual or exposed filters, custom controllers, archives and search produce URL spaces core cannot list. The traces Wanigan keeps, with each part's cache tags, are therefore the reverse index for code, and they are complete only for pages Wanigan has rendered.

## What stays impossible through core alone

The genuine limits share two causes, and the app should name the cause when it refuses. The table gathers them with what the app should offer instead.

| Genuinely impossible through core | Why, in core's own terms | What the app should offer |
|---|---|---|
| Literal Twig text and PHP template strings | No stored override for templates; `locale_custom_strings_*` is settings.php | A template copy in the owner's theme, as a diff; interface translation only for `t()` strings |
| Shortcode, plugin and classic-theme PHP output | Produced at render, stored nowhere (`wp-includes/default-filters.php:209`) | A theme-file copy or translation file; an agent |
| A static WordPress block's non-sourced settings | No PHP `save()`; the editor validates markup against it | The block editor |
| A stable WordPress block id | `GLOBAL_ATTRIBUTES` are `lock` and `metadata`; RTC removed | Path, name and fingerprint with re-find; say a container with no words is fragile |
| Per-language WordPress content | One value per field, post, template and option | Report the locale; say the edit changes the one stored value |
| A display-only WordPress widget | No registered update callback (`class-wp-rest-widgets-controller.php:554-560`) | Appearance › Widgets, or its plugin |
| Placing a Drupal component without code | No core entity, block or field holds a component instance | A template override that embeds it |
| Drupal per-instance style beyond CKEditor 5 Style classes, column widths and formatter settings | `$additional` is never rendered; block config has no class | An agent adds a variant prop or a scoped rule |
| Breakpoint-specific values on Drupal | Breakpoints are metadata; no value store | A change inside `@media` in theme CSS |
| A complete reverse index for components, templates and CSS | Code use is recorded nowhere; dynamic names exist | Traces, with "complete for pages rendered" stated |
| The page as it was, for configuration and code | Only content entities and a few WordPress post types keep revisions | A capture taken before every save |
| Previewing config or code changes in context | Workspaces refuses config; nothing stages code | Agent changes verified after the fact |
| Source maps for a Drupal aggregate | `CssOptimizer` strips every comment | Unaggregated reads through the helper's override |
| Pinning WordPress `time()` and `current_time()` | No filter | Mask the calendar and similar blocks by type |
| Unsynced multi-root pattern provenance and Block Hooks content in WordPress | Provenance kept only for one root; hooked blocks are inserted at render | Traces of rendered pages |

Two refusals belong to core and should be kept or added. The helper already refuses to take an inline block out of a layout without revisions, because core would then delete its content (`src/core/live-helper-drupal-edit.ts:1612`; core's cleanup of unused inline blocks is at `modules/layout_builder/src/InlineBlockEntityOperations.php:81-125`); that refusal is correct as written. Core also denies Layout Builder overrides on any non-default translation (`modules/layout_builder/src/Plugin/SectionStorage/OverridesSectionStorage.php:369-373`). The helper's layout writes do call `$storage->access('view')` (`src/core/live-helper-drupal-edit.ts:1651`), but they build the storage from the default translation they load, so that check passes even when the page showed a translation. Whether a layout move made from a translated page should be refused, as core's own UI would, was not traced; it needs a Northstar test, and until then the helper should carry the page's langcode and say "change the layout in the original language".

## Conclusion

The refusals were written as statements about Drupal and WordPress, but most are statements about how far the helper had got. That distinction is the product's own principle — prefer an honest unsupported state to an invented one — turned on itself: an owner told "this cannot be done" when core can do it is misled as surely as one told a capability exists when it does not. Each refusal should say which kind it is, "core keeps no such thing" or "Wanigan does not do this yet", and the second kind should shrink release by release while the first stays fixed. The two platforms also diverged in a way the design did not assume. WordPress 7.0 and 7.1 turned per-instance style, hover states, breakpoints and block-type styles into **data with revisions**, so on a block theme the default route for a style edit should be a REST write, with the agent as fallback. Drupal kept style as **code**, so there the agent path is correct for nearly everything beyond words, configuration and three narrow homes.

The most leverage sits in two mechanisms rather than many features. One Drupal save route keyed by target kind, running the same five gates for every target, removes most Drupal refusals and every current Drupal defect at once, and it is the extension point a future target kind plugs into. And "render this URL with a substitution, inside Wanigan's own token request" — a param converter or entity-load hook on Drupal, `the_posts`, `render_block_data`, template and global-styles filters on WordPress — gives verification its missing "before", gives owners a preview without a write, and gives phase 5 its reach samples. Because it touches nothing stored, it is also the safest thing on the list to build next.
