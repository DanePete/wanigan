## Module boundary before fixes

First commit: convert Backup into a **required** `WaniganModule` because it replaces the canonical evidence database. Move the three existing `backup:*` IPC handlers and their default-folder/stamp helpers from `index.ts` into `src/main/modules/backup.ts`; preserve existing behavior, dialogs, backup formats, preload signatures and trust/demo wrapper. Register it in `modules/register.ts`. Its implementation can remain in `backup.ts` and `backup-files.ts`; a module need not move every service file. `ModuleIpcContext.getWindow` already supplies the necessary host window. [module-registry.ts:38](../../src/main/module-registry.ts#L38), [module-registry.ts:76](../../src/main/module-registry.ts#L76), [index.ts:619](../../src/main/index.ts#L619)

Second commit: implement restore coordination against that module. A global storage-open/maintenance boundary is a missing kernel extension point, not a reason to hand-wire more backup logic into `index.ts`. Define the required runtime capability narrowly: register a storage participant, close admission, collect quiescence/closed-handle acknowledgements, and perform a fenced swap. Keep lifecycle orchestration in the host and expose typed capabilities through module context. If changing unconverted DB connection ownership, extract that connection-lifecycle boundary behavior-preservingly first; do not migrate every unrelated legacy table as part of Backup.

## Recommended protocol and non-negotiable invariants

1. **Coordinate outside the replaceable record.** All UI, daemon and CLI database participants must enter the same stable maintenance boundary before opening `wanigan.db`. A restore transaction/lock stored only inside the database being renamed cannot cover close, swap and restart. Prefer a small persistent coordination store in the private user-data root, excluded from backup restore; prove its atomic acquire/open/close protocol in isolation before adoption. An expiring lock or PID check alone does not prove a peer or child stopped.
2. **Preview, then atomically freeze and revalidate.** Bind confirmation to the selected backup manifest/content digests and a live database generation/revision. After the dialog, atomically refuse new participants and every new mutation/launch, then validate the receipt again. If the disclosed state changed, return a fresh review requirement. UI counts remain diagnostic only. Two simultaneous restore requests must have one winner.
3. **Account for every writer.** Admission must cover session preparation through finalization, headless rows, review commands, setup/teardown, checkpoint apply, all queue lanes, schedule/autopilot/intake starts, remote requests and late usage/attachment/transcript writes. Already-open peers must drain and acknowledge closure of the old generation. An unresponsive, old-version or unknown peer blocks swap. Do not delete its claim after a timeout or signal a persisted PID.
4. **Refuse uncertain execution and liability.** Read durable ownership/quarantine and unresolved remote billing from the current record after the barrier. Initially refuse restore while any remains unresolved; the preceding orphan-reconciliation work can later supply reviewed evidence. The replaced directory preserves bytes but does not enforce this safety contract. Explicit database-overwrite consent is not execution reconciliation or forgiveness of charges.
5. **Prepare recovery across process death.** Persist operation id, source/destination generation, verified manifest, staging/replaced paths and phase outside the swapped database. Keep all files private and same-filesystem rename/rollback behavior. Startup must see an unfinished operation before opening/migrating the database or dispatching work and either complete a proven rollback or enter a readable recovery refusal. Do not infer completion from the presence of a timestamped directory.
6. **Close all old handles before swap; stay closed afterward.** No participant may retain old prepared statements/finalizers while a new generation opens. In-process database failure after close needs an explicit restart/recovery result even if filesystem rollback succeeded; the present cached `_db` still refers to a closed connection. [db.ts:12](../../src/main/db.ts#L12), [backup.ts:719](../../src/main/backup.ts#L719)
7. **Restart into a hold on automation.** A restored database is historical data, not fresh authority to run archived waiting rows, schedules, autopilots or paid requests. Use a restore-generation hold outside rollback scope. Preserve old ownership as historical/unresolved evidence; require a specific review before enabling affected execution. Cross-machine restored owners cannot be trusted as local process identities. Account spending since the backup is not reconstructed by merely restoring old totals.

Start with a fail-closed restore refusal for participants that cannot prove quiescence. Do not automatically stop active agents, uninstall the scheduler, edit its OS registration or release unresolved claims as a side effect of “Restore.” The macOS daemon is installed with `KeepAlive`, so killing it once would not establish absence of future database opens. [daemon.ts:92](../../src/main/daemon.ts#L92)

## Red-test matrix for the implementation session

Use fresh user-data directories, real SQLite connections, disposable Git repositories and harmless child writers; no provider calls. Route tests through the production module/service, not a test-only replacement admission policy.

| Case | Required observation |
| --- | --- |
| UI has zero local agents; a second daemon-like process holds/writes the DB | Restore refuses or obtains its explicit close acknowledgement; no split generation or lost ownership. |
| Session/headless/review/setup/teardown starts during either dialog | Stale preview/refusal; exact original database/files and receipt remain intact. |
| New CLI or daemon begins opening after the restore barrier | It cannot open/migrate/write the old or half-installed record. |
| Dispatcher tick was already inside an awaited gate when stop begins | It cannot claim/spawn after maintenance admission closes. |
| Child has exited but finalizer or transcript/usage write is pending | Swap waits for completion or refuses; no closed-DB errors masquerading as success. |
| Active checkout receipt, expired queue quarantine, unresolved review/worktree/headless owner, or pending suggestion liability | Each independently blocks restore; status/clock changes do not bypass it. |
| Snapshot has waiting work subsequently completed in the live DB | Fresh startup does not execute that archived work; schedules and automatic starts stay held. |
| Unknown/legacy peer, suspended owner, or stale coordination heartbeat | No lease theft and no signal to persisted PIDs. Explain the specific unresolved participant. |
| Backup changes after preview; live revision changes after confirmation | Receipt fails before mutation, including the case where overwriteNewer was already true. |
| Process dies at staging, after close, after each rename and before final journal completion | Next startup preserves evidence and enters deterministic recovery without automatic dispatch. |
| Rename/rollback failure; peer acknowledgement timeout; second restore request | No success report; first operation remains attributable and replacement files are discoverable. |
| Clean no-work restore of v1/v2 backups | Verified bytes, relocated structured paths, excluded machine trust, preserved replacement and one restart still work. |

Keep existing backup/file-integrity tests. Add module conversion parity checks and one real two-process end-to-end restore/startup test; source-string checks cannot prove this boundary. Run the repository's eight `npm test` gates on implementation, plus relevant native probes and both-theme screenshots if UI changes. This planning pass does not claim those future checks passed.

## Decisions still to prove

- The coordinator mechanism and registration ordering must be tested against concurrent startup and crash; no current shared storage-maintenance primitive was found in the reviewed sources.
- Enumerate all connections/mutating background activities, including direct `new Database` users, before claiming complete participation. Pre-migration startup and older daemon binaries are especially important.
- Decide the bounded operator flow for post-restore execution/spending reconciliation. A generic “clear all blockers” button would undo both earlier safeguard phases.
- This review establishes source-level risk and acceptance criteria. It does not establish an actual SQLite corruption reproduction, OS-wide process containment, Windows behavior, or safe cross-version peer negotiation.
