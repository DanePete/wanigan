# Material and orb references for the Wanigan redesign

Accessed 2026-09-09. Dates below are publication/announcement dates stated by the source, not access dates. This research supports a full visual redesign with an expressive material object, rather than adding an animated icon to the current layout. No product code or dependencies changed; no Electron performance measurements were made.

## Visual checks actually performed

WaterBall rendered in Chrome. Changing its Box width control from 100 to 38 visibly changed the fluid's confinement; the demo showed its medium setting as 60,000 particles. That is a demo setting, not a suggested Wanigan budget or measured performance result. Its source passes pointer position and velocity into the simulation. [Live demo](https://waterball.netlify.app/), [simulation entry point](https://github.com/matsuoka-601/WaterBall/blob/main/main.ts).

Paper Gem Smoke also rendered. Selecting `shape="circle"`, `outerGlow={0}`, `innerGlow={1}` and `innerDistortion={0.8}`, with teal/ivory colors, produced a self-contained swirling marble-like orb. That is a useful material sketch for this brief. It needs no image when using the built-in circle. Its material changes over time, but adding an impulse to an angle/offset parameter would still be an approximation rather than a fluid solver. [Demo and documented parameters](https://shaders.paper.design/gem-smoke).

## Feasible implementation choices

**Recommended fidelity target: a custom material orb rendered with Three.js, with explicit motion state.** Keep the glass shell, material interior, facial expression and input response as separate layers. Pointer acceleration should produce a bounded impulse; the interior should lag, overshoot and settle. For water, show a free surface and a meniscus; for gas, use a density pattern that bends and dissipates. These are proposed design requirements, not capabilities supplied by a single researched component.

There are three materially different ways to build it:

1. **Art-directed approximation:** Three.js materials or Paper's circular shader plus damped tilt/deformation state. A practical way to prove the composition and character, but describe the result as responsive animation. It cannot honestly be called simulated sloshing merely because it reacts to the pointer.
2. **Reduced simulation:** an evolving wave/height-field model inside the orb, with pointer impulses and damping, combined with a refractive shell. Three's Compute Water is a relevant reference, but its planar height field would need adaptation; it cannot by itself represent overturning splashes and detached droplets. [Source](https://github.com/mrdoob/three.js/blob/dev/examples/webgpu_compute_water.html).
3. **Fuller fluid simulation:** adapt an MLS-MPM approach and fluid surface renderer for an interior spherical boundary. WaterBall and the author's [Splash](https://github.com/matsuoka-601/Splash) prove browser feasibility; they are standalone graphics projects, not production-ready React orb components. [WaterBall](https://github.com/matsuoka-601/WaterBall). Splash was announced **March 21, 2025**, according to the [author's portfolio](https://matsuoka-601.github.io/#splash).

**Spline/Hana** are strong tools for authoring the surrounding materials and interaction studies. Spline's physics documentation describes gravity, forces, rigid bodies and collisions; it does not establish liquid simulation inside an orb. Its React/Vanilla runtime exports preserve animation/events and allow self-hosted downloads; the Three.js/R3F export path does not preserve the same animation/event runtime. [Physics](https://spline.design/solutions/physics-simulations), [export documentation](https://docs.spline.design/exporting-your-scene/web/exporting-as-code).

**Rive** is a strong choice for a deliberately authored expressive character layered with the material, especially for coordinated eyes, glow and state changes. Its current React API also exposes an experimental GPU Canvas option for 3D/shaders, but that does not amount to a supplied fluid solver. Its new-work data-binding approach is the better starting point than deprecated state-machine input hooks. [React API](https://rive.app/docs/runtimes/react/parameters-and-return-values).

## Electron boundaries to preserve

Three's WebGPU renderer can choose WebGL2 as a rendering backend, but both inspected compute simulation examples explicitly require WebGPU; general renderer fallback does not prove that these simulations work on WebGL2. Probe the actual packaged Electron adapter and provide an intentional reduced/static mode. [Renderer documentation](https://threejs.org/docs/pages/WebGPURenderer.html), [Compute Water capability guard](https://github.com/mrdoob/three.js/blob/dev/examples/webgpu_compute_water.html), [Fluid Particles capability guard](https://github.com/mrdoob/three.js/blob/dev/examples/webgpu_compute_particles_fluid.html).

Use one bounded canvas for the principal orb, package assets locally, stop simulation when inactive, and release GPU resources on teardown. Keep terminal rendering and selection independent. Measure frame time and idle GPU use in Wanigan before selecting a simulation resolution; the live demo's particle counts do not establish an appropriate application budget. These are proposed acceptance checks. Library-specific offline assets, licenses and reduced-motion controls are covered in the [companion library research](2026-09-09-animation-libraries.md).
