# Wanigan feature-gap research: implementation audit

Date: 2026-09-15. This is the local-code half of the feature research. It audits the current working tree, including existing modified and untracked files, rather than the last commit or the published marketing copy. No app behavior was changed. No Wanigan agent sessions or model-backed product workflows were launched. “Existing” means implementation is present and was read; it does not mean this audit independently exercised it in a running app. “No implementation found” is a bounded code finding, not proof that an external CLI cannot provide the capability.

The strongest opportunities are completing the evidence/review loop, joining parallel work into a verified integration result, connecting external work intake, and filling provider-specific evidence gaps. Wanigan already implements much of the ordinary competitor checklist: task graphs, worktrees, review commands, checkpoints, budgets, scheduling, a mobile control plane, transcript search, memory, and provider packs.

## Existing work deliberately included

At audit start, `git status --short` included modified main/session/schedule/headless/preload code, navigation/views/styles and test/probe files, plus untracked `SessionReview.tsx`, `SessionHistory.tsx`, `TranscriptReader.tsx`, `HomeWork.tsx`, `scheduled-execution.ts`, session permission/name helpers and UX research artifacts. These were treated as current implementation where read, never as empty gaps. This audit creates only this note and preserves all of that work.

The reference guide is useful orientation but is not the final feature authority. For example, it describes a narrower phone-control surface than the current separately scoped repository-review and goal-decision routes. Implementation and typed boundaries take precedence for this audit; a separate runtime check is needed to establish packaged-release behavior.

## Recommended sequencing

1. Make the existing review experience reliable end to end: session worktree checks, exact tested-tree identity, stale-result handling, and a portable proof bundle.
2. Complete parallel integration: explicit fan-in checkout, conflict state, combined verification and traceable human landing decision.
3. Add explicit GitHub issue/PR-feedback intake using the existing goal/queue/review structure.
4. Fill Codex evidence coverage, then add browser/dev-server evidence where the projects need it.
5. Evaluate managed local isolation and runnable learning experiments as larger efforts, with their runtime and cost boundaries made explicit.

The classification above is source inspection. No runtime/security/performance claims were verified by execution in this research pass. No tests were run because there is no code change; document whitespace was checked before handoff.
